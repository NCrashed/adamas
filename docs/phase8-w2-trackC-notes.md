# Трек C волны 2 Фазы 8: байты в языке

Развилку решает владелец — это расширение поверхности языка. Трек её **мерил**,
и здесь только то, что он установил, и чем именно установил. В `adamas-design.md`
не внесено ничего.

Ветки доведены до прогона, и **работают все**: `gzopen("file.gz")` берётся
настоящей zlib через `-lz` каждой из них. Лежат они в истории отдельными
коммитами и оттуда достаются:

| Ветка | Коммит | Строк |
|---|---|---|
| **(а)** строка есть `Array (n+1) UInt8` везде | `4137386` | +88 / −0, один файл |
| **(б)** байтовый литерал массива | `4bd2972` | +64 / −2, один файл |
| **(а′)** то же, что (а), но **только** под написанным `Array n UInt8` | `47d96de` | +106 / −0, один файл |

Третья взялась по дороге и в постановке её нет. Заводить её пришлось потому, что
замер (а) упёрся в вопрос, который постановка называет самым ценным, — **не
закрывает ли (а) дорогу к нормальным строкам**, — и ответ на него оказался не
«да/нет», а «смотря какая (а)». Разница между (а) и (а′) — одна охрана в
условии, и именно она решает, занят ли синтаксис `"…"` навсегда.

Дерево к концу трека возвращено к состоянию до проб: решения нет — значит нет и
реализации.

## Мера на старте

Снято на `3f79482`, до единой правки.

| Что | Значение |
|---|---|
| Гейт `cargo test --workspace --all-targets --no-fail-fast` | `EXIT=0`, целей 102, пройдено 1453, упало 0, пропущено 2 |
| Строковых значений в языке | 0 |
| Форм литерала (`LitKind`) | 4: `Nat`, `Int`, `Float`, `Str` |
| Мест, читающих `LitKind::Str` | 3, все в `adamas-elab/src/expr.rs` |

Отказ снят прогоном `adamas check` и подтверждён дословно:

```
greeting : Array 3 UInt8
greeting = "hi"
  отрицательный, дробный или строковый литерал пока не элаборируется: …
  строк нет вовсе (§4.5)
```

Токен `Str` в лексере есть и escape'ы (`\n \t \r \0 \\ \" \' \u{…}`) **проверяет**,
но не раскрывает: текст литерала хранится как написан, вместе с кавычками.
Второй читатель того же токена — имя ABI в `extern "C"`, и он идёт своим путём
(`parser.rs:757`), а не через `LitKind`.

## Что сделано в каждой пробе

**(а)** — в `Elaborator::literal` одна ветка перед всем прочим: `LitKind::Str`
собирается спайном `arraySet` над `arrayNew` длины `n+1`. Ожидаемый тип не
читается **вовсе**: у строки он один, и длина выводится из литерала; разойдись
она с написанным типом — скажет проверка типов, и скажет обоими числами.
Нулевые байты пропускаются: `arrayNew` уже залил ими блок.

**(б)** — в `Elaborator::list` одна ветка перед всем прочим: под написанным
`Array n t` та же скобка `[a, b]` есть массив, а не `Cons`/`Nil`. Форма
выбирается ожидаемым типом — **тем же правилом**, каким его выбирает числовой
литерал (§4.3). Байтам (б) не специфична: `[7, 8, 9] : Array 3 Int64` работает
тем же кодом, и обе формы стоят рядом в одном файле (`b6`). Заполнителем
`arrayNew` служит первый элемент — значения у ячейки произвольного типа взять
больше неоткуда.

**(а′)** — та же (а) плюс одна охрана: ветка срабатывает, только если
**ожидаемый тип написан** и это `Array n UInt8`. Длина по-прежнему не смотрится
— её решает литерал, — смотрится ячейка. Всё остальное дословно то же.

Лексер и парсер не тронуты ни одной пробой. Своей формы (`b"…"`, `#[…]`) (б) не
заводит нарочно: это было бы четыре места вместо одного (лексер, парсер, печать,
LSP), а мерить надо **дешёвую** ветку — если дешёвая уже проигрывает, дорогая
тем более.

## 1. Сколько мест правится и сколько принимают молча

Счёт снят компилятором и прогонами: «громко» — место, отказавшее сборку;
«молча» — место, которое приняло новую форму и **не сказало о ней правды**.

| Развилка | Громких | Молчаливых | Строк | Файлов |
|---|---|---|---|---|
| **(а)** | **0** | **5**, из них одна — **обрыв процесса** | +88 / −0 | 1 |
| **(б)** | **1** | **1** | +64 / −2 | 1 |
| **(а′)** | **0** | **3**, из них одна — **обрыв процесса** | +106 / −0 | 1 |

Два молчаливых места (а) из пяти — и сверх них утечку сахара в диагностику —
охрана (а′) снимает разом, и это прогон, а не довод: мёртвых веток не возникает
(обе живы — они и отвечают там, где массив не написан), паттерн перестаёт
расходиться с выражением (обе стороны отказывают строке, если байтового массива
не написано), и `odd : "hi" -> UInt64` отвечает про литерал, а не про
`arraySet 3 UInt8 (…)`.

Остаются у (а′) три: половина ложного текста отказа, встроенный ноль и обрыв на
длинном литерале. Все три — те же, что у (а), и ни одна к охране отношения не
имеет.

Цена охраны измерена и она есть: там, где (а) отвечала «ожидался
`Array 3 UInt64`, получен `Array 3 UInt8`» — то есть называла оба типа, — (а′)
отвечает общим «строковый литерал пока не элаборируется». Точность
диагностики на чужой ячейке хуже; на всех прочих путях лучше.

**Ноль громких у строковых веток — главное число всех трёх проб.** Сборка (а)
прошла с первого раза:
в 144 867 строках Rust не нашлось ни одного исчерпывающего `match`, который
заметил бы, что у строкового литерала появилось значение. `LitKind::Str`
существовал, и все три его читателя уже имели свою ветку — каждая говорит
«строк нет».

Единственное громкое место у (б) — сам вызов `self.list(…)`, и создано оно моей
же правкой сигнатуры. То есть и здесь язык не сопротивлялся.

**Все три прошли гейт целиком, не тронув ни одного теста: 102 цели, 1453
пройдено, 0 упало — до правки и после каждой из трёх.** Корпус расширения
поверхности языка не наблюдает вовсе.

### Молчаливые места (а), каждое — прогон

1. **Паттерн остался с прежним отказом.** `classify "hi" = 1` отвечает «строк
   нет вовсе (§4.5)», хотя выражением строка уже есть. Ветка
   `written_literal` — `LitKind::Str => return None` — исчерпывающая, компилятор
   о ней молчит. Свидетель — `s10`.
2. **Текст отказа под снапшотом только наполовину.** Единственный снапшот с
   этой строкой (`golden__errors-literal-without-a-primitive.snap`) записан на
   **отрицательном** литерале и остался зелёным. Ложная половина сообщения не
   покрыта ничем.
3. **Две ветки `Str` стали мёртвыми** — в `defaulted` и в `primitive_literal`:
   обе теперь за ранним возвратом, и обе по-прежнему написаны. Компилятор
   мёртвого `match`-плеча не видит; проверено мутантом — плечо `defaulted`,
   заменённое на `unreachable!`, оставляет зелёными и все десять свидетелей, и
   корпус (`adamas-cli --test golden`, 4 из 4).
4. **Встроенный ноль принимается молча.** `"hi\0there" : Array 9 UInt8`
   проверяется; чужая сторона прочтёт два байта. Ни отказа, ни предупреждения;
   свидетель `s9` фиксирует само принятие.
5. **Литерал длиннее ~2650 байт роняет процесс.** Не отказ, а
   `stack overflow, aborting`, и одинаково на всех трёх путях:

   | байт | `adamas check` | машина | понижение C |
   |---|---|---|---|
   | 2600 | 0 | 0 | 0 |
   | 2700 | 134 | 134 | 134 |

   Это паника от валидного пользовательского текста — жанр, который CLAUDE.md
   называет серьёзным багом. Причина структурная: терм строки глубиной в саму
   строку, тот же обрыв, ради которого §4.3 держит `UNARY_LIMIT = 256` у
   унарного числа.

Сверх пяти — **диагностика показывает сахар, а не написанное**: `"hi"` в позиции
типа отвергается словами «получено `arraySet 3 UInt8 (arraySet 3 UInt8 (arrayNew
UInt8 3 0) 0 104) 1 105`». Отказ громкий и правильный, но автор написал четыре
символа, а прочёл шестьдесят.

### Молчаливое место (б)

**Пустая скобка под `Array 0 UInt8` уезжает в список.** Заполнителя `arrayNew`
взять неоткуда, и `[]` идёт прежним путём: при объявленном `Nil` отказ читается
«ожидался `Array 0 UInt8`, получен `List{?0} (?6)`», без него — «имя `Nil` не
найдено». Оба называют форму, которой автор не писал.

Прочего у (б) нет, и это проверено, а не предположено: **паттернов-списков в
языке нет вовсе** (`firstOf [a, b] = a` — «ожидается `=`, а не `[`»), поэтому
асимметрии выражения и паттерна у (б) не возникает; отказ строке остаётся
дословно верным; мёртвых веток не появилось; обрыва процесса нет — длинный
литерал отводит **парсер** своим пределом вложенности.

### Потолок длины: есть у всех, и они разные

| Развилка | Потолок | Чем отвечает за потолком |
|---|---|---|
| **(а)** и **(а′)** | ~2650 байт | `stack overflow, aborting`, кода 134, ни строчки текста |
| **(б)** | **256 элементов** (255 байт плюс ноль) | «вложенность глубже предела в 256» с указанием на скобку |

Обрыв у строковых веток прощупан бинарным поиском по длине: 2600 берётся,
2700 роняет, и граница одна на все три пути. У (а′) она ровно там же — охрана
терма не меняет.

У (б) потолок в **десять раз ниже** и при этом не стоит ничего: он унаследован
от `adamas-parser/src/depth.rs`, который уже стоит и уже назван. Имя файла в 255
байт помещается; шаблон, запрос или шейдер — ни в ту, ни в другую.

## 2. Где живёт нулевой байт

**(а): в литерале, и это соглашение компилятора.** `"hi"` есть `Array 3 UInt8`,
`arrayIndex` видит длину **с нулём**, и написанный тип обязан её назвать: автор
пишет `Array 18 UInt8` для семнадцатибуквенного имени. Ошибиться в счёте легко —
я ошибся на первой же попытке, и отказ был точный («ожидался `Array 19 UInt8`,
получен `Array 18 UInt8`»).

**(б): у автора, дословно.** Последним элементом стоит `0x00`, написанный
рукой. `arrayIndex` видит ту же длину с нулём, но она не результат
договорённости — она написана.

Побочное следствие (а), которое стоит назвать: **пустой строки длины ноль не
бывает**. `"" : Array 1 UInt8` и есть `arrayNew UInt8 1 0` — один нулевой байт.
Это правильно для C и странно для всего остального.

**Наблюдаем ноль ровно одним способом, и это замер, а не рассуждение.** Мутант
«`arrayNew` заливает единицей» (M5) оставляет `gzopen` **зелёным**: обе функции
возвращают ненулевой указатель, ответ программы по-прежнему 11. Красным его
делает только свидетель, сверяющий **имя файла на диске** — там оказывается
`zprobe-written.gz` с лишним байтом. То есть «вызов удался» про завершающий ноль
не говорит ничего, и свидетель без проверки имени ловил бы пустоту. Это и есть
причина, по которой §5.3 не вправе обещать больше, чем обещает: ноль — соглашение
**чужой** стороны (трек A волны 2), и язык его не проверяет ни в одной из веток.

## 3. Что с юникодом

**(а): байты UTF-8, и другого ответа у неё нет.** `"привет"` есть `Array 13
UInt8` — двенадцать байт плюс ноль, — и `arrayIndex hello 0` даёт 208 (`0xD0`) у
всех трёх вычислителей. `\u{416}` тоже раскрывается в UTF-8: два байта, 208 и
150. Довод не в удобстве, а в том, что других кандидатов нет: `Char` в ядро
сознательно не взят (`prim.rs` перечисляет десять примитивов, `Char` среди них
отсутствует, хотя §4.11 его называет), кодовым точкам в `Array n UInt8` места
нет, а отказ нелатинскому литералу отверг бы текст, который язык и так читает
UTF-8.

Цена названа: **длина в типе — байтовая, а не буквенная**, и «привет» стоит 13,
а не 7. Это ровно то, что §4.5 и обещает («UTF-8 ByteString»), но в написанном
типе это видно всякий раз.

**(б): вопрос не встаёт, потому что кодирует автор.** `"привет"` не пишется;
пишутся тринадцать чисел (`b3`). Ошибка кодировки становится ошибкой автора и не
ловится ничем — числа валидны по построению.

## 4. Что печатает машина

**Обе пробы печатают спайн, и совпадает он с понижениями по тому же правилу,
каким совпадает всякий массив.**

```
-- (а), значение `"\u{416}"`
arraySet 3 UInt8 (arraySet 3 UInt8 (arrayNew UInt8 3 0) 0 208) 1 150
-- (б), значение `[0x68, 0x69, 0x00]`
arraySet 3 UInt8 (arraySet 3 UInt8 (arrayNew UInt8 3 104) 1 105) 2 0
```

Строкой обратно не печатается ни одна: значение есть массив, и машина печатает
его как массив. Разница между образцами — заполнитель `arrayNew`: у (а) ноль, у
(б) первый элемент.

**Договор трёх на массив не распространяется вовсе, и это не свойство строк.**
Понижение отвечает на `main : Array 3 UInt8` названным отказом — «ответ
программы — массив: печатать его нечем (§4.11)», — а машина печатает спайн. То
есть сравнивать нечего **уже сегодня**, безотносительно того, откуда массив
взялся.

Наблюдаемо поэтому чтение ячейки, и там договор держится: фикстуры `s6` (а) и
`b4` (б) дают **111** у машины, у понижения C и у понижения LLVM, живых блоков
ноль у обоих.

**Цена в блоках у обеих одна и равна нулю сверх массива.** Контрольная пара:
семнадцатибайтовый литерал против `arrayNew 18 blank` — «блоков выдано 1» и там,
и там (`s7`/`s8` для (а), `b9` для (б)). Спайн `arraySet` схлопывается
переиспользованием Perceus в запись на месте; литерал не платит ни ячейки на
байт, ни ячейки вообще сверх самого массива.

## 5. Годится ли для `gzopen("file.gz")`

**Годится всем трём, и это настоящая сборка с `-lz`, а не рассуждение.** У (а′)
путь буквально тот же, что у (а): ожидаемый тип там написан (`written : Array 18
UInt8`), охрана срабатывает, и свидетели (а) зелены до единого.

zlib в окружении есть — заголовок и библиотека приезжают с gcc; во `flake.nix`
её нет, и добавлять не потребовалось. Секция `[link] libraries = ["z"]` (волна 1)
довозит ключ до обоих понижений.

Программа наблюдает три разных ответа одной чужой функции, и подделать их
нечем: `gzopen(имя, "wb")` открывается, тот же файл после `gzclose` открывается
на `"rb"`, а `gzopen("zprobe-absent.gz", "rb")` **не** открывается. Ответ 11.

| Путь | (а) | (б) |
|---|---|---|
| понижение C | 11, блоков 12, живо 0 | 11, блоков 12, живо 0 |
| понижение LLVM | 11 | 11 |
| файл на диске | `zprobe-written.gz`, 20 байт | то же |
| машина | **отказ**: «`gzopen` одалживает чужой стороне буфер: у массива машины адреса нет» | тот же отказ |

Отказ машины — не свойство литерала, а названная граница трека A волны 2:
массив в машине есть спайн, адреса у него нет. Фикстура `gzopen` ложится поэтому
в `programs/`, а не в `eval/`, какую бы ветку ни выбрали.

Прототип печатается словом (`uint64_t`/`i64`) с `__asm__`-меткой, поэтому
`zlib.h` не подключается и конфликта типов с системным заголовком нет — то же
решение трека D волны 1 работает и здесь.

**Чего стоит имя файла автору.** Четыре литерала одной и той же программы:

| | строк | символов |
|---|---|---|
| (а) | 11 | 194 |
| (б) | 19 | 474 |

У (б) к каждому литералу пришлось приписать комментарий с тем, что числа
означают, — без него программу не прочесть. Это не стилистика: комментарий,
расходящийся с числами, — молчаливый баг, которого у (а) нет по построению.

## Рекомендация

**Рекомендация трека — (а′): строка элаборируется в `Array (n+1) UInt8`, но
только там, где этот тип написан.** Это рекомендация, а не решение.

Сводка по трём, чтобы довод был виден числами, а не порядком абзацев:

| | (а) | (б) | (а′) |
|---|---|---|---|
| Громких мест | 0 | 1 | 0 |
| Молчаливых | 5 (обрыв среди них) | 1 | 3 (обрыв среди них) |
| Потолок длины | ~2650 байт | **256 элементов** | ~2650 байт |
| Чем отвечает за потолком | обрыв | отказ | обрыв |
| Имя файла автору | 194 символа | 474 | 194 |
| Ошибка кодировки | ловится компилятором | не ловится ничем | ловится компилятором |
| Синтаксис `"…"` занят | **навсегда** | свободен | **только под массивом байт** |
| Блоков на литерал сверх массива | 0 | 0 | 0 |
| `gzopen` тремя путями | C и LLVM да, машина нет | то же | то же |

**Против (б) решает потолок, а не удобство.** 256 элементов — это имя файла и
больше ничего; буфер, запрос или шаблон не пишутся вовсе, и снять это без
правки предела вложенности парсера нельзя. Сверх того у (б) ошибка кодировки не
ловится ничем и не может быть поймана, а комментарий над числами — новый жанр
молчаливого бага.

**Против (а) в пользу (а′) решает занятость синтаксиса.** (а) тратит `"…"` на
буфер C ABI **везде**, включая позиции, где в будущем будет стоять `String`.
(а′) тратит его ровно там, где автор написал `Array n UInt8`, — то есть на
границе, ради которой развилка и заведена, — и в остальных позициях литерал
по-прежнему отвергается. Два молчаливых места (а) и утечка сахара в диагностику
при этом исчезают, а стоит охрана восемнадцать строк.

**Чего числа не решают.** Возражение «строковый литерал вообще не должен значить
буфер C, пока в языке нет строк» ни одним замером не снимается: все три ветки
заводят одну и ту же сущность, и спор идёт о синтаксисе, а не о ней. (а′) —
самый узкий способ сказать «да» на этот вопрос; (б) — способ сказать «нет».
Выбор между ними — вкус к языку, и он не мой.

Что обязано войти в выбранную ветку, прежде чем она станет фичей, и это
**условие**, а не пожелание:

1. **Предел длины с названным отказом** — по образцу `UNARY_LIMIT` §4.3, который
   стоит ровно из-за той же болезни. Без него компилятор падает от валидного
   текста; у (б) этого пункта нет — предел ей достался от парсера.
2. **Встроенный ноль**: либо отказ, либо предупреждение. Молча отдавать чужой
   стороне обрезанное имя нельзя. Пункт общий для всех трёх.
3. **Текст отказа** обязан перестать говорить «строк нет вовсе» там, где строки
   уже есть хоть в одной позиции. У (а′) он остаётся верным по существу и
   неверным по букве.

И **отдельно, потому что это решение, а не деталь**: (а) измерена в **дешёвом**
исполнении — сахар в спайн `arraySet`. У неё есть второе исполнение — **узел
ядра** для блока байт, — и разница между ними именно там, где живёт ответ на
вопрос про `String` (ниже).

## Чего (а) стоит против будущего `String` (§4.5)

Развилка (в) вне волны, но по дороге выяснилось, чего (а) ей стоит, и это самое
важное, что трек может сказать. Ответ оказался не «да/нет», а **«смотря какая
(а)»** — ради этого и заведена (а′).

Мешают три вещи, и они разной природы: **синтаксис — снимается охраной,
нулевой байт — не снимается ничем, дешёвое исполнение — снимается узлом ядра**.

**Синтаксис — и это единственное, что меряется сегодня.** §4.5 обещает `String`
как UTF-8 ByteString, §4.11 явно говорит, что `String` **не** `Flat`, а длина
`Array n a` стоит **в типе** — значит `Array n UInt8` и `String` типы разные, и
один другим стать не может. Отсюда вопрос: что будет значить `"hi"`, когда
`String` доедет?

- У **(а)** — уже занято, всюду и навсегда: `"hi"` есть буфер C. Приезд `String`
  либо меняет смысл написанного (ломая всё, что было), либо вводит класс
  преобразования, после которого сырой формой останется массив с нулём.
- У **(а′)** — занято **только** под написанным `Array n UInt8`. Во всякой
  другой позиции литерал по-прежнему отвергается, и это проверено прогоном
  (`loose : Nat = "hi"` отказывает). То есть место для `String` остаётся
  буквально свободным.
- У **(б)** — не занято вовсе.

Разница между (а) и (а′) здесь — вся разница по этому вопросу, и стоит она
восемнадцать строк.

Как именно `String` встанет рядом — **разбор, а не замер**, и помечено так
нарочно. По-видимому, тем же механизмом, каким §4.3 совмещает `42 : Int8` и
`42 : Nat`: литерал элаборируется в свою сырую форму, а класс преобразования
(`FromNat`/`FromInt`/`FromFloat`, а здесь — что-то вроде `FromString`) переводит
её в целевой тип, и «преобразование применяется, только если объявлено».
Проверить это можно будет только вместе с `String`.

**Соглашение мешает, и это нулевой байт.** Он нужен C и не нужен `String`:
`fromString` каждого инстанса обязан будет его отбросить, иначе `length "hi"`
станет 3. То есть либо в языке навсегда остаётся сырая форма, у которой длина на
единицу больше написанного, либо ноль отовсюду срезается — и тогда
`gzopen("file.gz")`, то есть весь довод (а), перестаёт работать без обёртки.
**Развилка эта не снимается выбором между (а) и (б)**: у (б) ноль тоже есть,
только пишет его автор.

**И мешает дешёвое исполнение.** Обрыв на 2650 байтах — прямое следствие того,
что литерал есть спайн длиной в себя. `String`, у которого литерал не может быть
длиннее двух с половиной килобайт, — не `String`. Узел ядра (блок байт одним
листом) снимает это по построению, даёт понижению положить литерал в `.rodata`
вместо записи по байту, и не роняет `Term` за 48 байт (`Rc<[u8]>` — два слова).
Цена его названа: он трогает **все три вычислителя**, а машину и эмиттеры правит
трек B параллельно. Поэтому он не измерен, а назван.

Итог для владельца в одну строку: **синтаксис (а) закрывает, (а′) нет, и стоит
разница восемнадцать строк; нулевой байт не закрывает ни одна из трёх и потому
решается сейчас, а не когда `String` доедет**.

## Мутанты

Свидетели — прогоны, а не записанные ожидания: 10 у (а) и 11 у (б), каждый
сверяет ответ `adamas check`, машины, обоих понижений либо имя файла на диске.
Контроль на нетронутой пробе — **ноль** красных у обеих. В корпус они не
положены намеренно: фичи нет, а свидетель без фичи — тест на пробную правку.

(а′) гоняется тем же набором, что (а): все десять зелены, то есть охрана не
отняла ни одного пути, ради которого ветка и заведена. Своих мутантов у неё нет
— код у неё тот же, плюс охрана, и охрану проверяют четыре прогона отказа
(`s13` без массива, `s3` с чужой ячейкой, `s10` паттерном, `s11` в позиции типа).

| Мутант (а) | Красных |
|---|---|
| `string_bytes`: не дописывать завершающий ноль | 9 |
| `string_literal`: ячейка `Int8` вместо `UInt8` | 9 |
| `string_literal`: `arrayNew` заливает единицей | 6 |
| `string_bytes`: символ одним байтом, не UTF-8 | 2 |
| `string_bytes`: escape `\u` усечён до байта | 2 |
| `string_literal`: нулевые байты не пропускаются | 1 |

| Мутант (б) | Красных |
|---|---|
| `array_literal`: ячейка не раздаёт свой тип элементу | 10 |
| `array_element`: ячейка берётся из длины, а не из элемента | 10 |
| `array_literal`: длина на одну меньше | 10 |
| `array_literal`: номер ячейки сдвинут | 8 |
| `array_literal`: остальные ячейки не пишутся | 7 |
| `list`: пустая скобка не отводится | 1 |
| `array_literal`: первая ячейка пишется дважды | 1 |

**Выживших в итоговых наборах нет ни у одной пробы**, но по дороге их было двое,
и оба — дефекты **свидетелей**, а не проб. Это и есть причина, по которой
мутанты гоняются.

1. **«`arrayNew` заливает единицей» (а) проходил `gzopen` зелёным.** Обе
   функции возвращали ненулевой указатель, ответ программы оставался 11 — то
   есть свидетель, сверяющий **ответ**, про завершающий ноль не говорит ничего.
   Красным мутанта делает только добавленный свидетель имени файла на диске
   (5 красных стало 6). Вывод записан выше, пункт 2: ноль наблюдаем именем, а
   не успехом.
2. **«Пустая скобка не отводится» (б) выживал при нуле красных.** Свидетеля с
   `[] : Array 0 UInt8` в наборе не было вовсе, а мутант роняет компилятор:
   `panicked at expr.rs:3095: index out of bounds: the len is 0 but the index
   is 0`. Со свидетелем — 1 красный. То есть охрана пустой скобки несущая, и
   без мутанта это осталось бы утверждением.

«Нулевые байты не пропускаются» (а) и «первая ячейка пишется дважды» (б) — по
одному красному, и красит их обоих **печать значения**: это оптимизации формы
терма, поведения они не меняют, и поймать их иначе нечем.

Ни одна проба не добавила ни цели, ни теста: свидетели трека живут прогонами в

**MSRV поймал в (б) настоящую поломку, и поймал только он.** Первая редакция

## Что из постановки опровергнуто

1. **«(а) минимально трогает язык».** Трогает минимально — **ноль** громких мест
   и восемьдесят восемь строк в одном файле, — но именно поэтому и опасно:
   расширение поверхности языка не заметил ни один из 1453 тестов и ни один
   `match`. Три прежних читателя `LitKind::Str` пережили решение молча: две
   ветки стали мёртвыми (`defaulted`, `primitive_literal` — обе теперь за
   ранним возвратом), третья (`written_literal`, паттерн) осталась живой и
   отвечает «строк нет вовсе». Дешевизна правки здесь снова оказалась доводом
   **против** неё, ровно как у трека A волны 1. Лечится это не объёмом, а
   охраной: у (а′) при тех же нуле громких мест молчаливых остаётся три.
2. **«(б) честнее к §4.5».** Честнее только на словах отказа. По прогону (б)
   заводит **ту же самую** сущность — плоский байтовый массив с нулём в хвосте, —
   и от (а) отличается лишь тем, кто набирает байты. §4.5 при этом не выполнена
   ни той, ни другой: `String` нет ни в одной.
3. **«(б) — только байтовый литерал».** Не только: измеренная (б) не знает про
   байты ничего и одинаково работает на `Array 3 Int64`. То есть развилка на
   самом деле не «строки против байтов», а «литерал массива вообще» против
   «строкового литерала», и первая шире, чем её ставила постановка.
4. **«Молчаливое принятие хуже громкого отказа».** Здесь верно с поправкой,
   меняющей вывод: у (а) есть не молчаливое принятие, а **обрыв процесса**, и он
   хуже обоих. Сравнивать ветки по этому правилу нельзя, пока обрыв не закрыт
   пределом.
5. **«Строковый литерал в `Array n UInt8` поедет без правок границы»** (трек A
   волны 2). Подтверждено дословно: границу не пришлось тронуть ни одной буквой
   ни в одной пробе, и `gzopen` берётся обоими понижениями.
6. **«Имя файла придётся писать числами»** (про (б)). Подтверждено и измерено:
   474 символа против 194, и сверх того — комментарий к каждому литералу, без
   которого программа нечитаема.
7. **Развилка поставлена из двух вариантов, а их три.** Постановка разводит (а)
   и (б) по тому, **что** элаборируется; замер показал, что решающая ось другая
   — **где** оно элаборируется. (а) и (а′) заводят одну и ту же сущность и
   расходятся одной охраной, но по вопросу «занят ли `"…"` для будущего
   `String`» они на разных сторонах, а (а′) и (б) — на одной. Без третьей ветки
   ответ на самый ценный вопрос постановки был бы «да, закрывает», и это был бы
   ответ про реализацию, а не про развилку.

## Что трек оставил другим

- **Ведущему.** Три решения, и ни одно не деталь: (1) какая из трёх веток — и
  главный вопрос здесь не «строка или числа», а **занят ли синтаксис `"…"`
  вне границы**; (2) **нулевой байт** — соглашение компилятора, обязанность
  автора или запрет, и ответ переживёт все три ветки и доедет до `String`;
  (3) если строковая, то сахаром или узлом ядра — от этого зависит, будет ли у
  литерала потолок в два с половиной килобайта и обрыв за ним.
- **Треку B (машина и корпус).** Литерал любой из веток машина считает уже
  сегодня — договор трёх на `s6`/`b4` держится. Не держится он на **займе**:
  `gzopen` машина отвергает, и фикстура с ним ляжет в `programs/`, пока массив у
  машины остаётся спайном.
- **Треку zlib.** `compress2`/`uncompress` строк не просят вовсе, и от этой
  развилки не зависят. Просит их `gzopen`, и он проверен — всеми тремя ветками.
- **Вне волны, как и было:** тип `String` (§4.5), `Char`, срезы, операции над
  строками.

## Приложение: программа `gzopen`, которой снят пункт 5

Фикстуры проб в корпус не положены (фичи нет), и живут они в песочнице, которая
сеанс не переживёт. Здесь — та единственная, без которой утверждение про zlib
не перепроверить. Манифест рядом: `[package] name = "zprobe"` и
`[link] libraries = ["z"]`.

Написана она в форме (а); под (б) те же четыре литерала пишутся числами, и
больше не расходится ничего.

```adamas
data Unit where
  MkUnit : Unit

data Bool where
  True : Bool
  False : Bool

pick : Bool -> UInt64 -> UInt64 -> UInt64
pick True yes no = yes
pick False yes no = no

effect Foreign

extern "C" fn gzopen : Array n UInt8 -> Array m UInt8 -> CPtr
extern "C" fn gzclose : CPtr -> Int32

nowhere : CPtr
nowhere = 0

written : Array 18 UInt8
written = "zprobe-written.gz"

absent : Array 17 UInt8
absent = "zprobe-absent.gz"

writeMode : Array 3 UInt8
writeMode = "wb"

readMode : Array 3 UInt8
readMode = "rb"

opened : CPtr -> UInt64
opened p = pick (eqUInt64 p nowhere) 0 1

body : (ω u : Unit) -> {Foreign} UInt64
body u =
  let sink : CPtr = gzopen written writeMode
  let madeIt : UInt64 = opened sink
  let shut : Int32 = gzclose sink
  let back : CPtr = gzopen written readMode
  let reopened : UInt64 = opened back
  let shutAgain : Int32 = gzclose back
  let missing : CPtr = gzopen absent readMode
  let refused : UInt64 = opened missing
  addUInt64 madeIt (addUInt64 (mulUInt64 reopened 10) (mulUInt64 refused 100))

runForeign : {a : Type} -> ((ω u : Unit) -> {Foreign} a) -> a
runForeign k = handle @Foreign k with
  return v -> v

-- 11: открылось на запись, открылось на чтение, отсутствующего не открыло.
main : UInt64
main = runForeign body
```

Эта программа **прогнана**, а не написана по памяти: `adamas run --backend c` и
`--backend llvm` печатают `11` при нуле живых блоков, и на диске остаётся
`zprobe-written.gz` в двадцать байт. Правки против первой редакции было две, и
обе — расхождения с языком: `opened handle = …` не разбирается (`handle` —
ключевое слово, «ожидается `=`, а не `handle`»), и обе длины массивов я
посчитал на единицу больше, забыв, что семнадцать букв плюс ноль — восемнадцать,
а не девятнадцать.
