# Волна 5 Фазы 9, трек C: зависимый ECS

Утверждение трека было одно и проверяемое: индексировать сущность множеством её
компонентов так, чтобы система по `{Position, Velocity}` не писалась для
сущности без `Velocity`, — без рантайм-проверки «есть ли компонент».

**Сходится.** И положительный свидетель, и отказ лежат в корпусе:
`eval/ecs-dependent`, `errors/ecs-missing-component`.

## Что получилось

Множество компонентов живёт в типе (`World cs`), доступ сторожит доказательство
членства `Has t cs`, доказательство **стёрто** — кратность `0`, в рантайме его
нет.

```adamas
posX : (0 cs : Tags) -> (0 p : Has Position cs) -> World cs -> UInt64 -> Float32
move : (0 cs : Tags) -> (0 a : Has Position cs) -> (0 b : Has Velocity cs)
     -> World cs -> World cs
```

Главное следствие: **ветви «компонента нет» не существует вовсе**. Ни `Option`,
ни умолчания, ни проверки. У apecs она есть по построению — множество
компонентов там не в типе, и обращение к отсутствующему даёт `Maybe`, который
автор обязан разобрать и может забыть.

Отказ приходит **на построении доказательства**, и это точнее, чем на вызове
системы: `Has Health movable` просто не населено — `Here` требует метку первой,
`There` требует найти её в хвосте, хвост кончается `None`.

## Доказательство сторожит, а не ищет, и это правило, а не выбор

Первая редакция хранила компоненты разнородным списком, индексированным
множеством, и `grab` ходил по доказательству к нужному полю. Она **работает** и
проверена прогоном — но доказательство там обязано быть `ω`: стёртое значение
разбирать нечем, и компилятор говорит это прямо, «объявлена с кратностью 0, а
использована 1».

Отсюда принятая форма: хранилище **статично** (SoA, §4.11), место компонента
известно по метке в типе функции, а доказательство отвечает на другой вопрос —
вправе ли эта функция быть здесь позвана. Так оно стирается целиком.

## Две формы записи, без которых это не собирается

Обе — ограничения сегодняшнего компилятора, и обе выведены в §10.

1. **Мономорфные обёртки над примитивами массива.** Внутри ветви разбора
   индексированного семейства `arrayIndex xs i` отвергается нерешённой дыркой,
   хотя тип `xs` написан в конструкторе. Вне такой ветви тот же вызов проходит.
2. **Индекс семейства написан стёртым полем конструктора.** Без него собранный
   заново `MkWorld` своего индекса не знает, и вывести его неоткуда — поля его
   не упоминают.

## Дефект, найденный ценой, а не поиском

Зависимый слой стоил **четырёх блоков кучи на кадр** (2407 против 7 за 600
кадров), при том что `@fbip` проходил на обеих функциях.

Сведено к 38 строкам и разложено по условиям
(`docs/measurements/erased-leak/`): течёт, когда от одного стёртого значения
зависят **и** второй стёртый аргумент, **и** нестёртый. Тогда стёртое значение
строится заново на каждом вызове.

Первая гипотеза — «зависимый стёртый аргумент сам по себе» — **не
воспроизвелась**. Проверил и отбросил вместо того, чтобы записать.

Отдельно стоит записать, **почему не заметили раньше**: стёртое поле
конструктора проверялось и выглядело бесплатным, но значением поля стоял
нульарный конструктор, строить который стоит нуля при любом поведении
компилятора. Проверка была негодной, и различает только составное значение.

## Чего это стоит демо

Не блокер. Горячий путь специализируется без параметров-доказательств — 600
кадров стоят семи блоков вместо 2407, — а зависимый API остаётся на границе.
Обход, не лечение.

## Порядок треков себя оправдал

План требовал мерить кадр **до** типового дизайна. Оправдалось дважды: замер
трека B дал шкалу, на которой четыре блока на кадр читаются как дефект, а не как
норма, — и он же дал ту форму цикла (внутренний проход по массивам, а не по
миру), без которой зависимая версия стоила бы **четырёх блоков на ячейку**, то
есть в двести пятьдесят шесть раз дороже.
