# Adamas — Design Document

> Координационный документ для разработки research-prototype языка программирования Adamas. Используется как источник истины по дизайн-решениям для всех участников проекта (человек, chat Claude, Claude Code).

**Статус:** черновик v0.4, август 2026
**Назначение документа:** фиксация дизайн-решений и их обоснований, roadmap, открытые вопросы.

## 0. Как читать этот документ

Документ организован от высокоуровневой философии к деталям реализации. Каждый раздел содержит **решения** (что выбрано) и **обоснование** (почему — какой trade-off и какая альтернатива отвергнута). Открытые вопросы вынесены отдельно — они означают, что мы ещё не определились и решение должно приниматься осознанно при появлении контекста.

Для **chat-сессий Claude** этот документ — точка входа: прочитав его, ассистент получает весь контекст по принятым дизайн-решениям. Для **Claude Code** — это источник истины для архитектурных выборов в реализации. Для **человека** — координационная карта проекта и трекинг прогресса.

При значимых изменениях добавлять запись в раздел [Decision log](#13-decision-log).

## 1. Видение и цели

**Что строим:** research-level прототип статически типизированного функционального языка программирования с предсказуемой моделью стоимости, зависимыми типами, линейностью и алгебраическими эффектами. Язык одновременно нацелен на функциональную ясность (в духе Haskell/OCaml) и на системное программирование (в духе Rust/Zig) — принципиально пытаемся не разделять эти миры, а показать, что дизайн, честный по отношению к обеим сторонам, возможен.

**Целевая аудитория языка:** программисты, которые знают Haskell/Rust/OCaml/Idris и хотят увидеть, что получится, если синтезировать их сильные стороны без исторического багажа. Это не «язык для всех» — это языковая лаборатория с продакшен-ориентированной семантикой. Целевые use cases покрывают три больших класса:

- **Прикладной функциональный код** — то, что типично пишется на Haskell/OCaml. Data pipelines, парсеры/интерпретаторы, символьная обработка, бизнес-логика с эффектами.
- **Systems programming** — hot loops, zero-allocation code paths, SIMD-workloads, embedded, network dataplane. То, где сейчас нужно уходить в Rust или Си, потому что Haskell «засоряет кучу» или «не занимайтесь ерундой, пишите на Си».
- **Type-heavy research** — dependent-типизированные библиотеки, DSL с compile-time проверками, protocol-корректный код, формальная верификация свойств программы (§3.7) на базе proof-terms в QTT.

Единая семантика для всех трёх: QTT + resource + региональная память + эффекты — не «фича для одного класса, костыль для другого», а связная система.

**Цели проекта (project goals):**
- Дотащить компилятор до состояния, в котором на нём можно написать нетривиальную программу (≥ 1000 строк, реализующую что-то осмысленное — например, интерпретатор для другого языка или решатель для задач определённого класса).
- Получить публикабельные характеристики производительности на минимальном наборе бенчмарков, включая systems-programming workloads (zero-alloc hot loops, SIMD-heavy code).
- Получить личное понимание реализации компиляторов на уровне, достаточном для предметного обсуждения дизайн-решений в индустрии и академии.

**Non-goals:**
- Не пытаемся заменить какой-либо существующий язык в продакшене.
- Не пытаемся охватить весь surface area промышленного языка (без полной стандартной библиотеки, без отлаженного package manager, без бэкендов под все архитектуры).
- Не стремимся к полной формальной верификации компилятора (хотя ключевые алгоритмы — type checker, elaborator — должны иметь mechanized proofs из литературы как ориентир).
- Alternative backends (WebAssembly, GPU offload) — не goals для research-прототипа, но дизайн заложен так, чтобы они были feasible расширениями без изменений в ядре (§4.10).

**Реалистичный временной горизонт:** 3–5 лет до состояния «работает и можно показать», с учётом, что это side project с обучающим компонентом и активным использованием AI-ассистентов.

## 2. Дизайн-философия

### 2.1 Принципы

1. **Предсказуемая модель стоимости.** Программист, глядя на код, должен понимать порядок его исполнения и аллокации без запуска профайлера. Никакой скрытой ленивости, никаких неявных аллокаций.
2. **Честный тип.** Тип функции должен отражать, что она делает: эффекты — в типе, линейность — в типе, тотальность — в типе (когда заявлена).
3. **Erasure как first-class.** Информация, используемая только для статической проверки, физически отсутствует в скомпилированном коде. Не должно быть «виртуального налога» на типобезопасность.
4. **Дисциплина важнее свободы.** Где есть выбор между гибкостью и предсказуемостью — выбираем предсказуемость. Это язык, который сложнее писать, но проще понимать.
5. **Прагматическая теория.** Берём из теории типов то, что окупается практически. Не строим Coq или Agda.
6. **Систем­ный код — first-class.** Программист не должен уходить в другой язык для zero-alloc hot loops, SIMD-обработки, direct FFI, или явного контроля над памятью. Механизмы для этого — часть языка, не костыли поверх: региональная память с pluggable-стратегиями (§3.6), SIMD-типы (§4.9), прямой C ABI (§5.3). Функциональная ясность и системный контроль — одна семантика, а не два языка в одном.

### 2.2 Что наследуется из ML/Haskell

- Pure-by-default как структурный принцип, реализованный через систему эффектов.
- Pattern matching, ADT, parametric polymorphism как базовые конструкции.
- Type classes (в трансформированном виде) — основной механизм ad-hoc полиморфизма.
- Currying, partial application.
- Significant indentation в синтаксисе.

### 2.3 Что явно отвергается

- **Лень по умолчанию** — главное архитектурное отличие от Haskell. Все доводы Саймона Пейтон Джонса о том, что если бы переделывали, делали бы strict, мы принимаем за принятые. Лень как опт-ин остаётся.
- **Monad transformer stacks** — заменяются алгебраическими эффектами.
- **Глобальная coherence типоклассов как умолчание** — заменяется scoped implicits с возможностью локальной coherence.
- **Partial функции в Prelude** (`head`, `fromJust`, etc.).
- **Множество несовместимых String-типов** — единственный UTF-8 представитель плюс views.
- **Records-as-functions** — записи становятся first-class с row polymorphism.

## 3. Семантическое ядро

### 3.1 Стратегия вычисления: call-by-value

**Решение:** строгий вызов по умолчанию. Тип `Lazy a` (или эквивалент) для мемоизированных отложенных вычислений, конструируется явно.

**Обоснование:** убирает класс багов с space leaks, делает порядок вычислений предсказуемым, упрощает интероп с C ABI, позволяет агрессивный inlining без потери семантики. Цена — некоторые элегантные ленивые программы (бесконечные потоки) требуют явных конструкций.

**Альтернатива (call-by-need):** отвергнута. Доминирующий класс багов в Haskell связан именно с непредвиденной ленью.

### 3.2 Типовая система: Quantitative Type Theory

**Решение:** ядро основано на QTT (Atkey 2018, реализован в Idris 2). Три кратности: `0` (erased), `1` (linear), `ω` (unrestricted).

**Базовые конструкции ядра:**
- Зависимая функция `(q x : A) -> B` где `q ∈ {0, 1, ω}`.
- Зависимая пара `(q x : A) ** B`.
- Универсумы `Type : Type 1 : Type 2 : ...` (predicative hierarchy).
- Индуктивные типы (data declarations) с автоматически выведенными квантификациями.

**Что это даёт:**
- Зависимые типы без runtime cost: `0`-кратные аргументы стираются.
- Линейные типы как частный случай: `1`-кратность.
- Обычные функции — `ω`-кратность по умолчанию.

**Universe polymorphism:** уровни параметризуют типы неявно, в духе Agda и Idris 2 — элаборатор их выводит, в пользовательском коде они появляются только при явной аннотации. Уровни — отдельный сорт `Level` с операциями `zero`, `suc`, `max`, имеют 0-кратность (стираются, не появляются в рантайме).

**Правило формирования `Pi` — `max`, не `imax`.** Если `A : Type u` и `B : Type v`, то `(q x : A) -> B : Type (max u v)`. Это и есть предикативность, выраженная арифметикой: тип функции никогда не опускается ниже уровня своего домена. Правило Lean `imax u v` (равное `0` при `v = 0`) отличается ровно в одном случае, и этот случай есть определение импредикативности нижнего универсума: с ним `(x : Type 0) -> Bool` попадает в `Type 0`, квантифицируя по коллекции, элементом которой сам является. У Lean это безопасно, потому что `Sort 0` — это `Prop` с иррелевантностью доказательств и урезанной элиминацией; здесь такого сорта нет и не планируется (см. отказ от двухсортной схемы ниже), поэтому `imax` в языке уровней отсутствует.

**Следствие для surface-конструкций:** структуры данных могут содержать типы как значения. Например, `List Type` — валидный тип уровня `Type 1`, полезный для индексирования GADT-подобных структур типизированным окружением (`Expr : List Type -> Type -> Type`, см. §4.1). Уровни автоматически поднимаются в implicit-параметры, пользователь не пишет их явно.

**Почему предикативная, а не импредикативная.** Импредикативный `Type` даёт парадокс Жирара/Хюркенса и тем самым возможность доказать `False`, что разрушает принцип «честный тип» (§2.1). Двухсортная система Coq (`Prop` импредикативен, `Type` предикативен) решает часть задач, но плохо сочетается с эффектами и линейностью — для прототипа сложность не окупается. Практическая потребность «библиотечного кода» (`Functor`, `Monad` через UP пишутся один раз, полиморфно по уровню) закрывается universe polymorphism без потери консистентности.

**Открытые подвопросы (см. §10):** кумулятивность; точная структура уровневых выражений; общая иерархия для `Type` и `Effect` vs раздельные миры.

### 3.3 Линейность и erasure

**Решение:** линейность встроена через QTT, как описано выше. Erasure не «оптимизация» — это часть семантики ядра.

**Практические следствия:**
- Линейный handle файла, mutable массив без MVar/IORef (механизм — `unique data` ниже для неалиасованных значений, `Heap r` §3.6 для алиасованных), безопасный in-place update структур данных.
- Доказательства корректности (например, что сортированный список действительно сортирован) не имеют рантайм-стоимости.
- Эквивалент `unsafePerformIO` не нужен для большинства задач «нужна мутация для производительности».

**Кратность `1` — affine, не strict linear.** Кратность `1` означает «использовано не более одного раза», то есть допустимо не использовать вовсе. Это критично для эффектных handler'ов: continuation `resume` в ветке handler'а может быть проигнорирована (например, в handler'е `Fail` continuation просто не вызывается — вычисление обрывается), при этом остаётся статическая гарантия отсутствия повторного вызова.

**Ресурсные типы: strict linear с автоматическим cleanup.** Для случаев, где требуется «ровно одно использование» на всех путях выполнения (file handle обязательно должен быть закрыт, транзакция обязательно commit/rollback, mutex обязательно unlock), вводится концепция **resource type** — тип, объявленный ключевым словом `resource` вместо `data`, с обязательным деструктором:

```adamas
resource File where
  drop h = closeFile h
```

Компилятор гарантирует:

- Биндинг переменной resource-типа автоматически получает кратность `1` (программист не пишет `let 1 h = …`).
- Деструктор `drop` вызывается автоматически при выходе из scope переменной — на нормальном пути, при выбросе исключения через `Except`, при обрыве вычисления через любой другой эффект, не вызывающий continuation.
- Порядок cleanup при вложенных scope — LIFO.

Это делает ресурсное управление предсказуемым без ручных `bracket`/`try/finally`. Модель ближе к Rust `Drop` и C++ RAII, чем к Haskell'овским `bracket`-паттернам. Явная маркировка через `resource` (а не через обычный `data`) сохраняет принцип §2.1 «честный тип»: программист видит по декларации, что тип управляет ресурсом с автоматическим cleanup.

Не всё, полученное через `IO`, — resource. `Int`, прочитанный из файла, — обычное значение. `resource` предназначен для сущностей, действительно требующих детерминированного закрытия.

**Замыкания над линейными значениями.** Бо́льшую часть случаев QTT закрывает сам, без отдельного механизма. Кратности живут на связывании, а проверка использований работает масштабированием, поэтому лямбда, захватившая линейное значение, учитывается автоматически — она использует захваченное столько раз, сколько применяется сама:

```adamas
let 1 h = openFile path
let ω f = \() -> closeFile h    -- ошибка здесь же: ω-связывание масштабирует
                                -- захваченную h до ω при объявленной 1
```

Ошибка возникает на самом связывании и от числа последующих вызовов `f` не зависит — их может не быть вовсе. Масштабирование применяется к правой части `let`, а не к местам использования.

В позиции аргумента то же масштабирование даёт нужный результат без единой дополнительной аннотации:

```adamas
spawn : (1 body : {Async, eff} a) -> {Nursery, Async} (Task eff a)

spawn (processConnection conn)   -- conn : resource, захвачен замыканием
```

Параметр объявлен с кратностью `1`, масштабирование на единицу оставляет `conn` в единице — проходит. Была бы у `body` кратность `ω`, `conn` уехал бы в `ω` и был бы отвергнут. То есть «сколько раз применяется замыкание» уже записано — в кратности параметра принимающей функции, а не в типе замыкания.

**Две позиции, где информации не хватает,** — возврат из функции и поле конструктора. У обеих нет кратности, которая масштабировала бы контекст:

```adamas
mkCloser : (1 h : File) -> (() -> {IO} ())
mkCloser h = \() -> closeFile h   -- тело корректно: h используется однократно

let ω f = mkCloser h
f ()
f ()                              -- двойное закрытие, ничем не ловится
```

Тип результата — обычная стрелка, одноразовость применения в ней не записана, а контекст, в котором она была известна, закончился внутри `mkCloser`.

**Правило: замыкание над линейным значением — scope-bound.** Лямбда, захватившая связывание кратности `1` (в том числе resource-типа), может применяться и передаваться аргументом, но не может появиться в позиции возврата функции и в поле конструктора. Параметр кратности `1` функционального типа наследует то же ограничение внутри вызываемой функции.

**Свойство «scope-bound» распространяется через локальные связывания**, а не проверяется синтаксически на лямбда-литерале. Иначе правило обходилось бы в одну строку:

```adamas
mkCloser h = let 1 g = \() -> closeFile h in g   -- возвращается g, не лямбда
```

Связывание, инициализированное scope-bound значением, само становится scope-bound; то же для полей записей и элементов кортежей, собранных из таких значений. Проверка при этом остаётся локальной для тела каждой функции: межпроцедурного анализа нет, потому что через границу функции такое значение по правилу и не проходит.

**Исключение: поле resource-типа.** Захваченное значение может пережить свой scope внутри сущности, у которой есть деструктор:

```adamas
resource Task (eff : Effect) (a : Type) where
  drop t = cancelAndCleanup t
```

`spawn` кладёт тело в `Task`, и это разрешено, потому что ответственность за захваченное переходит к `drop` этого `Task`. Ровно то, что §5.2 уже описывает словами «untask'нутый Task при drop Scope — cancelled».

Отсюда формулировка принципа: **захваченный ресурс покидает свой scope только внутри чего-то, у чего есть деструктор.** У обычного замыкания деструктора нет, поэтому оно и не выпускается. Нужно владение за пределами scope — оборачивай в `resource` и напиши `drop`; это перестаёт быть обходом правила и становится явным переносом владения, видимым в типе.

**Следствие: деструкторов у замыканий не существует.** Вопрос «что будет, если такое замыкание уничтожат, ни разу не вызвав» снимается по построению: замыкание не может пережить scope захваченного ресурса, поэтому ресурс в любом случае закроется своим собственным scope-exit — на нормальном пути, при исключении, при обрыве continuation через любой handler, не вызывающий `resume`. Отдельного понятия «замыкание-ресурс» в языке нет, порядок дропов внутри захваченного окружения описывать не требуется.

**Что попадает под запрет из реального кода.** Фабрики замыканий, владеющих ресурсом:

```adamas
mkLogger : (1 h : File) -> (String -> {IO} ())   -- отвергается
```

Отвергается заслуженно: функция возвращает замыкание, владеющее файлом, и ответа на вопрос «кто и когда его закроет» в её типе нет. §3.3 строит владение на scope-based RAII, и замыкание, пережившее scope ресурса, противоречит этой модели по существу. Каноническая форма того же кода — аргументная позиция, `withFile path (\h -> …)`, либо явная resource-обёртка с `drop`, если владение действительно должно пережить scope.

**Диагностика** указывает на захваченное связывание, а не на лямбду: «замыкание захватывает `h : File` кратности 1 и не может быть возвращено; передайте его аргументом (`withFile`) либо оберните владение в resource-тип с деструктором».

**Уникальность: `unique data`.** Кратность `1` ограничивает потребление, а не производство: ω-связывание можно передать в `1`-параметр (ω·1 = ω, бюджет бесконечен), поэтому `1` на параметре не гарантирует отсутствия других ссылок на значение. Мутабельность требует именно уникальности. Она вводится маркером на декларации типа, а не атрибутом в типе:

```adamas
unique data Array (0 n : Nat) (a : Type) where ...

newArray : Nat -> a -> Array a
freeze   : (1 arr : Array a) -> Vect n a
```

Правило элаборации: **любое связывание unique-типа получает кратность `1`**, если явно не объявлено `0` (стёртые упоминания в доказательствах законны); явное `ω` — ошибка на самом связывании. ω-значений такого типа не существует, поэтому дыра ω→1 закрыта не проверкой, а отсутствием её предмета. Дальше работает обычное масштабирование QTT: `dup arr` при `dup : (ω x : a) -> (a, a)` отвергается, потому что ω-параметр скалирует использование до ω при объявленной `1`. Констрейнт вида `Shareable` и отдельный сорт для unique-типов не нужны: полиморфная инстанциация `a := Array Int` безвредна сама по себе, вредно только попадание значения в ω-позицию, а это уже ловится.

Утечка через поле конструктора закрывается дефолтом кратности полей (§4.1): конструктор использует аргумент ровно однажды, поэтому поля имеют кратность `1`, и `let ω p = (arr, v)` отвергается на самом связывании — отдельного правила «тип с unique-полем сам обязан быть unique» не требуется.

**Позиция возврата — не дыра**, в отличие от замыканий. У замыкания линейность не записана в типе стрелки, что и потребовало правила scope-bound; у unique-типа она записана в типе, поэтому вызывающая сторона свяжет результат при `1` автоматически. Следствие: CPS-обёртка в духе Linear Haskell (`withArray : … -> ((1 arr : Array a) -> {e} b) -> {e} b`) не требуется, достаточно `newArray` — свежее значение алиасов не имеет по построению, дальше уникальность держит дисциплина связывания.

**`resource` — частный случай.** `resource T where drop = …` эквивалентен `unique data T` плюс вставка `drop` в exit-points. Оба surface-keyword'а сохраняются (`resource` описателен и говорит о детерминированном закрытии), но элаборируются одним правилом; третьего механизма рядом с линейностью и регионами не заводится. Свойство «affine, не strict linear» наследуется: unique-значение можно не использовать, память освобождается статически.

**Переход в иммутабельное — функция, не сабтайпинг.** `freeze` потребляет unique-связывание и отдаёт обычное ω-значение под управлением Perceus; смерть исходного связывания обеспечена кратностью `1` в сигнатуре, отдельного правила элаборации не нужно. Реализуется как **интринсик**: тело на Adamas невыразимо, потому что требует смены дисциплины владения над тем же представлением, lowering эмитит переход. Это слабее, чем конструкция языка, и слабее, чем unsafe-примитив в prelude, — §3.3 сохраняет позицию «эквивалент `unsafePerformIO` не нужен». Обратный `thaw : Vect n a -> Array a` копирует, либо выполняется in-place при RC = 1, то есть является вопросом FBIP на уровне API.

Ожидание к рантайму (§5.1): unique-объекты аллоцируются с зарезервированным местом под RC-заголовок, не трогаемым, пока значение уникально; `freeze` записывает туда `1`. Цена — слово на объект там, где RC не используется; альтернатива без заголовка превращает `freeze` в копирование и обесценивает механизм. `freeze` shallow по построению: вложенные unique-значения (`Array (Array Int)`) отвергаются кратностью полей, поэтому глубокая версия не нужна.

**Граница ответственности.** `unique data` отвечает за **неалиасованные** значения: буферы, хендлы, значения, передаваемые по владению, границу с Perceus, cross-thread transfer без RC promotion. **Алиасованная** мутация — не его задача и через него не выражается: она живёт в §3.6 как эффект `Heap r`. Ось разделения — не mutable/immutable, а aliased/unaliased: неалиасованная мутация семантически невидима и эффекта не требует, алиасованная наблюдаема и обязана быть эффектом.

**Отношение к семантическому ядру.** `unique`, `resource` и правило scope-bound замыканий — surface-конструкции, а не расширение ядра QTT. При elaboration `resource File where drop h = …` превращается в: (1) обычный data-тип `File`; (2) правило элаборации, автоматически присваивающее биндингам с типом `File` кратность `1`; (3) вставку вызова `drop` в exit-points scope при lowering в core. `unique data` — те же (1) и (2) без (3). Правило scope-bound замыканий — проверка на элаборированном терме, не меняющая ни типов, ни суждений. Второй аннотации на стрелке (`A ->{1} B` в духе Linear Haskell) не вводится. Семантическое ядро остаётся чистым QTT в формулировке Atkey — никаких новых кратностей, никаких новых форм суждений.

Отвергнутая альтернатива — **атрибуты уникальности в духе Clean** с coercion unique → shared. Даёт полиморфизм по уникальности и снимает нужду в `freeze`, но: заводит первую в языке решётку подтипов вопреки позиции §3.4 и §4.2 («настоящего сабтайпинга нет, эргономика через row polymorphism»); помещает атрибуты в язык термов и тем лишает нормальную форму статуса полного инварианта — ровно то свойство, ради которого из §3.2 удалялся `imax` и на котором держится content addressing (§7.3). Комбинация QTT + uniqueness + dependent types на момент решения не реализована никем (Granule — без полноценных зависимых типов, Idris 2 — без uniqueness, Clean — без QTT) и могла бы быть исследовательским вкладом; цена признана перевешивающей.

Это важно для §9 Фазы 2 (реализация QTT в ядре): `unique` и `resource` реализуются как surface-фичи поверх уже готового ядра, а не требуют его модификации.

### 3.4 Эффекты: algebraic handlers с evidence translation

**Решение:** эффекты — row-polymorphic, обрабатываются handler'ами, компилируются по схеме evidence translation (Leijen 2017, Xie et al. 2020).

**Тип функции с эффектами:** `f : A -> {e1, e2 | r} B` где `e1, e2` — эффекты, `r` — row variable для дополнительных эффектов.

**Базовые эффекты библиотеки:**
- `IO` — внешний мир (выделен синтаксически, но не магически).
- `State s`, `Reader r`, `Except e`, `Writer w` — классика.
- `Async`, `Channel` — для concurrency.
- `Random`, `Time`, `FS` — гранулированный IO.

**Single-shot и multi-shot handler'ы через разные keyword'ы:**

- `handle expr with …` — single-shot continuation. `resume` в теле каждой ветки имеет кратность `1` (§3.3, affine). Вызывается не более одного раза.
- `handleMulti expr with …` — multi-shot continuation. `resume` имеет кратность `ω`. Может вызываться многократно, обязателен для backtracking-паттернов (parser combinators, non-determinism, поиск с возвратом).

Компилятор автоматически выбирает кратность `resume` по keyword'у — программист не аннотирует. Различие видно на месте использования: `handleMulti` в grep'е сразу указывает, где применяется multi-shot и связанная с ним стоимость.

**Стоимость multi-shot.** Каждый вызов continuation в `handleMulti` требует копирования segment'а стека (см. «Стратегия компиляции» ниже). O(stack depth) на resume. `handleMulti` — не бесплатный default, а осознанный опт-ин.

**Ограничения multi-shot.** Resource-типы (§3.3) не допускаются в scope `handleMulti`-выражения — семантика cleanup несовместима с многократным вызовом continuation (при втором вызове ресурс был бы либо уже cleanup'нут, либо требовал бы клонирования, что противоречит его линейной природе). Компилятор проверяет статически; ошибка — «resource `X` cannot appear in scope of handleMulti; consider extracting to single-shot section».

**Continuations и QTT.** Различие single-shot vs multi-shot реализуется не отдельным механизмом, а через линейность: `resume` в `handle` имеет кратность `1`, в `handleMulti` — `ω`. QTT «покрывает» задачу, которая в других языках требует отдельной аннотации.

**Стратегия компиляции:**
- Tail-resumptive handlers (включая state) → inline без overhead.
- General handlers (single-shot) → evidence vector + indirect call.
- Multi-shot → segmented stack copy на каждый resume.

**Альтернатива (MTL):** отвергнута. Композиция эффектов через монад-трансформеры не масштабируется (O(n²) instances), компиляторы плохо специализируются через layers, error messages нечитаемы.

**Эффекты как канонический механизм для монадических паттернов.** Failure (`Option`/`Maybe`), non-determinism (`List`-как-монада), окружение (`Reader`), состояние (`State`), исключения (`Either`/`Result`) — исторически моделируются монадами. В Adamas канонический способ — эффекты. `Option`/`Result` остаются как data-типы для хранения значений (в возвращаемых типах, полях структур), но код, порождающий их через цепочки вычислений, пишется в эффектной форме: эффект `Fail`/`Except` + handler `runFail : ({Fail | e} a) -> {e} (Option a)`.

`Monad` как класс существует в prelude для интеропа и для случаев, где нужен action на самой структуре (например, `List` как non-determinism monad для генеративных задач). Do-нотация отсутствует — типичные case покрываются let-цепочками в эффектном коде (§4.1). Для явной монадической цепочки — `bind` или оператор `>>=`.

Это следствие §2.3 «отвергается: monad transformer stacks» — эффекты не «ещё одна монада», а замена монадической эргономики для большинства задач.

**Взаимодействие с ресурсным управлением.** Эффекты, обрывающие continuation (`Except`, ранняя терминация, любой handler, не вызывающий `resume`), триггерят автоматический cleanup для resource-переменных в scope перед перебросом или обрывом. Это связка §3.3 (ресурсные типы) с эффектной системой: программист не должен помнить о `bracket` при работе с файлами внутри эффектного кода. Порядок cleanup — LIFO, симметрично scope-based RAII.

**Subtyping эффектных row: нет; эргономика через auto-lift row-переменных.** Настоящего sub-typing на effect row нет — правил вида `{IO} <: {IO, State s}` система типов не содержит. Эргономика достигается универсальным правилом: **в позициях сигнатуры функции row-переменная авто-поднимается**, как и обычные типовые переменные. `log : String -> {IO} ()` элаборируется в `log : String -> {IO | e} ()` со свежей `e`, которая при вызове инстанцируется любым (в том числе пустым) row. Результат: функция валидна и в pure-контексте, и в контексте с любым дополнительным набором эффектов.

Правило применяется симметрично к записям (§4.2). Единый механизм для двух форм row polymorphism.

Позиции, где row **закрытая** (без auto-lift):
- В declaration типа: `type M = {IO} a` — фиксированный тип с ровно этим набором эффектов.
- Внутри explicit row-выражений с явной переменной: `f : {State s | e} a` — программист сам управляет полиморфизмом.

Позиции, где row **открытая** (auto-lift):
- Все позиции сигнатуры функции: аргументы, return type. Включая позиции **без явных `{}`** — `sum : List Int -> Int` элаборируется в `List Int -> {e} Int` с той же общей `e`, что и в других row-позициях сигнатуры (если они есть). Тело функции проверяется отдельно: если оно pure, `e` может быть инстанцирована пустой row. Аналогия с HM: типовая переменная всегда получает свежее имя, реальные ограничения приходят из тела и контекста использования.

**Ключевая деталь:** одна свежая row-переменная генерируется **на всю сигнатуру**, а не по одной на каждую позицию. Это критично для higher-order функций: `withFile : String -> (File -> {IO} a) -> {IO, Except IOError} a` элаборируется в `String -> (File -> {IO | e} a) -> {IO, Except IOError | e} a` с общей `e` — эффекты callback'а пробрасываются в return type. Разные переменные разорвали бы связь и сделали HOF-типы неспоcобными к композиции. Аналогично Koka.

Явная закрытая row в сигнатуре функции — потенциальный open question (см. §10), если появятся случаи, где программисту нужно явно запретить дополнительные эффекты. Стартово таких случаев не выделено, механизм не вводим.

### 3.5 Модули и implicits

**Решение:** единая система, в которой ML-style модули с функторами и type classes — две точки на одной шкале. Ядро содержит одну конструкцию (module = именованный набор типов и значений с необязательной сигнатурой), surface даёт разные keyword'ы для разных use case.

**Уровни на surface:**

- **Module type:** сигнатура — интерфейс модуля.
  ```adamas
  module type Ord where
    type T
    compare : T -> T -> Ordering
  ```

- **Explicit modules:** именованные структуры с типами и значениями, first-class (передаются как обычные значения, в духе 1ML / Scala 3 objects). Могут иметь опциональную аннотацию сигнатурой.
  ```adamas
  module IntOrd : Ord where
    type T = Int
    compare a b = intCompare a b
  ```

- **Module functors:** модули, параметризованные другими модулями. Синтаксис применения — function-call style.
  ```adamas
  module OrderedMap (Key : Ord) where
    data Map v = ...
    insert : Key.T -> v -> Map v -> Map v

  module IntMap = OrderedMap IntOrd
  ```
  Signature refinement через `with type`:
  ```adamas
  module IntMap = OrderedMap IntOrd with type Key.T = Int
  ```

- **Type classes = module types + implicit-режим.** Class-декларация объявляет module type и одновременно активирует его для implicit-разрешения:
  ```adamas
  class Ord a where
    compare : a -> a -> Ordering
  -- элаборируется в:
  --   module type Ord where
  --     type T = a
  --     compare : T -> T -> Ordering
  --   плюс регистрация Ord как implicit-разрешаемого
  ```
  Class-инстанс — обычный module value, canonical для implicit-резолвинга в текущем scope.

- **Implicit module parameters:** параметр module functor'а может быть помечен как implicit (`{Key : Ord}`), тогда апплицируется без явного аргумента через тот же механизм резолвинга, что и class-инстансы. По умолчанию параметры functor'а — explicit; implicit — опт-ин.

**Применение через function-call syntax.** Апплицирование functor'а к аргументу выглядит как обычный вызов: `OrderedMap IntOrd`. Симметрично тому, что модули — first-class values. Никаких специальных ключевых слов для functor application.

**Coherence:** scoped by default. Глобальная coherence (как в Haskell) опционально через `coherent` маркер у определения класса. Это позволяет orphan instances без потери надёжности там, где она действительно нужна.

**Class vs explicit module functor — когда какая форма.** Обе изоморфны формально, но эргономически различны:

- **Class:** параметр — «естественный» для типа (один инстанс типичен), функции мыслятся как «функции над типом с constraint'ом», implicit-разрешение экономит писанину.
- **Module functor:** несколько «правильных» вариантов параметра для одного типа (например, `Set` строк с case-sensitive vs case-insensitive сравнением), результат мыслится как «отдельная структура данных со своими типами», важна независимость от глобальных инстансов и невозможность случайно смешать несовместимые instances.

Классический OCaml-пример: `Set.Make(String)` и `Set.Make(CaseInsensitiveString)` — два разных Set, случайное смешивание — статическая ошибка. Через class это требует newtype-обёрток или именованных инстансов с явным `using`.

**Явные module-параметры и implicit class-разрешение не пересекаются.** Если `insert : Key.T -> v -> Map v -> Map v` в module functor'е и в scope есть class-инстанс `Ord Int`, это никак не помогает: functor всё равно требует `Key` явно. Программист выбирает механизм по вкусу к явности.

**Альтернатива (классический Haskell type classes):** отвергнута из-за orphan problem и нерасширяемости.

**Альтернатива (чистый ML):** отвергнута из-за многословности в типичных вызовах.

**Отношение к записям (§4.2).** В ядре модули и записи имеют одинаковую структуру — набор именованных значений с типами — и реализуются одной конструкцией. Но на surface разделены: `type Foo = { ... }` для чистой data-записи без инкапсуляции, `module Foo where ...` для модуля с приватностью, экспортом и зависимостями. Причина разделения — ясность: механизмы видимости, естественные для модулей, мешали бы записям как данным, и обратно.

### 3.6 Региональная память

**Решение:** Perceus (§5.1) — основная стратегия управления памятью. Для systems-programming use cases, где нужны zero-alloc hot loops, изолированные аллокации, специфический alignment или явный контроль над стратегией размещения, вводится **регионы** — pluggable-механизм альтернативных аллокаторов, интегрированный через resource-типы (§3.3) и эффектную систему (§3.4).

**Модель.** Регион — resource с pluggable-стратегией:

```adamas
module type AllocStrategy where
  type Handle          -- runtime-представление региона
  new        : {IO} Handle
  alloc      : Handle -> (n : Nat) -> {IO} Ptr
  deallocate : Handle -> {IO} ()

resource Region (s : AllocStrategy) where
  drop r = s.deallocate r.handle
```

Аллокация в конкретном регионе идёт через эффект `Alloc region`, который резолвится соответствующей стратегией:

```adamas
effect Alloc (r : Region s) where
  allocIn : a -> {Alloc r} (Ref r a)
  read    : Ref r a -> {Alloc r} a
  write   : Ref r a -> a -> {Alloc r} ()

-- Ref r a — ссылка, привязанная к региону r
-- Тип Ref не может пережить свой Region (проверяется через эффект Alloc,
-- снимающийся ровно в withRegion — механика та же, что для Nursery в §5.2)
```

**`Alloc r` — канонический механизм алиасованной мутабельности.** Аллокация, чтение и запись — операции одного эффекта, потому что все три требуют одного и того же: живого региона. Разделять их на `Alloc` и отдельный `Heap` смысла нет — capability одна.

Ключевое свойство — **параметризация по идентичности региона, а не по типу данных**. Один эффект `{Alloc r}` покрывает произвольное число мутабельных объектов внутри региона, каждый из которых назван first-class значением `Ref r a`:

```adamas
mergeSort : {Ord a} => Ref r (Array a) -> Ref r (Array a) -> {Alloc r} ()
```

Эффект в row один при любом числе буферов. Альтернатива с параметризацией по типу элемента (`{Mut a, Mut b}`) этим свойством не обладает: два объекта одного типа дают дубликат метки, требующий `mask` на каждой операции, а число handler'ов перестаёт соответствовать числу эффектов. Отсюда позиция: **отдельного эффекта мутабельности, параметризованного типом, в языке нет**; мутабельность с алиасингом всегда идёт через регион.

Это делает `withRegion` прямым аналогом `runST`: `Ref r` соответствует `STRef s`, параметр региона `r` — параметру `s`, handler гасит эффект, поэтому функция с внутренней in-place мутацией остаётся чистой снаружи.

```adamas
sort : {Ord a} => Vect n a -> Vect n a
sort xs = withArena (
  let buf = allocIn (thaw xs)
  let _   = qsort buf 0 (length xs - 1)
  freeze (read buf))
-- снаружи pure: эффект Alloc погашен withArena
```

`Ref r a` — обычное ω-значение, копируется свободно, поэтому протаскивание через рекурсивные вызовы не потребляет и не требует переименований: боль линейного токена (Idris 2, Linear Haskell) здесь не возникает.

**Индексация — `Int` с рантайм-проверкой границ.** `Fin n` как тип индекса требует доказательства в границах на каждом арифметическом шаге (`i + 1`, `p - 1`), а корректность типичного алгоритма разбиения — нетривиальная теорема. Стандартные операции берут `Int`; `Fin`-варианты доступны как опциональный слой для кода, где доказательства уже есть. Позиция общая: зависимые типы в hot-path системном коде — инструмент, а не обязательство.

**Тотальность.** Канонический системный код в регионах, как правило, не `@total`: терминация идёт по убыванию арифметической меры, а не структурно, и её обоснование требует постусловий. По §4.7 тотальность опциональна, поэтому это законно и ожидаемо.

**Базовые стратегии в стандартной библиотеке:**

- **Arena** — bump allocator, освобождение всей области целиком при drop региона. Идеален для phase-based workloads (парсеры, интерпретаторы, request handlers).
- **Pool** — pool с фиксированными chunk'ами одинакового размера, alloc/free amortized O(1). Для рабочих нагрузок с однородными объектами.
- **StackAlloc** — размещение на C-стеке (alloca), для очень коротких hot loops с гарантированной кратковременностью.

Дополнительные стратегии — **пользовательские**. `AllocStrategy` — обычный module type; пользователь может реализовать свою стратегию (slab allocator, GC-regione, NUMA-aware allocator, что угодно) и использовать через тот же `withRegion`-паттерн. Стандартная библиотека предоставляет минимальный набор; расширение — обычный библиотечный код, без специальных compiler-hooks.

**Thread-safe стратегии как отдельный уровень.** Обычные стратегии не thread-safe: конкурентные alloc из разных потоков ведут к data race на bump pointer'е / pool metadata. Для случаев, когда регион нужно разделять между потоками (shared mempool в network dataplane, worker-shared caches, and т.п.), вводится отдельный module type:

```adamas
module type SharedAllocStrategy when AllocStrategy where
  -- Дополнительные гарантии:
  -- (1) Все методы AllocStrategy — thread-safe (lock-free или lock-based).
  -- (2) Реализация handles concurrent drop корректно
  --     (например, hazard pointers или epoch-based reclamation).
```

Стандартные thread-safe стратегии:

- **SharedArena** — bump-allocator с atomic CAS на bump pointer'е. Быстрее lock-based, но alloc contention может стать bottleneck. Приемлем для медленных path'ов; для hot loops с шириной alloc — предпочтителен SharedPool с per-thread caches.
- **SharedPool** — pool с per-thread caches и global-fallback (в духе jemalloc/tcmalloc arenas). Amortized lock-free для типичных allocations.

**Разделение эффектов для thread-safety.** Аллокация в shared region идёт через отдельный эффект:

```adamas
effect SharedAlloc (r : Region s) when AllocStrategy s where
  allocInShared : a -> {SharedAlloc r} (Ref r a)

-- SharedAlloc — capability, переносимая через spawn boundary (см. §5.2).
-- Обычный Alloc — не переносится: попытка использовать Ref r a внутри 
-- spawned task при local Alloc — статическая ошибка «Alloc r not available
-- in spawned task; use SharedAlloc for cross-thread sharing».
```

Компилятор различает two capabilities статически: `Alloc r` — thread-local, `SharedAlloc r` — thread-portable. Программист выбирает уровень при создании региона (`withArena` для local, `withSharedArena` для shared).

**Пример использования (shared mempool сценарий):**

```adamas
withSharedArena : ({SharedAlloc r, IO} a) -> {IO} a
withSharedArena k = ... -- как withArena, но со SharedArena стратегией

-- Multi-worker packet processor с shared mempool
runWorkers : Int -> {IO} ()
runWorkers numWorkers = 
  withSharedArena (
    withNursery (
      for coreId in [0..numWorkers]:
        spawn (workerLoop coreId)
      awaitAll))
  -- SharedAlloc r переносится в spawned tasks, workers могут аллоцировать
  -- в общий регион; drop региона на выходе выполняет thread-safe cleanup
```

**Пример non-shared (типичный случай):**

```adamas
withArena : ({Alloc r, IO} a) -> {IO} a
withArena k =
  let r : Region Arena = Arena.new
  handle k with
    allocIn v resume => resume (Arena.allocIn r v)
  -- r.drop — освобождает всю арену за одну операцию

-- Пользовательский код: hot loop, парсящий запросы в арену
handleRequest : Request -> {IO} Response
handleRequest req = withArena (
  let parsed : Ref r ParsedRequest = allocIn (parse req)
  let result = process parsed
  serialize result
  -- вся временная память освобождается drop'ом арены
)
```

**Взаимодействие с Perceus.** Значения по умолчанию управляются Perceus. Значения в регионе (типа `Ref region a`) — вне Perceus, их время жизни определяется регионом. Компилятор различает по типу: `Ref r a` — регионное, `a` — Perceus-управляемое. Смешение статически безопасно: `Ref r a` не может утечь наружу scope региона (нет `Alloc r`/`SharedAlloc r`-эффекта во внешнем контексте).

**Взаимодействие с линейностью и resource (§3.3).** Регион сам — resource. `Ref r a` — обычная copyable ссылка внутри scope региона. Линейные значения могут быть перемещены в регион и обратно, но это требует явного управления (allocIn + read-out).

**Взаимодействие с §5.1 (RC promotion).** `Ref r a` не участвует в RC (он вне Perceus), поэтому cross-thread transfer `Ref` не требует promotion — упрощает hot path через spawn boundary. Единственный RC-actor — сам regional объект, но его thread-safety гарантирована выбранной SharedAllocStrategy.

**Отношение к семантическому ядру.** Как и `resource`, регионы — surface-конструкция. Элаборируются через resource + эффекты + primitive allocator-функции, привязанные к runtime backend'у. Ядро QTT не расширяется. Различие Alloc / SharedAlloc — маркер на эффекте, распознаваемый §5.2 при spawn.

**Открытые вопросы (см. §10):** портируемость регионов между backend'ами (Arena через malloc vs через mmap vs через специфический OS mechanism); конкретные implementation strategies для thread-safe allocators (lock-free CAS bump, per-thread caches, hazard pointers или epoch-based reclamation для safe drop); специфика user-defined стратегий и их composability; правила приведения local Region к shared при необходимости migration.

### 3.7 Верификация свойств программы

**Решение:** формальная верификация свойств как first-class, но опциональная feature — доступна на базе уже имеющихся механизмов ядра (QTT + dependent types + total functions), без дополнительной инфраструктуры в стартовой конфигурации. Стратегия эволюционная, в два уровня.

**Уровень 1 (стартово, Фаза 0+): proof-terms native.**

Свойства выражаются как типы, доказательства — как программы кратности 0 (стираются в runtime). Это прямое следствие §3.2 (QTT) и §4.7 (тотальность): тип может кодировать propositional statement, тотальная функция того типа — доказательство.

Базовые механизмы в prelude:

```adamas
-- Пропозициональное равенство
data (≡) : {a : Type} -> a -> a -> Type where
  Refl : {x : a} -> x ≡ x

-- Decidable propositions
data Void where  -- пустой тип, представляет ложь

data Dec (P : Type) where
  Yes : P -> Dec P
  No  : (P -> Void) -> Dec P

-- Propositional truncation (для proof-irrelevance случаев)
data Trunc (P : Type) where
  MkTrunc : P -> Trunc P
-- + правило: любые два значения Trunc P дефиниционально равны

-- Пример: доказательство свойства
plusZero : (n : Nat) -> n + Zero ≡ n
plusZero Zero     = Refl
plusZero (Succ k) = cong Succ (plusZero k)

-- Использование в типе структуры (invariant)
data SortedList (0 lower : Nat) where
  SNil  : SortedList lower
  SCons : (x : Nat) -> (0 _ : lower ≤ x) -> SortedList x -> SortedList lower
-- SortedList lower — список, элементы которого не меньше lower
```

Ключевые свойства уровня 1:

- **Никаких внешних зависимостей.** Всё в самом языке; никакого SMT-solver'а, никаких `Z3` в build chain.
- **Предсказуемо.** Либо доказательство компилируется, либо нет — никаких таймаутов.
- **Zero-cost.** Кратность 0 означает, что proof-terms полностью стираются; runtime performance не страдает.
- **Уже поддерживается.** Не требует изменений в ядре — только prelude expansion и accompanying стандартная библиотека.

Ограничения уровня 1:

- Arithmetic proofs руками — трудоёмко даже для тривиальных properties (commutativity, associativity).
- Большое количество boilerplate при работе с induction, rewriting.
- Требует обучения — идиома «сначала докажи, потом кодируй» не всем комфортна.

**Уровень 2 (долгосрочно, Фаза 7+): SMT-backed refinements.**

Атрибуты в стиле Design-by-Contract с автоматической проверкой через SMT-solver (обычно Z3):

```adamas
@requires (x >= 0)
@ensures (result >= x)
increment : Int -> Int
increment x = x + 1
-- VC generator собирает предикаты, шлёт в SMT
```

Плюсы уровня 2:
- Автоматика для арифметики, bounds checking, no-overflow.
- Постепенное добавление к существующему коду (`@ensures` можно добавлять инкрементально).
- Знакомо программистам из Rust (Verus), Dafny, Liquid Haskell.

Минусы:
- Требует SMT-solver как build-time dependency.
- Возможны непредсказуемые таймауты и тяжело диагностируемые «прошло/не прошло».
- Существенная инженерная работа (VC generator, error reporting, IDE integration).

Уровень 2 не блокирует уровень 1 и добавляется как compiler extension без изменений в ядре. Порядок ввода — по мере роста pain'а от ручных proof-terms и появления пользовательского спроса.

**Что явно не делаем (уровень 3, только по необходимости):**

- Model checking / symbolic execution (Kani-style).
- Full tactic language (как Coq `Ltac` или Lean 4 `by`).
- Refinement type syntax `Int{x >= 0}` — вместо этого dependent types `(x : Int) -> (0 _ : x >= 0) -> ...`.

**Место в общей архитектуре.** Верификация — один из «векторов» использования языка (§1: type-heavy research use case), не доминирующий. Прикладной FP и systems programming — равнозначные приоритеты. Верификация не должна усложнять типичный код: программист без интереса к proofs пишет обычные типизированные программы, механизмы уровня 1 просто не активируются в его коде.

**Отношение к семантическому ядру.** Уровень 1 — целиком surface + prelude, ядро уже готово. Уровень 2 — additional pass над elaborated core, external tool integration, тоже без изменений в ядре. Это preserved property: верификация как «слой сверху» на надёжном ядре QTT.

**Открытые вопросы (см. §10):** конкретный timing перехода к уровню 2 (по каким метрикам pain'а от manual proofs решать); scope tactics library — минимальный набор convenience-функций vs полноценный tactic engine; interaction верификации с эффектами (как рассуждать о property эффектной функции — через handler-based semantics или через отдельный logical framework).

## 4. Поверхностный язык

### 4.1 Синтаксис

**Стиль:** ML/Haskell-семейство, significant indentation, currying. Ниже — иллюстративные наброски, окончательно не зафиксировано.

**Блоки — только отступами.** Тело `where`, `with`, `mutual`, `let` открывается переводом строки и задаётся отступом. Haskell'евской альтернативы «явный layout через `{ ; }`» нет: один блок — одна запись. Фигурные скобки в языке заняты другим — effect row (`{IO}`), записи (`{ x : Float }`), implicit-параметры (`{Key : Ord}`), — и переиспользовать их под layout значило бы ставить `where {` рядом с `{IO}` в одной сигнатуре.

```adamas
-- Ресурсный тип с автоматическим cleanup
resource File where
  drop h = closeFile h

openFile : String -> {IO, Except IOError} File

-- withFile — cleanup гарантирован компилятором
-- Row-переменные auto-lift'ятся; сигнатура эквивалентна
-- (File -> {IO | e} a) -> {IO, Except IOError | e} a с общей e.
withFile : String -> (File -> {IO} a) -> {IO, Except IOError} a
withFile path k =
  let h = openFile path
  k h
  -- h закрывается автоматически при выходе из scope,
  -- включая exceptional exit через Except

-- Зависимые векторы со стираемой длиной
data Vect : (0 n : Nat) -> Type -> Type where
  Nil  : Vect 0 a
  Cons : a -> Vect n a -> Vect (n + 1) a

map : (a -> b) -> Vect n a -> Vect n b
map f Nil         = Nil
map f (Cons x xs) = Cons (f x) (map f xs)

-- Определение эффекта
effect State s where
  get : {State s} s
  put : s -> {State s} ()

-- Использование эффекта
counter : {State Int} Int
counter =
  let n = get
  put (n + 1)
  n

-- Handler для State
-- Все позиции сигнатуры получают общую auto-lifted e:
-- элаборируется в s -> ({State s | e} a) -> {e} (s, a).
runState : s -> ({State s} a) -> (s, a)
runState s0 prog = handle prog with
  get     resume => resume s0 s0
  put s'  resume => runState s' (resume ())
  return v       => (s0, v)

-- Multi-shot handler для backtracking (parser combinators, non-determinism)
runNondet : ({Nondet} a) -> List a
runNondet prog = handleMulti prog with
  choose resume => resume True ++ resume False  -- resume вызывается дважды
  return v      => [v]

-- Disambiguation при нескольких одинаковых эффектах через TypeApplication
-- В row {Except IOError, Except ParseError} два разных Except:
runIO : ({Except IOError} a) -> Result IOError a
runIO prog = handle @(Except IOError) prog with
  throw e resume => Err e
  return v       => Ok v

-- Type class с UP (уровни неявны)
class Functor (f : Type -> Type) where
  map : (a -> b) -> f a -> f b

class Applicative f when Functor f where
  pure : a -> f a
  ap   : f (a -> b) -> f a -> f b
  map f x = ap (pure f) x  -- default через pure/ap

instance Functor Option where
  map f None     = None
  map f (Some x) = Some (f x)
```

**Открытые вопросы синтаксиса** перечислены в §10.

**Уточнения, вынесенные из работы над примерами:**

- **Кратности в декларациях типов** пишутся явно: `(0 n : Nat)`, `(1 h : File)`. Это делает контракт про erasure и линейность видимым в сигнатуре, ценой некоторого шума. Дефолт при отсутствии аннотации зависит от позиции:

  - **Параметр функции — `ω`.** Функция ничего не обещает о том, сколько раз использует аргумент, поэтому ω — честный дефолт.
  - **Поле конструктора — `1`.** Конструктор использует аргумент ровно однажды: он его кладёт. `ω` здесь было бы ложным утверждением, выбрасывающим истинную информацию.

  ```adamas
  data Pair a b where
    MkPair : a -> b -> Pair a b     -- элаборируется в (1 _ : a) -> (1 _ : b) -> Pair a b
  ```

  Асимметрия не является непоследовательностью: кратность описывает, как принимающая сторона использует значение, и для конструктора этот ответ известен. Прецедент — Linear Haskell, где поля линейны по умолчанию; Idris 2 оставил `ω` и получил невозможность класть уникальные значения в контейнеры.

  Обычный код изменения не замечает: `let ω p = (1, 2)` скалирует поля до ω, что для `Int` законно. Разница проявляется только на unique-типах — `let ω p = (arr, v)` отвергается на связывании, `let 1 p = (arr, v)` проходит и сохраняет уникальность `arr` при деструктуризации (1·1 = 1). Это позволяет функциям возвращать unique-значение в кортеже:

  ```adamas
  withMut : (1 arr : Array a) -> ({Alloc r | e} b) -> {e} (Array a, b)
  ```

  Обратная нужда — положить ω-значение в поле, связанное при `1`, — покрывается явной аннотацией `(ω x : a)`; каноническая обёртка `Ur` в prelude (§4.4).
- **Свободные переменные в конструкторах data и в top-level сигнатурах** автоматически поднимаются в implicit-параметры (Agda/Idris style). Например, `Nil : Vect 0 a` фактически элаборируется в `Nil : {0 a : Type} -> Vect 0 a`. Пользователь не обязан объявлять `{a}` вручную.
- **Effect row в сигнатуре — обязателен когда есть, отсутствует когда pure.** Функция без `{...}` в возвращаемом типе считается чистой; функция с эффектами обязана их указать. Частичное закрытие §10 вопроса 5 в сторону explicit-on-effects, inference не используется на public API.
- **Nat-арифметика в типах.** `Nat` имеет конструкторы `Zero` и `Succ`. Оператор `+` определяется рекурсией по первому аргументу, что даёт `Zero + m ≡ m` и `Succ k + m ≡ Succ (k + m)` дефиниционально — необходимо для эргономичных сигнатур вроде `append : Vect n a -> Vect m a -> Vect (n + m) a`. В pattern matching разрешены обе формы, `Succ k` и `n + 1`, элаборатор их отождествляет (Idris 2 style).
- **GADT — частный случай индуктивных типов с dependent parameters.** Синтаксис `data T : … where …` покрывает и обычные ADT, и GADT-стиль равномерно; отдельного language extension не требуется, потому что dependent types субсумируют GADT:

  ```adamas
  data Expr : Type -> Type where
    LitInt  : Int -> Expr Int
    LitBool : Bool -> Expr Bool
    Add     : Expr Int -> Expr Int -> Expr Int
    If      : Expr Bool -> Expr a -> Expr a -> Expr a
  ```

  Каждый конструктор возвращает `Expr` с уточнённым параметром типа. При pattern matching элаборатор автоматически уточняет параметр (`eval (LitInt n) = n` типизируется как `Int → Int`). Экзистенциальная квантификация выражается через dependent pair (§3.2). Индексы могут содержать `Type` как значение (например, `Expr : List Type -> Type -> Type` для typed environment) — работает благодаря universe polymorphism (§3.2).
- **Определение эффектов.** Через ключевое слово `effect Name [params] where …`. Каждая операция объявляется с полной сигнатурой, включая явное `{Name …}` в effect row — сигнатуры операций читаются standalone (в hover'ах, документации). Эффект синтаксически ведёт себя как модуль: операции доступны квалифицированно (`State.get`) или по короткому имени (когда нет конфликта).
- **Вызов эффектных операций.** Nullary операции вызываются как значения без `()`: `let n = get`. Операции с аргументами — как обычные функции: `put x`. Элаборатор различает по типу операции. Если нужно передать nullary-операцию как отложенное вычисление — явная лямбда: `let f = \() -> get`.
- **Синтаксис handler'а.** Два keyword'а. `handle expr with …` — single-shot, кратность `resume` = 1. `handleMulti expr with …` — multi-shot, кратность `resume` = ω, применяется для backtracking-паттернов (parser combinators, non-determinism). Ветки идут с новой строки под отступом: `opname args… resume => body` для операций, `return v => body` для нормального завершения. Имя continuation — `resume` (без альтернатив). Различие видно на месте использования; multi-shot платит копированием стека на каждый resume (см. §3.4).
- **Row в сигнатурах.** Эффекты в row разделяются запятой: `{State Int, Log, IO} a`. Row — **scoped multiset**, а не множество: дубликаты меток допускаются и не схлопываются, порядок между одноимёнными метками значим (внутренний handler перехватывает раньше внешнего, доступ к внешнему — через `mask`), порядок между различными метками несущественен. Это вынужденно: при row-как-множестве подстановка не сохраняет типизацию — сигнатура `foo : a -> b -> {Mut a, Mut b} …` при `a := b` схлопнулась бы в один эффект, и число handler'ов перестало бы соответствовать числу эффектов. Теория — Leijen, «Extensible Records with Scoped Labels» (2005), та же, из которой взят row polymorphism; Koka по той же причине допускает дубликаты в effect rows. Row-переменная записывается через `|`: `{State s | e} a` означает «`State s` плюс произвольные другие эффекты `e`». В позициях сигнатуры функции все row-выражения (включая отсутствие `{}` — pure) auto-lift'ятся общей свежей переменной, что делает функции полиморфными по «остальным» эффектам без необходимости писать `| e` руками (см. §3.4). Явно закрытая row в сигнатуре функции — если понадобится — открытый вопрос (§10).
- **Последовательность эффектов через let-цепочки.** Специальная do-нотация не нужна: строгий порядок вычислений плюс наличие эффектов в типе делают цепочку let-биндингов эквивалентной haskell'овскому `do { x <- op1; y <- op2; expr }`:

  ```adamas
  let x = op1
  let y = op2
  expr
  ```

  Это следствие §3.1 (строгость) — цепочка let-биндингов уже даёт imperative-like flow без сахара.
- **Type classes через `class Name (args) where …`.** Class — форма implicit-модуля (§3.5). Тело содержит method signatures и опционально default implementations. Superclass constraints через `when`: `class Applicative f when Functor f where …`. Несколько constraints разделяются запятой: `class Traversable f when Functor f, Foldable f where …`. Method-level constraints остаются через `{Class T} =>` в сигнатуре метода — это два разных clause с разной локальностью, `when` для класса в целом, `=>` для отдельного метода. Инстансы — `instance [name :] Class Type where …`. Именование опционально; несколько инстансов одного класса для одного типа допустимы, но требуют явного выбора: `using instanceName (expr)` для scoped-режима (внутри `expr` этот instance canonical) или `@instanceName` в точечном применении к функции. Для случаев обычных (не implicit) модулей — отдельная форма `module`; для module type — `module type`.
- **Type без индекса — implicit universe level.** В сигнатурах `f : Type -> Type`, `id : a -> a` уровни автоматически поднимаются в implicit-параметры (по аналогии с типовыми переменными). Пользователь пишет явные `{ℓ : Level}` только когда нужны несколько разных уровней в одном определении (например, `Bifunctor {ℓ ℓ' : Level} (f : Type ℓ -> Type ℓ')`).
- **Ресурсные типы через `resource Name where drop h = …`.** Обязателен деструктор `drop`. Биндинги переменных resource-типа автоматически линейны (кратность `1`), деструктор вызывается автоматически при выходе из scope на всех путях (см. §3.3). Обычные data-типы (`data`) остаются копируемыми и без автоматического cleanup — `resource` явно маркирует другую семантику.
- **TypeApplications через `@`.** Handler'ы, параметризованные типом эффекта, выбирают конкретный тип через `runExcept @IOError prog`. Синтаксис заимствован из Haskell TypeApplications, используется как для явного указания implicit-типового параметра в местах, где inference неоднозначен, так и для disambiguation при нескольких вариантах одного эффекта в row (например, `{Except IOError, Except ParseError}`).

**Объявление инстанса вместе с суперклассами.** В теле `instance C T where …` допустимо определять методы не только самого `C`, но и любого его транзитивного суперкласса. Компилятор раскладывает их по принадлежности и синтезирует недостающие инстансы суперклассов.

```adamas
instance Field (Complex Rational) where
  add (C a b) (C c d) = C (a + c) (b + d)
  mul (C a b) (C c d) = C (a*c - b*d) (a*d + b*c)
  neg (C a b)         = C (neg a) (neg b)
  div x y             = mul x (reciprocal y)
  zero                = C 0 0
  one                 = C 1 0
  reciprocal (C a b)  = …
```

Одна декларация порождает шесть инстансов: `Add`, `Mul`, `Neg`, `Div`, `Ring`, `Field`. Эквивалентная запись — шесть отдельных `instance`-деклараций, разницы в семантике нет.

База выписана явно: `Complex Rational` — поле, `Complex Float` полем не является по той же причине, по которой им не является сам `Float` (§4.3). Пример на конкретном типе, а не на `Complex a`, — не случайность: группировка предназначена именно для конкретных инстансов, см. ниже про наследование контекста.

Правила:

1. **Допустимость метода.** Метод принимается в тело, если объявлен в `C` или в транзитивном суперклассе `C` (замыкание по `when`). Метод вне этого замыкания — ошибка с указанием класса, в котором он объявлен на самом деле.
2. **Синтез.** Методы суперкласса `S` собираются в синтезированный `instance S T`, помещаемый в ту же точку программы, что и объемлющая декларация.
3. **Конфликт с существующим инстансом.** Если `instance S T` уже виден в scope — ошибка, а не переопределение и не переиспользование. Молчаливый выбор между двумя источниками одного инстанса — ровно та неоднозначность, против которой §2.3 держит scoped coherence.
4. **Неполнота.** Если методы `S` предоставлены частично — обычная ошибка неполного инстанса со списком недостающих и пометкой, что `S` синтезируется из этой декларации.
5. **Анонимность.** Синтезированные инстансы имён не получают. Если для `using`/`@` нужно имя, соответствующий инстанс пишется отдельной декларацией: именованные инстансы существуют для случая «несколько инстансов на один тип», который по построению не является случаем группировки.
6. **Коллизия имён методов.** Если одно имя объявлено двумя разными классами в замыкании суперклассов, требуется квалификация метода или вынос в отдельную декларацию. Ситуация редкая и детектируется статически.

**Контекст синтезированных инстансов наследуется целиком.** Синтезированный `instance S T` получает контекст объемлющей декларации без изменений:

```adamas
instance {Ring a} => Ring (Complex a) where
  add (C x y) (C z w) = C (x + z) (y + w)
  …
-- синтезирует instance {Ring a} => Add (Complex a), а не {Add a} => Add (Complex a)
```

Следствие: `Complex Float` не получит `Add`, потому что `Float` не `Ring`. Это ожидаемое поведение, а не дефект — контекст написан в исходнике и совпадает с тем, что синтезируется. Альтернатива, выводить минимальный контекст для каждого синтезированного инстанса из тел методов, отвергнута: она удобнее в коде с обёртками над числами, но означает, что контекст публичного инстанса нигде не написан и меняется при правке тела метода. §4.1 уже отказалась от вывода на публичном API применительно к эффектам; здесь была бы та же уступка с той же ценой.

Практический вывод: группировка предназначена для инстансов на конкретных типах. Полиморфные инстансы, у которых суперклассы требуют разных контекстов, расписываются отдельными декларациями — это честный escape hatch, а не обход недоработки. Диагностика при попытке использовать `Add (Complex Float)` указывает на источник: «`Add (Complex a)` требует `{Ring a}`, поскольку синтезирован из `instance {Ring a} => Ring (Complex a)`; для более слабого контекста объявите `Add` отдельной декларацией».

### 4.2 Записи: row polymorphism

**Решение:** анонимные extensible records с row polymorphism (в духе PureScript / Elm). Поля — first-class, проекция через `.field`, конструирование и обновление через pipe-синтаксис `{record | field = new}`.

```adamas
type Point   = { x : Float, y : Float }
type Point3D = { x : Float, y : Float, z : Float }

-- Проекция и polymorphic-функция
magnitude : { x : Float, y : Float } -> Float
magnitude p = sqrt (p.x * p.x + p.y * p.y)
-- Работает и для Point, и для Point3D благодаря auto-lift row-переменной
-- в позиции аргумента функции (см. §3.4). Эквивалентно
-- { x : Float, y : Float | r } -> Float с freshly-lifted r.

-- Конструирование
origin : Point
origin = { x = 0.0, y = 0.0 }

-- Обновление
translated : Point -> Float -> Float -> Point
translated p dx dy = { p | x = p.x + dx, y = p.y + dy }

-- Extension: та же операция { r | field = value }, компилятор различает
-- update vs extension по типу исходной записи
promote : Point -> Float -> Point3D
promote p z = { p | z = z }

-- Punning: { x, y } эквивалентно { x = x, y = y }
mkPoint : Float -> Float -> Point
mkPoint x y = { x, y }

-- Field projection как first-class function
xs : List Point -> List Float
xs = map .x
```

**Микрорешения:**

- **`type` объявляет алиас записи, не nominal type.** `Point` и `{ x : Float, y : Float }` полностью взаимозаменяемы. Nominal type — через отдельный механизм `data` (см. §4.1).
- **Обновление и extension — одна операция `{r | field = value}`.** Компилятор различает по типу исходной записи: если поле уже есть, это update; если нет — extension. Возвращаемый тип отражает результат. При scoped labels (§4.1) базовая операция row — это shadowing, а не замена: `{r | x = v}` при уже существующем `x` порождает row с двумя метками `x`, из которых видна внешняя. Surface-семантика остаётся update — элаборатор вставляет restriction перед extension, чтобы дубликат не накапливался. Разница видима только в том случае, если restriction когда-либо станет доступна пользователю (сейчас не встроена).
- **Восстановление старого значения при update.** Множественные обновления в одной операции `{ p | x = new_x, y = new_y }`, разделитель — запятая.
- **Restriction (удаление поля) не встроена.** Пересоздание через явный конструктор либо библиотечная функция типа `omit @field record`. Типичный код обходится row-polymorphism и не нуждается в явном удалении.
- **Punning.** `{ x, y }` — сахар для `{ x = x, y = y }`, когда имя переменной совпадает с именем поля.
- **Field projection как function.** `.x : { x : a | r } -> a` — синтаксическая точка используется как first-class функция, эквивалентна `\p -> p.x`.

**Row polymorphism — общая теория с эффектами.** Row polymorphism в записях и в эффектах (§3.4) — одна абстракция «расширяемый набор помеченных сущностей». В ядре реализуется один механизм row polymorphism, две surface-формы (records с полями и effects с операциями). Правила unification, extension и polymorphic quantification — общие. Симметрия pipe-синтаксиса `{ x : Float | r }` в записях и `{State s | e}` в эффектах — не совпадение, а следствие общей теории.

**Auto-lift row-переменных в позициях сигнатуры функции** (симметрично §3.4). Запись в аргументе или return type функции получает fresh row-переменную автоматически: `magnitude : { x : Float, y : Float } -> Float` элаборируется в `{ x : Float, y : Float | r } -> Float`. `magnitude` работает для любой записи, содержащей хотя бы `x` и `y`. Явное `| r` в сигнатуре не требуется, программист его не пишет.

Позиции, где row в записи **закрытая** (без auto-lift):
- В declaration типа: `type Point = { x : Float, y : Float }` — фиксированная запись с ровно двумя полями. `Point` — конкретный тип, не «класс записей содержащих x и y».
- В pattern matching: `case p of { x, y } -> …` — паттерн ожидает конкретную структуру.

**Records × dependent types.** Поля записи могут иметь любые типы, включая полиморфные и dependent:

```adamas
type Vec a = { len : Nat, data : Vect len a }
```

Это даёт **first-class Σ-типы** через record-синтаксис — более привычную альтернативу ML-стилю sigma-типов. Универсум записи вычисляется по универсумам полей автоматически (см. UP-конвенцию в §4.1).

**Records vs modules — разделены на surface, унифицированы в ядре.** Формально запись и модуль имеют одинаковую структуру: набор именованных значений с типами. В ядре реализуется одна конструкция, обслуживающая обе. Но на surface — два разных keyword'а:

- `type Foo = { ... }` — data-запись, без инкапсуляции и приватности, все поля публичны, никаких зависимостей между полями через `import`/`open`.
- `module Foo where ...` — модуль с полной поддержкой инкапсуляции: приватные определения, явный экспорт, зависимости от других модулей.

Разделение сделано ради ясности: механизмы видимости и приватности, естественные для модулей, мешали бы работе с записями как с обычными данными. Программист по keyword'у сразу понимает, с какой сущностью работает.

### 4.3 Числовая иерархия

**Решение:** операции и законы разнесены по разным классам. Операторные классы несут только сигнатуру и никаких законов не заявляют; алгебраические классы надстраиваются над ними и добавляют нейтральные элементы вместе с законами. `Num`-конгломерата нет. Иерархия — частичный порядок, не линейный, поскольку `Ring` содержит две `Monoid`-структуры на одном типе.

**Почему операции отделены от законов.** Оператор `+` должен работать и на `Int`, и на `Float`. Но `Float` не образует кольца: `(a + b) + c ≠ a + (b + c)` на совершенно обычных конечных числах — ломает не NaN, а округление, и никакое подмножество IEEE-чисел этого не чинит. Привязать `(+)` к `Ring` значит либо соврать в законах `Ring`, либо завести `+.` в духе OCaml. Оба варианта отвергнуты: первый нарушает §2.1 «честный тип», второй — налог на каждое арифметическое выражение с плавающей точкой, и платится он в том самом системном коде, ради которого §1 берёт числовую производительность в цели.

Отсюда разделение: оператор не обещает ничего, обещания живут в классе с законами. Класс либо гарантирует закон, либо его не объявляет.

**Операторные классы (законов нет):**

```adamas
class Add a where add : a -> a -> a
class Mul a where mul : a -> a -> a
class Neg a where neg : a -> a
class Div a where div : a -> a -> a
```

**Алгебраическая линия (законы есть):**

```adamas
class Ring a when Add a, Mul a, Neg a where
  zero : a
  one  : a
  -- законы: (a, add, zero, neg) — Group; (a, mul, one) — Monoid; дистрибутивность

class Field a when Ring a, Div a where
  reciprocal : a -> a  -- определено для всех x ≠ zero
  -- законы: x mul reciprocal x == one для x ≠ zero; div x y == mul x (reciprocal y)
```

**Приближённая линия (законов нет и не будет):**

```adamas
class Approximate a when Add a, Mul a, Neg a, Div a where
  nan      : a
  infinity : a
  epsilon  : a                -- машинное эпсилон
  isNaN    : a -> Bool
  isFinite : a -> Bool
  ieeeEq   : a -> a -> Bool   -- IEEE-754 равенство: nan `ieeeEq` nan == False
  ieeeLt   : a -> a -> Bool   -- IEEE-754 сравнение: на NaN False в обе стороны
```

`Approximate` намеренно не наследуется ни от `Ring`, ни от `Field`: у него нет ни ассоциативности, ни дистрибутивности, ни обратимости. Он декларирует ровно то, что арифметика с плавающей точкой действительно даёт — операции и наблюдаемые особые значения.

`ieeeEq`/`ieeeLt` живут в классе, а не в `Data.Float`, потому что без них семантику NaN не выразить, а класс никаких обещаний и так не несёт. Использоваться они должны редко — см. ниже про `Ord Float`.

**Моноидальная линия:**

```adamas
class Semigroup a where
  combine : a -> a -> a
  -- закон: ассоциативность

class Monoid a when Semigroup a where
  mempty : a
  -- закон: mempty combine x == x combine mempty == x

class Group a when Monoid a where
  invert : a -> a
  -- закон: x combine invert x == mempty
```

`Semigroup` намеренно не связан с `Add`: первый заявляет ассоциативность, второй — нет. Моноидальная линия остаётся полезной для не-числовых случаев: `String` как Monoid по конкатенации, `List a` как Monoid по append, `NonEmpty a` как Semigroup (без Monoid — нет identity).

**Ring не наследуется от Monoid.** На `Int` есть два естественных `Monoid`-инстанса (`+` с identity 0 и `*` с identity 1), выбрать один как canonical означало бы конфликт. `Ring` содержит обе структуры и извлекает их views: `additiveMonoid : {Ring a} => Monoid a`, `multiplicativeMonoid : {Ring a} => Monoid a`.

**Распределение инстансов:**

| Тип | Add | Mul | Neg | Div | Ring | Field | Approximate |
|---|---|---|---|---|---|---|---|
| `Nat` | + | + | — | — | — | — | — |
| `Int` | + | + | + | — | + | — | — |
| `Float` | + | + | + | + | — | — | + |
| `Rational` | + | + | + | + | + | + | — |

`Nat` не получает `Ring`: вычитание на нём не определено, а `Ring` требует `Neg`. Операции `+` и `*` при этом работают. Вычитание — явное, в `Data.Nat`: `sub : Nat -> Nat -> Option Nat` для случая «может не получиться» и `monus : Nat -> Nat -> Nat` с усечением в ноль, когда усечение и есть нужная семантика. То же соображение, что ниже про `Int` и деление: частичную операцию не прячут за оператор, а заставляют назвать.

`Int` не получает `Div`: целочисленное деление усекает, что при `/` в выражении читается неверно, и частично (деление на ноль). Целочисленное деление — явные `divMod`, `quotRem` в `Data.Int`, возвращающие `Option`. Это осознанное неудобство: `x / 2` на `Int` не компилируется, и программист вынужден сказать, какое именно деление он имеет в виду.

**Дополнительно, отдельно от алгебраических классов:**

- `Ord a` — сравнение, без связи с числовой структурой (`String`, кастомные типы тоже могут быть Ord).
- `Bounded a` — типы с `minBound`/`maxBound`, независимо от Ring-структуры.

**`Eq` и `Ord` для `Float`.** Инстансы есть, и они законные, но их семантика — IEEE-754 `totalOrder`, то есть побитовая:

- `nan == nan` истинно, `0.0 /= -0.0`;
- порядок тотален, `compare` определён на любых двух значениях, NaN упорядочены по знаку и полезной нагрузке.

Это настоящий тотальный порядок и настоящее отношение эквивалентности, поэтому `Float` годится ключом `Map` и `Set` без оговорок, а `Ord`-законы не нарушаются. Расходится с IEEE-сравнением он ровно в двух точках: на NaN и на знаковом нуле.

Практический выигрыш — **восстановленная трихотомия**. При IEEE-сравнении на NaN ложны все три отношения сразу (`x < t`, `x == t`, `x > t`), из-за чего `if x < t then A else B` и `if x >= t then B else A` — записи, эквивалентные для чисел, — на NaN расходятся: первая берёт `B`, вторая `A`. С `totalOrder` ровно одно из трёх истинно, и эквивалентные записи снова эквивалентны.

Чего это **не** даёт: NaN не становится заметен. Ветка по-прежнему выбирается молча, и какая именно — зависит от знакового бита NaN (отрицательный меньше всех чисел, положительный больше всех), а знак у NaN, полученного из вычислений, по сути произволен. Обнаруживать NaN нужно явно, через `isNaN`. Там, где нужна именно IEEE-семантика сравнения, вызываются `ieeeEq`/`ieeeLt` из `Approximate`.

**Тип без NaN — библиотечный, не примитив.** `NonNaN Float` со smart-конструктором в `Data.Float`. Второй примитивный тип с плавающей точкой не заводится: NaN ломает только `Eq`/`Ord`, а ассоциативность ломается округлением, и подмножество носителя её не восстанавливает — то есть «Float без дырок» законным кольцом всё равно не станет. Когда доедет уровень 2 верификации (§3.7), `NonNaN` станет refinement-типом и получит гарантии оттуда.

**Именованные инстансы для однозначности.** Если нужен `Monoid Int` явно, задаются как именованные инстансы (§3.5):

```adamas
instance additiveMonoid : Monoid Int where
  mempty = 0
  combine a b = a + b

instance productMonoid : Monoid Int where
  mempty = 1
  combine a b = a * b
```

Выбор в месте использования — через `using additiveMonoid (expr)` (scoped) или `@additiveMonoid` в точечном применении.

**Оператор-декларации отделены от классов.** Операторы привязаны к операторным классам, а не к алгебраическим — в этом и смысл разделения:

```adamas
infixl 6 +
(+) : {Add a} => a -> a -> a
(+) = add

infixl 6 -
(-) : {Add a, Neg a} => a -> a -> a
(-) a b = add a (neg b)

infixl 7 *
(*) : {Mul a} => a -> a -> a
(*) = mul

infixl 7 /
(/) : {Div a} => a -> a -> a
(/) = div

infixr 6 <>
(<>) : {Semigroup a} => a -> a -> a
(<>) = combine
```

Precedence 0–9 (как в Haskell). Ассоциативность: `infixl` (левая), `infixr` (правая), `infix` (запрет цепочек без скобок). Разделение оператора и класса позволяет добавлять операторы к существующим классам извне и иметь несколько операторных синонимов для одной функции.

**Литералы полиморфны через классы преобразования.** Три класса для трёх синтаксических форм:

```adamas
class FromNat a where
  fromNat : Nat -> a

class FromInt a where
  fromInt : Int -> a

class FromFloat a where
  fromFloat : Float -> a
```

Литерал элаборируется в вызов соответствующего преобразования: `42` → `fromNat 42`, `-42` → `fromInt (-42)`, `3.14` → `fromFloat 3.14`. Тип литерала выводится из контекста через ожидаемый тип; инстанс выбирается по этому типу.

**Default type для неоднозначных литералов.** Если контекст не задаёт тип, `FromNat`/`FromInt`-литералы default'ятся на `Int`, `FromFloat` — на `Float`. Компилятор выводит warning: «использую default Int; для явного типа добавьте аннотацию». Warning можно подавить прагмой на модуле или локально. Строгий режим (без default'ов) — опция компилятора для проектов, где неявные типы литералов недопустимы.

**Пример полной картины:**

```adamas
-- Через Ring: нужны и операции, и zero
sumR : {Ring a} => List a -> a
sumR []      = zero
sumR (x::xs) = x + sumR xs

-- Через Add: zero не нужен, работает и на Float
sumNE : {Add a} => NonEmpty a -> a
sumNE ne = foldl add ne.head ne.tail

-- Через Monoid — для строк, списков и прочего не-числового
foldM : {Monoid a} => List a -> a
foldM []      = mempty
foldM (x::xs) = x <> foldM xs

exampleInt : Int
exampleInt = sumR [1, 2, 3]                            -- 6

exampleFloat : Float
exampleFloat = sumNE { head = 1.5, tail = [2.5, 3.0] } -- 7.0
-- sumR здесь не типизируется: Float не Ring, и это ровно то,
-- что мы хотим сказать про Float

exampleStr : String
exampleStr = foldM ["hello", " ", "world"]             -- "hello world"

exampleNamed : Int
exampleNamed = using productMonoid (foldM [2, 3, 4])   -- 24
```

**Цена решения.** Объявление нового числового типа затрагивает четыре-пять классов вместо одного. Записывается это по-прежнему одной декларацией — см. группирующие инстансы в §4.1. Остаточная цена не в объёме кода, а в том, что автор инстанса должен знать карту дробления: в каком классе живёт `add`, в каком `zero`, в каком `reciprocal`. У `Num`-конгломерата этого знания не требовалось. Это прямое следствие разделения операций и законов и осознанная плата за то, что ограничение `{Ring a}` теперь что-то значит.

### 4.4 Prelude

**Принципы:**
- Минимальный, всё небазовое — явный импорт.
- Никаких partial функций.
- `NonEmpty` встроен; `head : NonEmpty a -> a`.
- Опции в стиле `Option` (не `Maybe` — слегка короче, привычно из Rust/Scala).
- `Result e a` для ошибок, `Either` — алиас или вообще убран.

**Базовые типы:**

```adamas
-- Числовые
Nat, Int, Float
-- Логика
Bool = True | False
-- Знак / отсутствие значения
Option a = None | Some a
Result e a = Err e | Ok a
-- Коллекции
List a = Nil | Cons a (List a)    -- строгий, см. §10 вопрос 13
NonEmpty a = { head : a, tail : List a }
-- Строки
String    -- UTF-8, §4.5
Char      -- Unicode scalar value
-- Порядок
Ordering = LT | EQ | GT
-- Явная ω-обёртка: поля конструкторов имеют кратность 1 (§4.1),
-- Ur возвращает значение к неограниченному использованию
Ur a = MkUr (ω x : a)
```

**Операторы (в prelude декларируются как отдельные infix):**

```adamas
-- Арифметика (через Add/Mul/Neg/Div, §4.3; `/` на Int не определён)
infixl 6 +, -
infixl 7 *, /
-- Сравнения (через Ord)
infix 4 ==, /=, <, <=, >, >=
-- Логика
infixr 3 &&
infixr 2 ||
-- Композиция и pipe
infixr 9 .           -- (f . g) x = f (g x)
infixl 1 |>          -- x |> f = f x
-- Cons
infixr 5 ::           -- 1 :: [2, 3] = [1, 2, 3]
-- Конкатенация через Semigroup
infixr 6 <>
```

**Ключевые функции коллекций:**

```adamas
-- List
map     : (a -> b) -> List a -> List b
filter  : (a -> Bool) -> List a -> List a
foldl   : (b -> a -> b) -> b -> List a -> b
foldr   : (a -> b -> b) -> b -> List a -> b
length  : List a -> Nat
reverse : List a -> List a
(++)    : List a -> List a -> List a       -- infixr 5
lookup  : {Eq k} => k -> List (k, v) -> Option v
zip     : List a -> List b -> List (a, b)
-- Option
map     : (a -> b) -> Option a -> Option b   -- через Functor
unwrapOr : a -> Option a -> a                -- default при None
-- Result
map     : (a -> b) -> Result e a -> Result e b
mapErr  : (e -> e') -> Result e a -> Result e' a
```

**Функции эффектов (стандартные convenience):**

```adamas
-- Except
try     : ({Except e} a) -> Result e a
throw   : e -> {Except e} a
-- IO
println : String -> {IO} ()
print   : String -> {IO} ()
readFile : String -> {IO, Except IOError} String
-- Общее
identity : a -> a
const    : a -> b -> a
flip     : (a -> b -> c) -> b -> a -> c
```

**Классы, доступные без импорта:**

- Из §4.3: операторные `Add`, `Mul`, `Neg`, `Div`; алгебраические `Semigroup`, `Monoid`, `Group`, `Ring`, `Field`; `Approximate` для плавающей точки; `Ord`, `Bounded`.
- Из §4.6 (derivable): `Eq`, `Show`, `Ord`, `Hashable`.
- Из §4.1: `Functor`, `Applicative`, `Monad` (последний — для интеропа, см. §3.4).
- Literal-конверсии: `FromNat`, `FromInt`, `FromFloat`.

**Что НЕ в prelude:**

- `HashMap`/`HashSet`/`TreeMap` — в `Data.Map`, `Data.Set`.
- `ToJSON`/`FromJSON` — в `Data.JSON`.
- Регулярные выражения, парсеры — в `Text.Regex`, `Text.Parser`.
- Async / Concurrency — в `Concurrent` (Nursery, Task, spawn, await).
- File system beyond read/write — в `System.FS`.

**Явный импорт:**

```adamas
import Data.Map as Map
import Concurrent (Nursery, spawn, await, withNursery)
```

Модули импортируются quualified (доступ через `Map.insert`) или с явным списком открытых имён. Wildcard-импорта (`import Module (..)`) намеренно нет — все имена в scope должны быть явны, чтобы навигация по коду не требовала знания всей библиотеки.

### 4.5 Строки

**Решение:** один тип `String` — UTF-8 ByteString. Slices (views) без аллокации. Операции на уровне grapheme clusters — отдельные функции в `String.Graphemes`.

### 4.6 Метапрограммирование

**Решение:** встроенные макросы, компилируемые и выполняемые в изолированном macro-runtime, hygiene by default. Синтаксически близко к Lean 4 (quotation/splicing), но с ограниченным API — pure-функции над AST без compile-time IO.

**Use cases:**
- Derivation instance'ов (Eq, Show, Ord, Hashable, ToJSON, etc.).
- DSL-расширения.
- Compile-time валидация (например, проверка SQL или regex на этапе компиляции).

**Синтаксис quotation и splicing:**

```adamas
-- Macro сигнатура — pure-функция с эффектом Macro для доступа к API
derive_eq : TypeInfo -> {Macro} InstanceDecl
derive_eq info = 
  quote instance Eq $(info.name) where
    (==) $(genLhs info) $(genRhs info) = $(genBody info)
```

- `quote { ... }` — quotation: код внутри превращается в AST-значение.
- `$(expr)` — splicing: вставка AST-значения в место кода.

**Macro reflection API.** Macro получает описание типа как обычную структуру:

```adamas
type TypeInfo = 
  { name         : Name
  , parameters   : List (Name, Kind)
  , constructors : List ConstructorInfo
  }

type ConstructorInfo = 
  { name   : Name
  , fields : List (Option Name, Type)   -- Option Name: Some для record, None для positional
  }
```

Macro также имеют доступ к операциям через эффект `Macro`: `freshName : {Macro} Name`, `reportError : String -> {Macro} a`, `resolveInScope : Name -> {Macro} (Option Definition)`. Никакого IO, файловой системы или сетевого доступа — только манипуляции с AST и запросы к elaboration-контексту.

**Стадии выполнения.** Macro запускаются на elaboration-time, когда типы уже разобраны, но instance-код ещё не сгенерирован. Это правильный момент для `deriving`: TypeInfo полностью доступен, генерируемый код проходит обычную type-check как если бы был написан руками. Более ранние стадии (parse-time expansion) — для случаев DSL, где нужно менять сам синтаксис до типизации; вводится по мере необходимости.

**Sandboxed macro API (без compile-time IO).** Macro — pure-функция AST → AST. Никакого доступа к environment, файловой системе, network, FFI, глобальному состоянию. Это принципиальное ограничение, а не временное упрощение.

Причины:
- **Cross-compilation.** Если macro выполняет произвольный код с runtime-зависимостями (проблема Template Haskell), при cross-compilation к target'ам вроде WebAssembly, embedded, или другой архитектуры приходится либо иметь целевой runtime на host'е (`-fexternal-interpreter` в GHC — сложная инфраструктура), либо запрещать macro. Sandboxed pure API — единственный target для macro (сам компилятор), никаких проблем с cross-compilation.
- **Reproducible builds.** Macro-execution детерминистичен: один и тот же исходник → один и тот же результат независимо от машины и environment (§7.1 lockfile + reproducibility).
- **Предсказуемость (§2.4).** Программист видит по типу `TypeInfo -> {Macro} InstanceDecl`, что macro не делает больше, чем заявлено. Compile-time не превращается в непрозрачную фазу.

**Macro Runtime Isolation.** Macro выполняются в isolated runtime, не совпадающем с target-runtime программы:

- **Стартовая позиция (Фаза 3–4):** macro интерпретируется прямо в компиляторе. Ограниченное pure-подмножество Adamas (без IO, без FFI) — интерпретатор написан на host-языке (Rust), работает над Adamas AST. Медленнее нативного, но для типичных derive-нагрузок приемлемо.
- **Долгосрочная позиция:** macro компилируется в bytecode специального VM, компилятор содержит интерпретатор bytecode. Компромисс между гибкостью (macro пишется на полном pure-Adamas) и изоляцией (VM независим от target). Прототипы такого подхода — Zig comptime, экспериментальные попытки использовать WebAssembly как universal macro-runtime.

Переход от интерпретации к bytecode VM — по метрикам: когда macro становятся сложны/долги настолько, что interpret-overhead ощутим, или когда библиотечные macro-утилиты становятся полноценным подмножеством Adamas (см. §10).

**Hygiene by default.** Свежие имена, вводимые macro через `freshName`, гарантированно не конфликтуют с пользовательскими. Ссылки на имена из scope определения macro (например, `combine` из `Semigroup` внутри `derive_eq`) резолвятся в scope определения, не в scope вызова. Escape hatch для намеренного захвата имён — явный синтаксис (детали позже).

**Синтаксис derive:**

```adamas
-- Attached (типичный случай, 90% использования)
data Color = Red | Green | Blue
  deriving (Eq, Show)

data Tree a = Leaf | Node (Tree a) a (Tree a)
  deriving (Eq, Show)

-- Standalone (для orphan-derive или отложенного derive)
data Foo = ...
derive Eq Foo
```

`deriving (X, Y, ...)` в attached-форме и `derive X Type` в standalone-форме — оба сахар для явного вызова macro:

```adamas
instance Eq Color = derive_eq typeof(Color)
```

Класс считается derivable, если для него в scope есть macro-функция с сигнатурой `Name -> TypeInfo -> {Macro} InstanceDecl`. Компилятор проверяет наличие такой функции; если её нет — статическая ошибка. Это делает derive расширяемым (пользователь пишет свою derive_MyClass macro для своего класса) и контролируемым (`deriving (SomeClass)` без macro — ошибка компиляции, не молчаливое поведение).

**Constraint inference для параметризованных типов.** Для типа с параметрами macro автоматически добавляет constraints по параметрам, чьи типы используются рекурсивно. `data Tree a deriving Eq` → `instance {Eq a} => Eq (Tree a)`. Value-параметры (`n : Nat` в `Vect n a`) в constraints не участвуют — только type-параметры.

**Стандартные derivable классы в prelude:**
- `Eq`, `Ord` — сравнения.
- `Show`, `Read` — string representation (Read с осторожностью: partial при некорректном input, требует явного обращения).
- `Hashable` — для HashMap/HashSet.
- `ToJSON`, `FromJSON` (в отдельном модуле) — сериализация.

Каждый экспонирует свой `derive_X` macro через стандартный API.

### 4.7 Опциональная тотальность

**Решение:** функция помечается `total`, и компилятор проверяет:
- Структурную рекурсию (или well-founded recursion с явным доказательством).
- Покрытие паттернов.

Тотальность распространяется по графу вызовов: `total` функция может вызывать только `total` функции (или функции на стираемых аргументах, для которых семантика тотальности тривиальна).

**Тотальность как основа верификации.** Тотальная функция может использоваться как spec: она гарантированно возвращает значение, значит тип возвращаемого значения — надёжное propositional statement о результате. Это база для механизмов §3.7 (верификация свойств): доказательства выражаются как тотальные функции, кратность 0 обеспечивает erasure. Non-total функция не может участвовать в proof-terms — попытка использовать её в 0-кратном контексте даёт compile error.

### 4.8 Модули

**Синтаксис объявления module type:**

```adamas
module type Ord where
  type T
  compare : T -> T -> Ordering
```

Module type — сигнатура, набор объявлений (типов и функций) без реализаций. Играет роль контракта для будущих module value.

**Синтаксис объявления модуля:**

```adamas
module IntOrd : Ord where
  type T = Int
  compare a b = intCompare a b
```

`: Ord` — опциональная аннотация сигнатурой. Без неё модуль имеет структурный тип, выводимый из содержимого. С аннотацией — модуль обязан удовлетворять сигнатуре, все члены сигнатуры реализованы.

**Module functor — модуль, параметризованный модулем:**

```adamas
module OrderedMap (Key : Ord) where
  data Map v = ...

  empty  : Map v
  insert : Key.T -> v -> Map v -> Map v
  lookup : Key.T -> Map v -> Option v
```

Параметр — именованный модуль с явной сигнатурой. По умолчанию параметр explicit; для implicit-варианта — фигурные скобки: `module OrderedMap {Key : Ord} where …` (тогда апплицируется без явного аргумента через механизм implicit-разрешения, см. §3.5).

**Applikation functor'а — function-call syntax:**

```adamas
module IntMap = OrderedMap IntOrd
```

Модули — first-class values, применение functor'а не отличается синтаксически от вызова обычной функции.

**Signature refinement через `with type`:**

```adamas
module IntMap = OrderedMap IntOrd with type Key.T = Int
```

Раскрывает abstract type parameter в контексте применения functor'а. Без refinement `IntMap.Map String` типизируется через абстрактный `Key.T`; с refinement — через реальный `Int`. Синтаксис заимствован из OCaml.

**Nested modules:**

```adamas
module Collections where
  module OrderedMap (Key : Ord) where
    ...
  module HashMap (Key : Hashable) where
    ...
```

Иерархическая организация, path-доступ: `Collections.OrderedMap IntOrd`. Уровень вложенности не ограничен.

**Доступ к членам модуля через `.`:**

- `IntMap.Map v` — тип из модуля.
- `IntMap.empty`, `IntMap.insert` — функции из модуля.
- `Key.T` внутри functor body — тип из параметра-модуля.

**Пример полной картины использования:**

```adamas
example : IntMap.Map String
example = 
  let m1 = IntMap.insert 1 "one" IntMap.empty
  let m2 = IntMap.insert 2 "two" m1
  m2

-- Или через class-форму, если Ord Int в scope как class-инстанс:
exampleClass : Map Int String
exampleClass = insert 1 "one" (insert 2 "two" empty)
-- Здесь insert : {Ord k} => k -> v -> Map k v -> Map k v
-- Ord Int резолвится implicit
```

Обе формы (functor и class) валидны и решают одну задачу разными способами. Выбор — по правилам §3.5.

**Ordered scoping внутри модуля.** Определения в модуле видят только то, что объявлено **выше по тексту** (Agda/Idris/Lean 4 стиль). Для взаимной рекурсии — явный блок `mutual`:

```adamas
mutual
  data Expr = ELit Int | EIf Cond Expr Expr | ...
  data Cond = CEq Expr Expr | CAnd Cond Cond | ...

  eval : Expr -> Value
  eval (ELit n)     = VInt n
  eval (EIf c t e)  = if evalCond c then eval t else eval e

  evalCond : Cond -> Bool
  evalCond (CEq a b)  = eval a == eval b
  evalCond (CAnd a b) = evalCond a && evalCond b
```

Всё внутри `mutual`-блока — взаимно-видимо; между `mutual`-блоками и обычными top-level определениями — обычное ordered scoping.

Обоснование выбора ordered vs Haskell/OCaml-style взаимно-рекурсивной видимости:

- **Консистентность с let-цепочками.** Внутри функций у нас уже ordered scope (`let n = get; put (n + 1); n`). Top-level модуль с той же семантикой убирает диссонанс.
- **Termination checking (§4.7).** `@total`-проверка call-graph'а работает предсказуемо, когда граф вызовов ограничен «объявленным выше плюс явный mutual». Иначе требуется полный dependency analysis до type-check'а.
- **Coverage checker для dependent pattern matching** (Idris 2 style, §10 вопрос 7) — аналогично, проще в ordered контексте.
- **Explicit mutual recursion как signal.** Взаимная рекурсия обычно требует внимания к termination и invariants; `mutual` заставляет программиста задуматься.
- **§2.1 п.4 «дисциплина важнее свободы».** Программист чуть менее свободен в порядке, получает более предсказуемую семантику и лучшую читаемость сверху вниз.

Правила строгие: forward-references запрещены даже для типов. Если тип `A` используется в сигнатуре функции `f`, `A` должен быть объявлен до `f` (либо оба в одном `mutual`-блоке). Смягчение для forward-refs типов рассматривалось и отвергнуто ради простоты правил и однозначности.

### 4.9 SIMD

**Решение:** SIMD как first-class часть языка, не через FFI к intrinsics. Обосновано принципом §2.1 п.6 «системный код — first-class». Программист, работающий с векторной обработкой (numerical computing, media codecs, dataplane), не должен уходить в C через FFI или писать unsafe-wrapping.

**Модель:**

```adamas
-- Фиксированной ширины векторный тип, только для SIMD-совместимых элементов
Vec : (n : Nat) -> (a : Type) -> {Primitive a} => Type
-- Типичные instantiation: Vec 4 Float, Vec 8 Int32, Vec 16 Int8, Vec 2 Float64, etc.
-- Ширина ограничена платформенным SIMD width (проверяется на elaboration-time)
```

**Ограничение `Primitive`.** `Vec n a` требует `{Primitive a}` — closed class для базовых numeric типов с известным SIMD layout:

```adamas
-- Closed class, инстансы предоставляет компилятор, пользователь добавить не может
class Primitive a where
  simdLayout : SIMDLayout    -- size + alignment для SIMD-операций

-- Instances: Int8, Int16, Int32, Int64, UInt8, UInt16, UInt32, UInt64,
--            Float32, Float64.
-- Bool представлен как маска (bit-packed) — отдельный внутренний layout.
```

Ограничение критично: `Vec 4 (Ref r Packet)` (SIMD-вектор из pointer'ов) — типовая ошибка, потому что `Ref` не Primitive. Реальные SIMD-инструкции работают с primitive numeric layout'ом, «SIMD-вектор pointer'ов» — концептуально скалярный цикл, семантически не то же самое.

**Операции над `Vec` — примитивы, а не резолвинг через классы элемента.** Element-wise арифметика на `Vec n a` определена операциями компилятора, привязанными к `{Primitive a}`, и лоуэрится в intrinsics напрямую. Она **не** резолвится через `Add a`/`Mul a` или `Ring a`: пользовательский инстанс мог бы содержать произвольную реализацию, а никакая произвольная реализация в векторную инструкцию не переводится. Пример проблемы, будь связь обратной:

```adamas
-- Если бы (+) на Vec шёл через Mul a, такой инстанс был бы легален,
-- и «SIMD-умножение» превратилось бы в цикл над списками
instance Mul Int where
  mul a b = length (crossProduct (replicate a ()) (replicate b ()))
```

Обещание §6 «паритет с C+intrinsics» держится только на том, что реализация операции известна компилятору, а не приходит из scope. Поэтому направление зависимости — от примитивов к классам, а не наоборот: `Add (Vec n a)`, `Mul (Vec n a)` и при желании `Ring (Vec n a)` существуют как инстансы, **построенные поверх** примитивных операций, чтобы `Vec` можно было передавать в обобщённый код. Пользовательский `Mul a` на элементе к содержимому `Vec`-операций отношения не имеет.

Практическое следствие: `Vec 4 Float` получает `Add`/`Mul`/`Neg`/`Div` и `Approximate`, но не `Ring` — по той же причине, что и сам `Float` (§4.3), поскольку element-wise сложение флоатов не ассоциативнее скалярного.

**Разделение `Vec` и `Vect`.** Это два разных типа:

- `Vect (n : Nat) (a : Type) -> Type` — обычный fixed-length container (§4.1), поля любых типов.
- `Vec (n : Nat) (a : Type) -> {Primitive a} => Type` — SIMD-вектор, элементы Primitive.

Разделение осознанное: `Vect` — data structure для программной композиции, `Vec` — hardware-mapped векторный register. Конверсия — явная (`fromVect : {Primitive a} => Vect n a -> Vec n a`, `toVect : {Primitive a} => Vec n a -> Vect n a`).

Основные операции (в prelude или `Data.SIMD`), все — примитивы по `{Primitive a}`:

```adamas
-- Конструирование
splat    : {Primitive a} => a -> Vec n a           -- заполнение одним значением
fromVect : {Primitive a} => Vect n a -> Vec n a    -- явная конверсия из Vect
toVect   : {Primitive a} => Vec n a -> Vect n a    -- обратно (unpacking)

-- Element-wise арифметика: примитивы, lowering в intrinsics;
-- операторы (+), (-), (*), (/) доступны через синтезированные
-- Add/Neg/Mul/Div (Vec n a), построенные поверх этих примитивов
vecAdd, vecSub, vecMul, vecDiv : {Primitive a} => Vec n a -> Vec n a -> Vec n a

-- Element-wise сравнения (возвращают маску)
vecEq, vecLt, vecGt : {Primitive a} => Vec n a -> Vec n a -> Vec n Bool

-- Reductions
sum       : {Primitive a} => Vec n a -> a
horizMax  : {Primitive a} => Vec n a -> a

-- Permutations / shuffles
shuffle   : {Primitive a} => Vec n a -> Vect n (Fin n) -> Vec n a
permute   : {Primitive a} => Vec n a -> Vec n Int -> Vec n a

-- Load/store с alignment
load    : {Primitive a} => AlignedBuffer n a -> {IO} (Vec n a)
store   : {Primitive a} => Vec n a -> AlignedBuffer n a -> {IO} ()
```

**Alignment через resource-типы:**

```adamas
resource AlignedBuffer (n : Nat) (a : Type) where
  drop b = freeAligned b
-- Alignment гарантирован конструктором (aligned malloc), 
-- runtime layout соответствует требованиям SIMD load/store
```

**Portability layer.** Ширина SIMD различается по платформам (SSE = 128 bit, AVX = 256 bit, AVX-512 = 512 bit, NEON = 128 bit, WASM SIMD = 128 bit). Абстракция:

- Компилятор знает target SIMD capabilities через target triple.
- `Vec n a` где `n × sizeof(a)` больше native width — элаборируется в серию native-операций (loop unrolling).
- `Vec n a` где ширина не соответствует native — либо fallback на scalar, либо compile-time error (зависит от прагмы).
- Пользователь может запросить target-specific optimizations через compile-time capability detection (`@simd(min_width=256)`).

**Реализация:** primitive-функции с прямым lowering в LLVM intrinsics (§8 backend). Для non-LLVM backends (C, WASM) — эквивалентные intrinsics либо scalar fallback. Portable API остаётся тот же.

**Открытые вопросы (см. §10):** правила выбора native width при mismatch; синтаксис для явного target-specific optimization request; interaction с regions (§3.6) для aligned buffer pools.

### 4.10 Alternative backends: WebAssembly и GPU offload

**Решение:** ядро языка backend-agnostic; альтернативные target'ы (WASM, GPU) — feasible расширения через комбинацию существующих механизмов + backend-specific lowering. В research-прототипе не реализуются (см. §1 non-goals), но дизайн явно проверен на compatibility.

**WebAssembly backend.**

Практически не требует изменений. Основа готова:

- **LLVM backend (§8)** генерирует WASM из коробки через target triple. Инженерная работа — минимальна.
- **Macro runtime isolation (§4.6)** решает главную боль cross-compilation языков с TH-подобными фичами: macros выполняются на host в sandboxed runtime, никогда не в target. WASM-target не создаёт проблем для метапрограммирования.
- **Регионы (§3.6)** — WASM linear memory естественно ложится на arena-стратегию. `Arena` через linear memory bump — прямой mapping.
- **Erasure (§3.2)** — меньше runtime overhead, что критично для WASM code size.

Работа для WASM backend:

- **FFI-шим для WASI/JavaScript imports.** WASM не имеет прямого C ABI; interop идёт через host imports. Требует специализированного `extern "wasm"` варианта (в дополнение к `extern "C"` из §5.3).
- **SIMD lowering** на WASM SIMD (fixed 128-bit) вместо native x86/ARM intrinsics. `Vec 4 Float` — прямой mapping; wider vectors — unrolling.
- **Concurrency.** WASM MVP single-threaded, threads — extension. Nursery (§5.2) работает только с extension; без него — синхронный runtime.
- **Perceus упрощён.** Без threads — атомарные счётчики не нужны, чистый неатомарный RC. Проще нативных target'ов.

Реалистичный timeline: одна дополнительная фаза в roadmap, ориентировочно 2–3 месяца работы после того, как основной LLVM backend готов (после Фазы 5).

**GPU offload.**

Более амбициозно, но фундамент есть. Модель — LLVM Offload style: отдельные функции помечаются для параллельной компиляции host + device, runtime library управляет data transfer и kernel launch.

**Атрибут `@offload`:**

```adamas
@offload gpu
processImage : Vec 1024 (Vec 1024 Float) -> Vec 1024 (Vec 1024 Float)
processImage img = 
  mapGPU (fun row -> mapGPU sigmoid row) img
```

Компилятор проверяет offload-safety:

- Только pure-функции или функции с явно offload-совместимыми эффектами (`{GPUMem g}` — специфический для GPU эффект аллокации).
- Только offload-safe типы (Primitive numeric, Vec, регионные Ref в GPU-регионе).
- Никаких multi-shot handler'ов (segmented stack copy не работает на GPU).
- Никаких обычных Nursery/spawn (GPU parallelism — data-parallel через `mapGPU`/`reduceGPU`, не task-parallel).

**GPU memory hierarchy через регионы (§3.6):**

Стандартная библиотека `Data.GPU` предоставит специфические стратегии:

```adamas
module GPU where
  -- GPU memory tiers как стратегии аллокации
  module GlobalArena : AllocStrategy       -- device global memory
  module SharedArena : AllocStrategy       -- per-block shared memory
  module PrivateArena : AllocStrategy      -- per-thread private memory
  
  -- Data-parallel primitives
  mapGPU    : {Primitive a, Primitive b} => (a -> b) -> Vec n a -> Vec n b
  reduceGPU : {Primitive a} => (a -> a -> a) -> a -> Vec n a -> a
  ...
```

Ref в GPU-регионе (`Ref g a` где `g : Region GPU.GlobalArena`) — уже поддерживается механикой §3.6 без изменений. Compiler знает, что аллокация физически в device memory, не host.

**SIMD как база для GPU compute (§4.9).** SIMT-модель GPU концептуально близка к SIMD. `Vec n a` — уже готов к mapping на GPU vector types (float4, int4). Дополнительной работы не требуется, только backend lowering.

**Что нужно для реализации:**

- **Атрибут `@offload target` и проверка restrictions.** Аналог `@total`, `@fbip` — существующий attribute-механизм расширяется одним пунктом.
- **Backend integration.** LLVM Offload runtime (уже работает для C/Rust); альтернативно — SPIR-V (более portable) или прямой PTX/AMDGPU IR. Существенная инженерная работа, но не языковой дизайн.
- **`Data.GPU` библиотека.** Data-parallel primitives, wrappers над offload runtime. Обычная библиотечная работа.

**Timeline:** отдельный подпроект после research-прототипа готов, ориентировочно 6–12 месяцев для рабочей MVP. Не блокирует Фазы 0–6 основного языка.

**Ключевой итог для дизайна.** Ни WASM, ни GPU offload **не требуют изменений в ядре**. Оба используют:

- Существующую систему эффектов для проверки backend-safety.
- Существующие регионы для управления backend-specific memory (WASM linear memory, GPU memory tiers).
- Существующие атрибуты (`@offload` в стиле `@total`/`@fbip`).
- Существующий SIMD как база для vector compute.
- Существующую macro runtime isolation для проблем cross-compilation.

Это подтверждает, что дизайн-выборы (regions, effects, attributes, sandboxed macros) — не accidental, а связная система, естественно масштабирующаяся на разнообразные targets.

**Открытые вопросы (см. §10):** полный список restrictions для `@offload`-функций; interaction offload-функций с эффектной системой (какие эффекты допустимы в offload-контексте); специфика GPU parallelism API — data-parallel-only или включить task-parallel через специфические GPU-primitives; поддержка heterogeneous computing (одна программа с частью на CPU, частью на GPU, координация memory transfers).

## 5. Рантайм

### 5.1 Управление памятью: Perceus

**Решение:** reference counting в стиле Perceus (Reinking, Xie, de Moura, Leijen 2021).

**Ключевые свойства:**
- Деаллокация детерминистична (нет GC pauses).
- RC-операции вставляются и оптимизируются компилятором (drop reuse).
- FBIP (Functional But In-Place): при уникальности значения обновление структуры выполняется как in-place мутация, без аллокации (см. подробнее ниже).

**FBIP: Functional But In-Place.**

FBIP — стиль исполнения, при котором функциональный код, синтаксически выглядящий как создание новой структуры, при определённых условиях исполняется как in-place мутация существующей. Не оптимизация «компилятор угадал», а гарантия из свойств Perceus + анализ уникальности.

Механика на примере `map` на бинарном дереве:

```adamas
data Tree a = Leaf | Node (Tree a) a (Tree a)

map : (a -> b) -> Tree a -> Tree b
map f Leaf         = Leaf
map f (Node l x r) = Node (map f l) (f x) (map f r)
```

В точке паттерн-матчинга на `Node l x r` компилятор emit'ит проверку RC:

- RC > 1 — нода shared, паттерн-match копирует поля, старая нода остаётся жить, новый `Node (...)` в правой части аллоцируется отдельно (классическое immutable-поведение).
- RC = 1 — нода уникальна, компилятор emit'ит `reuse` вместо `drop + alloc`: слоты той же ноды переписываются новыми значениями. Аллокаций 0.

Результат: `map succ tree` на уникальном дереве работает без аллокаций Node'ов вообще.

Условия срабатывания reuse:
- Уникальность в момент match (RC = 1). Гарантируется статически для linear и resource инпутов; для ω-инпутов проверяется runtime.
- Совпадение формы нового и старого конструктора (Node → Node, не Node → Leaf, не Node → Cons).

**FBIP работает для не-линейных типов** — с runtime-проверкой RC. Программист может писать чистый функциональный код без явной линейности, и оптимизация сработает при типичном use pattern передачи уникального значения через цепочку преобразований. Для гарантированного FBIP (без runtime-проверки) — линейный или resource инпут.

**Атрибут `@fbip` для явных гарантий:**

```adamas
@fbip
map : (a -> b) -> Tree a -> Tree b
map f Leaf         = Leaf
map f (Node l x r) = Node (map f l) (f x) (map f r)
```

Атрибут — обязательство перед компилятором: «функция должна быть FBIP-совместимой везде, где это структурно возможно». Проверяет: (1) все ветви pattern-matching, в которых создаётся результирующая структура, совместимы с reuse исходной (совпадение формы конструкторов, размера); (2) нет ветвей, где reuse структурно возможен, но не применяется из-за ограничений реализации. Не гарантирует, что RC действительно 1 в момент вызова — это runtime-свойство, зависящее от use pattern.

Если функция не может быть FBIP-совместимой (например, результат — принципиально другого типа, как в `flatten : Tree a -> List a`), компилятор выдаёт ошибку с указанием строки. Программист либо снимает `@fbip`, либо переписывает функцию.

По духу `@fbip` симметричен `@total` из §4.7: явное обязательство о свойстве функции, проверяемое компилятором.

**Уровень аннотации — функция, не pattern-match.** `@fbip` применяется ко всей функции; частичная FBIP-совместимость (например, только в одной ветви filter'а) — допустима и покрывается общей проверкой. Финер-грануляции (аннотация отдельных ветвей) — не вводим стартово.

**Discoverability FBIP.** Без `@fbip` статус функции показывается через LSP hint: «reuse applies to unique inputs» / «reuse not applicable, allocations expected». Программист может explorer'ить без формальных обязательств, при необходимости — переводить в `@fbip` для строгой проверки.

**Линейные значения** в смысле QTT — обходятся без RC вообще: компилятор знает уникальность статически, генерирует direct deallocation. Это важно и для производительности, и для concurrency (см. ниже): линейные значения не участвуют в RC-протоколе, а потому не создают проблем ни с атомарностью, ни с циклами. Побочно: линейные и resource инпуты — идеальные FBIP-кандидаты, reuse на них происходит без runtime-проверки RC.

**Concurrency и атомарность счётчиков.** Оригинальный Perceus, Koka и Lean 4 используют неатомарные счётчики: в чисто функциональном локальном коде атомарность не нужна, а её цена (на x86 ~10–20 циклов против ~1 для обычной инкрементации, на ARM хуже) существенна в hot loop. Однако как только значения пересекают границы потоков — через `Async`, channels, spawn — неатомарные счётчики становятся data race. Lean 4 обходит это deep-copy при передаче в `Task`, что для proof assistant приемлемо, но противоречит §5.2, где structured concurrency — first-class.

Стратегия для Adamas:

- **Фаза 5 (первая реализация):** неатомарные счётчики, sharing между потоками либо через явное копирование, либо запрещён на уровне типов. Минимальная работоспособная версия для замера single-thread performance.
- **Фаза 5+ (когда появится реальный concurrency-код):** различение local vs shared через тип. Естественная точка — эффект `Async` знает, что значение уходит в другой поток; пересекающие эту границу значения промоутятся в shared режим (atomic RC). QTT здесь ключевой актив: линейные значения не требуют RC, что уменьшает горячий путь.
- **Долгосрочно:** biased/hybrid RC (Choi et al. 2018, BRC) как оптимизация — только если бенчмарки покажут, что атомарные операции реально болят. Владелец-поток работает с неатомарным счётчиком, остальные — с атомарным; типичный overhead 1.5–2× против чисто неатомарного, но без deep copy.

**Открытые вопросы:**

1. **Циклические структуры.** Perceus в чистом виде не справляется с циклами. Варианты: weak references как явная конструкция; arena allocation для известно-циклических случаев; trial deletion как fallback. Стартовая позиция: weak references, циклы строятся явно (не «прозрачно как в GC»).
2. **Интеграция RC-режима с эффектами.** Как именно `Async`/`Channel` триггерят промоушен из local в shared? Стартовая гипотеза (см. §5.2): автоматический promotion transitively reachable значений на границе `spawn`. Точечный маркер через тип-уровневый `Shared` — потенциальная оптимизация по бенчмаркам.

### 5.2 Concurrency

**Решение:** lightweight threads (как в Haskell), structured concurrency через nursery-паттерн (Trio-style). Nursery — не аргумент пользовательской функции, а эффект: операции доступны внутри `withNursery`, а Scope как resource живёт в замыкании handler'а и невидим на surface. Это решает проблему линейности Scope-как-аргумента (несколько `spawn` подряд иначе невозможны при кратности 1).

**Публичный API:**

```adamas
effect Async where
  suspend : {Async} ()  -- yield point, в котором может произойти cancellation

effect Nursery where
  spawn         : (1 body : {Async, eff} a) -> {Nursery, Async} (Task eff a)
  spawnDetached : (1 body : {Async} ()) -> {Nursery, Async} ()

await         : Task eff a -> {Async, eff} a
withNursery   : (1 body : {Nursery, Async} a) -> {Async} a
```

Row-переменные во всех этих сигнатурах auto-lift'ятся общей fresh `e` (см. §3.4). `eff` — явная переменная task-specific effect row, семантически осмысленная, не auto-lifted.

**Кратность `1` у тела — не украшение.** Тело исполняется ровно один раз, и записанная единица масштабирует захваченное им на единицу. Именно поэтому `spawn (processConnection conn)` с ресурсным `conn` проходит без единой дополнительной аннотации (§3.3): захват линейного значения в аргументной позиции разрешён кратностью принимающего параметра. Была бы у `body` кратность `ω`, `conn` уехал бы в `ω` и был бы отвергнут. У `await` кратность не пишется: `Task` — resource-тип, и его биндинг получает `1` автоматически (§3.3).

Ключевые свойства:

- **Scope невидим на surface.** Внутри `withNursery` пользователь вызывает `spawn` как эффектную операцию, никакого явного Scope-аргумента. Scope как resource живёт в handler'е `withNursery`, автоматически cleanup'ится при выходе.
- **Task полиморфен по эффектной row внутренней вычисления.** `Task eff a` при await'е «переносит» эффекты `eff` в вызывающий контекст (`await : Task eff a -> {Async, eff} a`, auto-lifted). Симметрично тому, как `resume` в handler'е сохраняет тип continuation.
- **Task — resource.** Обязательно должен быть либо awaited, либо явно cancelled, либо принят как detached. Untask'нутый Task при drop Scope — cancelled, результат и exceptions игнорируются. Для fire-and-forget с обязательным `()`-возвратом — отдельный примитив `spawnDetached`, где потерянного значения нет по построению.
- **Cancellation через встроенное exception `Cancelled`.** При drop Scope task получает `throw Cancelled` в ближайшей suspend-точке. Ресурсы cleanup'ятся автоматически через resource-механику §3.3. По умолчанию Cancelled не ловится пользовательским кодом — task умирает после cleanup.
- **Ошибки propagate предсказуемо.** Exception в одной task → cancel всех siblings через drop scope → переброс в withNursery-контекст. Аггрегация нескольких одновременных ошибок из разных tasks — открытый вопрос (§10).
- **Cross-thread capability transfer.** Не все эффекты и capabilities переносятся в spawned task. Правило: capability переносится через spawn boundary только если явно помечена thread-portable. Стандартные примеры: `IO`, `SharedAlloc r` (§3.6) — переносятся. `Alloc r` (thread-local region) — не переносится: попытка использовать local `Ref r a` внутри spawn — статическая ошибка. Пользовательские эффекты по умолчанию не thread-portable; для явного opt-in — маркер `@thread-portable` на определении эффекта (стартовая позиция; конкретика — открытый вопрос).

**Пример:**

```adamas
fetchBoth : String -> String -> {Async, IO, Except IOError} (Data, Data)
fetchBoth url1 url2 =
  withNursery (
    let t1 = spawn (fetch url1)
    let t2 = spawn (fetch url2)
    let d1 = await t1
    let d2 = await t2
    (d1, d2))

-- Если fetch url1 бросил IOError:
--   Cancelled инжектится в t2 в ближайшей suspend-точке;
--   ресурсы внутри t2 cleanup'ятся автоматически;
--   IOError перебрасывается наружу withNursery.
```

**Interplay с RC (уточнение к §5.1 вопросу 2).** Стартовая гипотеза для Фазы 5+: при вызове `spawn` компилятор emit'ит код автоматической промоушен-операции для transitively reachable RC-значений из захвата closure — они переходят из local-режима в atomic. Стоимость — единичный traversal на spawn; после этого все операции атомарны. Точечный маркер (тип-уровневый `Shared`) — потенциальная оптимизация, если бенчмарки покажут, что автоматика существенно замедляет типичный код.

**Implementation caveat: cancellation atomicity.** Точка, требующая внимания при реализации в Фазах 4–5. Cancellation инжектится в suspend-точке, но между `acquire` ресурса и биндингом к переменной с известной кратностью может быть небольшое окно, где resource создан, но ещё не отслеживается механизмом автоматического drop. Пример: `let h = openFile path` — если Cancelled прилетит между `openFile` (возвращает handle) и биндингом `h` (регистрирует переменную для cleanup), файл потечёт. Решение — atomicity guarantee: suspend-точки не могут находиться между allocation'ом resource-значения и его биндингом; в терминах реализации это означает, что compiler маркирует такие критические окна как «не-suspend zones», в которых cancellation откладывается до ближайшей безопасной точки. Похожий подход используется в Rust `tokio` (async cancellation happens только на `.await`), в GHC (asynchronous exceptions блокируются в `mask`), в Kotlin coroutines (yield points явны). Стартовая позиция: cancellation допустима **только** на явных `suspend` (включая `await`); прочие эффектные операции неявно не-суспендящие. Это упрощает reasoning для программиста и compile-time проверку safety.

**Открытые вопросы (см. также §10):**
- Аггрегация ошибок из нескольких одновременно упавших tasks (MultiError vs первая-ошибка-выигрывает vs пользовательский handler).
- Как реализовать `race` (первый готовый task выигрывает, второй cancelled) — как встроенный примитив или библиотечно поверх Nursery.

### 5.3 FFI

**Решение:** прямой C ABI как основа. Owned-ресурсы выражаются через `resource` (§3.3), что даёт C++/Rust-style RAII автоматически. Внешние вызовы помечаются эффектом `Foreign` (под-эффект IO).

**Три уровня FFI-support:**

1. **Manual bindings.** Программист пишет `extern` декларации руками:

   ```adamas
   extern "C" fn malloc : Nat -> Ptr
   extern "C" fn free   : Ptr -> ()

   -- Оборачиваем как resource для RAII
   resource CBuffer where
     drop b = free b.ptr
   ```

   Подходит для маленьких библиотек, embedded API, случаев где нужен полный контроль над сигнатурами.

2. **Header parser (bindgen-tool).** Инструмент `adamas-bindgen`, читающий `.h` файлы и генерирующий bindings. Как Rust `bindgen`. Промежуточный вариант для средних библиотек — сотни функций и структур, но не требующие continuous integration с обновляемыми headers.

3. **Direct C interop (долгосрочная цель).** Компилятор понимает C-headers нативно через встроенный C-парсер, никакой промежуточной генерации:

   ```adamas
   import c "dpdk/rte_ethdev.h"
   
   -- Функции и типы из header доступны напрямую как c.rte_eth_rx_burst, c.rte_mbuf, etc.
   ```

   Как Zig `@cImport`. Радикально улучшает UX для systems-программирования с крупными библиотеками типа DPDK, где сотни функций и постоянно меняющиеся headers. Требует встроенного C-парсера в компилятор — значительная work item, но избавляет от целого класса проблем «сгенерил bindings, они устарели, снова генери».

Стартовая цель (Фаза 5) — уровень 1 + 2. Уровень 3 — долгосрочно, если пользовательский спрос это оправдает.

**Взаимодействие с резюме § memory:**

- **С Perceus:** значения, полученные через FFI как `Ptr` — вне Perceus, управляются вручную через `resource`. Значения, переданные из Adamas в C — должны быть либо линейными (полностью «сдаются» в C), либо получить cross-boundary-protocol (обычно deep copy).
- **С регионами (§3.6):** аллокации в C для взаимодействия с C-библиотекой могут идти через отдельный регион с C-совместимой стратегией (обычный malloc/free). Cleanup региона автоматически освобождает все C-объекты.
- **С SIMD (§4.9):** SIMD-типы имеют memory layout, совместимый с C SIMD intrinsics (aligned, fixed-width). Прямой pass SIMD-значений в C-функции работает без обёрток.

**Layered wrapping паттерн.** Реалистичный FFI к крупной библиотеке (DPDK, OpenSSL, Vulkan) строится слоями: (1) raw `extern` bindings — сырые C-функции; (2) resource-wrappers — safe RAII-обёртки над C-объектами (`resource Packet where drop = rte_pktmbuf_free`); (3) batch/collection abstractions — работа с массивами C-объектов (например, `resource PacketBatch (n : Nat)` с partial move-out для redispatch); (4) идиоматический Adamas-API поверх — эффектные операции, интеграция с регионами и SIMD. Стандартные библиотеки для больших C-библиотек публикуются в экосистеме как отдельные packages (`adamas-dpdk`, `adamas-openssl`), не входят в стандартную библиотеку языка.

**Открытые вопросы (см. §10):** правила cross-boundary передачи полиморфных значений; interaction FFI с эффектной системой (может ли C-функция «делать» эффект? как это выразить); детали safety-инвариантов для manual bindings (что компилятор гарантирует, что программист).

## 6. Performance targets

| Сценарий | Target | Reference |
|---|---|---|
| Горячие циклы с линейностью и unboxed numerics | паритет с Rust | Rustc на эквивалентном коде |
| Zero-alloc hot loops с регионами (§3.6) | паритет с C | C с manual arena management |
| Multi-core shared-mempool workloads (§3.6) | паритет с DPDK/tcmalloc | C с lock-free mempool |
| SIMD-heavy код (§4.9) | паритет с C+intrinsics | ISPC / Rust `packed_simd` |
| Типичный бизнес-код с эффектами | 1.5–2x Rust | OCaml 5 baseline |
| Символьно-тяжёлый код | паритет с Rust или лучше | GHC -O2 + 30% margin |
| Direct C FFI overhead | нулевой (uro `Foreign` — маркер типа, не runtime cost) | Zig `@cImport` |
| Старт компилятора | < 100ms cold | Rust hello world |

**Необходимые проходы оптимизации:**
- Inlining (size-based + user hints).
- Specialization / monomorphization implicits.
- Perceus RC optimization (drop reuse).
- Escape analysis для closures.
- Tail call optimization (guaranteed для self-tail).
- Constant folding в т.ч. compile-time evaluation чистых функций.
- SIMD auto-vectorization и intrinsics lowering.

**Зависимости целей от механики.** Target «Символьно-тяжёлый код: паритет с Rust или лучше» опирается на FBIP (§5.1): типичные символьные workloads (интерпретаторы, парсеры, transformer'ы AST) — цепочки функциональных преобразований над деревьями и списками. Без FBIP каждое преобразование = O(n) аллокаций; с FBIP на уникальных инпутах — 0 аллокаций. Обещание паритета с Rust требует, чтобы FBIP реально срабатывал на типичном коде, что программист может проверить через `@fbip` или LSP hint.

## 7. Toolchain

### 7.1 Build system

Единственный канонический инструмент, cargo-inspired:

- Команды: `adamas new`, `adamas build`, `adamas test`, `adamas run`, `adamas check` (type-check only, для быстрой обратной связи), `adamas fmt`, `adamas doc`.
- **Lockfile + воспроизводимые сборки.** Sandboxed macro runtime (§4.6) гарантирует детерминизм compile-time evaluation — сборка одного и того же исходника на разных машинах даёт идентичный результат.
- **Workspace для multi-package проектов** — cargo-style, с shared lockfile.
- **Target selection.** Стартово — native (host triple). Далее с добавлением backends: `--target wasm32-wasi`, `--target gpu-cuda`, etc. Cross-compilation тривиальна благодаря macro runtime isolation — macros не выполняются в target runtime.
- **Build modes.** Debug (fast compilation, checks enabled, minimal optimization), release (максимум оптимизаций включая FBIP reuse, full monomorphization), profile (release + instrumentation для perf analysis).
- **SIMD/target capability configuration.** Через prof-файл проекта: минимальные требуемые SIMD extensions, targeted CPU features. Компилятор emit'ит соответствующие intrinsics или fallback.

### 7.2 LSP-first

LSP-сервер строится одновременно с компилятором, не как afterthought. Используется incremental computation framework (Salsa-style, или собственный поверх). Начиная с Фазы 3 (см. §9), полноценная реализация — Фаза 9.

**Feature-specific LSP capabilities:**

- **Hover для типов.** Полный тип включая auto-lifted row-переменные (§3.4), universe levels (§3.2, если явно интересно), constraints (`when …`, `{Class T} =>`).
- **Effect row display.** Наглядный показ эффектов в hover'ах — какие эффекты требует функция, какие она бросает через exceptions.
- **FBIP hints (§5.1).** Inline hints над функциями: «reuse applies to unique inputs» / «reuse not applicable, allocations expected» / «this Node allocation is reused». Warning в problems panel для ветвей, где reuse структурно возможен, но не применяется.
- **Resource lifecycle visualization.** Highlighting точек, где resource acquired и где cleanup будет вставлен. Полезно для понимания exceptional-exit cleanup поведения (§3.3 × §3.4).
- **Verification proof state (Фаза 4+).** Когда пишется proof-term, IDE показывает текущий goal и context (в духе Coq/Agda). Стартово — базовый text-display, интеграция с уровнем 2 SMT verification — позже.
- **Handler resolution.** При использовании эффекта — навигация к handler'ам в scope, disambiguation для нескольких handler'ов одного эффекта.
- **Region scope highlighting.** При работе с `Ref r a` — визуализация scope региона `r`, где ссылка валидна.

### 7.3 Package manager и content addressing

**Стартово (Фаза 9):** git-based package manager. Зависимости в манифесте — git URL + commit/tag. Никакого centralized registry для начала. Проще для research-стадии, минимизирует инфраструктурные обязательства.

**Долгосрочная цель:** content addressing в духе Unison — модули идентифицируются по хешу содержимого, не имени. Это решает проблему dependency hell на уровне модели данных: две библиотеки, использующие «одну и ту же» функцию, получают её как identical hash, независимо от того, как называется package. Vendored в §9 Фаза 10+.

**Что нужно от языка для content addressing** (закладывается уже сейчас, чтобы не переделывать позже):

- Стабильная normalization AST — два семантически одинаковых определения дают идентичный hash.
- Явные dependencies — модуль знает, от чего именно зависит; изменение зависимости меняет hash транзитивно.
- Deterministic elaboration — macro runtime isolation (§4.6) уже это обеспечивает.

Второе и третье — следствия существующих решений. **Первое требует отдельной работы**, вопреки тому, как это было записано изначально. Обнаружено при реализации NbE (§9 Фаза 1): обратное чтение значений в термы не выполняет η-развёртку, потому что не знает типов, — и `f` и `\x -> f x` при одном и том же типе дают разные нормальные формы, оставаясь конвертируемыми. Нормальная форма при таком обратном чтении — не канонический представитель класса конвертируемости, значит хеш от неё для content addressing не годится. Причин расхождения две, и типизированное обратное чтение (η-длинные нормальные формы, в духе Coq и Lean) закрывает только первую. Вторая — кратность лямбды: конвертируемость её игнорирует (иначе теряется транзитивность, см. decision log), а обратное чтение сохраняет, поэтому `\(1 x) -> f x` и `\(0 x) -> f x` тоже конвертируемы при разных нормальных формах, уже безо всякого η. Значит для content addressing нужны оба шага: типизированное обратное чтение и приведение кратностей лямбд к канону.

Стоимость первого: `quote` начинает требовать тип значения, то есть перестаёт быть чистой функцией от значения. Решать при подходе к Фазе 10+; на само ядро выбор не влияет, поэтому в §9 Фазе 1 сознательно не делается.

### 7.4 Инструменты качества кода

- **`adamas fmt`** — форматтер с opinionated defaults, конфигурация минимальна (в духе `gofmt`, `rustfmt`).
- **Диагностика с самого начала.** Ошибки типа — с образцами кода, suggested fixes где возможно, hints на related концепции. `ariadne`/`miette`-style presentation.
- **Property testing в стандартной библиотеке.** `PropCheck`-style API поверх QuickCheck-подобных generators. Тотальность (§4.7) и pure-функции естественно тестируются.
- **Snapshot testing для type checker'а.** Golden files с ожидаемым output type checker'а — быстро ловит regression'ы в elaboration.
- **Benchmarking framework.** Стандартная библиотека содержит `Bench` module с criterion-style API. Continuous benchmarking для performance-critical оптимизаций (Perceus reuse, SIMD lowering).

### 7.5 Debugger integration

**Стартово (Фаза 6+):** источник-уровневая debugging через DWARF в native binary. Что видит debugger:

- Оригинальные имена переменных, типы (с элаборированными row-переменными).
- Handler stack — для отладки эффектного кода, показывать какой handler активен для каждого эффекта.
- Resource lifecycle events — точки acquire/drop.

**Долгосрочно:** time-travel debugging для pure-функций (детерминистичны), integration с profiling для FBIP hot path visualization.

## 8. Стек реализации

**Host language:** **Rust**.

Обоснование:
- Известен пользователю, не нужно учить параллельно с языком, который реализуется.
- Отличные ADT через enums, exhaustive pattern matching.
- Производительность, предсказуемая память — компилятор не должен быть тормозом.
- Богатая экосистема компиляторных инструментов.

**Конкретные крейты (отправная точка, не догма):**
- Лексер: `logos` или ручной.
- Парсер: `chumsky` или ручной recursive descent (для лучших error messages в долгосрочной).
- Инкрементализация: `salsa`.
- Error reporting: `ariadne` или `miette`.
- Backend: на первой стадии — генерация C, потом LLVM через `inkwell`.
- Property testing: `proptest`.

**Backend targets (текущие и будущие):**
- **Стартово (Фаза 5):** C emit (простой bootstrap), затем LLVM через `inkwell` для нативных target'ов (x86_64, aarch64).
- **Ближайшее расширение (после MVP):** WebAssembly через LLVM WASM target — минимальная дополнительная работа, детали в §4.10.
- **Долгосрочно (отдельный подпроект):** GPU offload через LLVM Offload runtime или SPIR-V — детали в §4.10. Не блокирует основной язык.

Оба альтернативных target'а спроектированы как расширения без изменений в ядре языка (см. §4.10).

**Tooling для разработки:**
- `cargo-insta` для snapshot-тестов type checker'а.
- `cargo-mutants` для mutation testing критических путей.
- Continuous benchmarking через `criterion` + историческое хранение.

### Фаза 1: Ядро QTT (6–9 месяцев)

Самая сложная и рискованная часть — core type theory реализуется полностью со всеми ключевыми решениями.

- **Done:** bidirectional type checking для dependent types — `adamas-core::check`: режимы `infer`/`check`, контекст с типами и кратностями, проверка конвертируемости на границе режимов.
- **Done:** NbE (normalization by evaluation) для definitional equality — `adamas-core`: термы на индексах де Брёйна, значения на уровнях, замыкания, обратное чтение, проверка конвертируемости с η. Кратности присутствуют в представлении (`Pi`/`Lam`) и различают типы функций; учёт использований — следующий срез. Baseline: `normalize` на сложении чисел Чёрча 16+16 — **~3.6 µs**, на цепочке из 256 стрелок без редексов — **~51 µs**, конвертируемость той же цепочки с собой — **~61 µs**.
- Universe hierarchy с **implicit universe polymorphism** (§3.2, Agda/Idris 2 style) — не «пока без UP», сразу с UP, чтобы не переписывать позже. **Done:** обе половины на месте (`adamas-core::meta`). В местах использования аргументы уровня **выводятся** — вместо них подставляются дырки, которые решает проверка конвертируемости. На границе определения нерешённые дырки **обобщаются** в параметры, и их число и есть арность: она выводится, а не объявляется. Дырка, оставшаяся там, где обобщать нельзя (только в теле, не в типе), — отказ, а не молча выбранный уровень.
- **Done:** multiplicities (QTT): erased/linear/unrestricted — учёт использований в `check`. Снаружи проверка вызывается при `σ = 1` (рантайм) или `σ = 0` (стёртый фрагмент, где живут все типы); переменная расходуется на `σ`, аргумент проверяется при `q · σ`, поэтому внутри рекурсии `σ` пробегает всё полукольцо. Это вплавленная форма правила Аткея, где `σ ∈ {0, 1}`, а масштабирование применяется к вектору использований (`Γ + q · Δ`); формы эквивалентны, поскольку полукольцо коммутативно и умножение дистрибутивно над сложением. Отсюда напрямую: стёртый аргумент ничего не тратит, стёртая переменная в рантайм-позиции отвергается, `1` остаётся аффинной. Erasure как проход по core — вместе с кодогенерацией (Фаза 6).
- Базовые индуктивные типы (Nat, List, Vect). **До них `Type 0` необитаем**: `Pi` живёт в `max` уровней своих частей, и опуститься до нуля неоткуда.
- Pattern matching elaboration в case tree с coverage checker'ом (§10 вопрос 7 — Idris 2 style).
- Терминация: `@total` проверка структурной рекурсии и exhaustiveness.

## 10. Открытые вопросы

Эти вопросы не решены и требуют отдельного обсуждения с появлением контекста.

1. **Кумулятивность универсумов.** Использовать ли cumulative subtyping (`Type i ≤ Type j` при `i ≤ j`)? За — меньше шума в типах библиотечного кода. Против — усложняет definitional equality, замедляет elaboration (Lean 4 специально отказался). Стартовая позиция: без кумулятивности, добавлять только если эргономика будет страдать.

2. ~~**Структура уровневых выражений.**~~ **Закрыт (см. §3.2, §9 Фаза 1).** Уровни — алгебраические выражения `zero`/`suc`/`max`, нормальная форма — «max атомов со смещениями плюс константа». Решающая процедура равенства **корректна и полна**: нормальная форма является полным инвариантом, что проверяется property-тестом против независимого вычисления уровня по подстановке. Неполнота, из-за которой вопрос оставался открытым, целиком приходилась на `imax`, а он убран вместе с приведением §3.2 в соответствие с предикативностью (decision log 2026-08-22).

3. **Раздельные иерархии для `Type` и `Effect`.** Эффекты — row-структура, не «значения». Стартовая гипотеза: раздельные миры. Подтвердить или опровергнуть после реализации §3.4.

4. **Scoping coherence implicits.** Как именно работают конфликты при scoped instances? Какие правила disambiguation? Частично прояснено: инстансы могут быть именованными (`instance sumMonoid : Monoid Int where …`), в неоднозначном контексте выбираются через `using sumMonoid`. Явные module-параметры (§3.5) и implicit class-разрешение — независимые механизмы, не пересекаются. Остаются вопросы: правила приоритета анонимных инстансов, правила видимости при импорте модулей, взаимодействие с `coherent` маркером.

5. **Effect inference vs explicit annotation.** Частично закрыт: на public API эффекты обязательны, отсутствие `{...}` в возвращаемом типе означает pure (см. §4.1). Остаётся вопрос: выводятся ли эффекты в локальных `let`-биндингах, лямбдах и private функциях, или там тоже требуется явное указание?

6. ~~**Синтаксис multi-shot handler'а.**~~ **Закрыт (см. §3.4, §4.1).** Отдельное keyword `handleMulti expr with …` параллельно с `handle expr with …`. Компилятор автоматически выбирает кратность `resume` по keyword'у (single-shot → 1, multi-shot → ω). Различие видно на месте использования.

7. **Pattern matching на зависимых типах.** Реализовать через elaboration в primitive J/case-tree, или через top-level coverage checker? Idris 2 идёт первым путём, Agda — вторым. Стартовая позиция: Idris 2 style (elaboration в case tree с сопутствующим coverage checker'ом), потому что coverage-задачи вроде «двухаргументный zipWith на векторах одинаковой длины исчерпан двумя ветвями» естественнее решаются во время elaboration, а не отдельным проходом. Подтверждается или пересматривается по мере реализации.

8. **RC-режим и concurrency.** Как именно эффекты передачи данных между потоками (`Async`, `Channel`, `spawn`) триггерят промоушен значений из неатомарного local-режима в atomic shared? Стартовая гипотеза (§5.2): автоматический promotion для transitively reachable значений на границе `spawn`. Открыты подвопросы: (а) корректно ли работать transitive traversal при глубоко вложенных структурах без deep-copy; (б) на каком этапе (Фаза 5+) вводить biased RC и по каким метрикам решать; (в) нужен ли также точечный маркер `Shared` в типе как escape hatch для case, где автоматика чрезмерна.

9. **Циклы в Perceus.** Какой механизм для разрыва циклов в графе reference counting? Стартовая позиция — weak references как явная конструкция; открыт вопрос эргономики (типичные ли use case всё ещё удобны) и нужно ли дополнительно trial deletion как fallback.

10. ~~**Module functor синтаксис.**~~ **Закрыт (см. §3.5, §4.8).** Function-call syntax для applikation (`OrderedMap IntOrd`), signature refinement через `with type`, параметры по умолчанию explicit с опциональным implicit-режимом.

11. ~~**Numeric literal resolution.**~~ **Закрыт (см. §4.3).** Три класса преобразования — `FromNat`, `FromInt`, `FromFloat`, — по синтаксической форме литерала. Литерал элаборируется в вызов соответствующего преобразования, инстанс выбирается по ожидаемому типу из контекста. При отсутствии контекстных ограничений — default на `Int` (для FromNat/FromInt) или `Float` (для FromFloat) с warning'ом. Строгий режим (без default) — опция компилятора.

12. **Эффект `IO` — встроен или библиотечен?** Если библиотечен, как реализовать "primitive" эффекты типа `print`?

13. **Strictness и data structures.** Структуры данных строгие по умолчанию или лениво построенные через `Lazy`? Например, `List a` — это `Nil | Cons a (List a)` (тогда вся структура strict) или `Nil | Cons a (Lazy (List a))` (тогда возможна потоковая обработка из коробки)?

14. **Mutually recursive types и termination.** Какие именно правила позитивности для индуктивных типов?

15. ~~**Resource cleanup и multi-shot continuations.**~~ **Закрыт (см. §3.4).** Resource-типы не допускаются в scope `handleMulti`-выражения; компилятор проверяет статически. Мотивация: cleanup несовместим с многократным вызовом continuation. При необходимости смешать backtracking с ресурсами — выделить resource-работу в отдельную single-shot секцию.

16. **Аггрегация ошибок в concurrent code.** Что происходит, когда несколько параллельных tasks одновременно бросают exceptions? Варианты: (а) MultiError, инкапсулирующий все ошибки — тип-система должна это поддержать, вероятно через специальный тип-обёртку в `Except`; (б) первая ошибка выигрывает, остальные логируются; (в) пользовательский handler на уровне `withNursery`, задающий политику агрегации. Стартовая гипотеза не выбрана — решать по конкретным use case, начиная с (б) как минимально работоспособного.

17. **`race` и подобные примитивы concurrency.** Как реализовать «первый готовый task выигрывает, остальные cancelled»? Как встроенный примитив (проще семантика, но расширение runtime) или библиотечно поверх `Nursery` + низкоуровневый `awaitAny` (более гибко, но нужен корректный `awaitAny`, а он требует internals)? Аналогично для `select`, `merge` и других comb'инаторов Trio/tokio.

18. **Module inclusion.** Аналог OCaml `include Foo` — переносит все члены Foo в текущий модуль. Полезно для extension-паттернов (расширить готовый модуль дополнительными функциями с сохранением исходного API). Добавляет сложности name resolution (потенциальные конфликты имён при inclusion нескольких модулей), взаимодействие с приватностью, конкретные правила override'а. Стартовая позиция: не поддерживать, обходиться композицией через explicit re-export. Пересмотреть, если типичные библиотечные паттерны без inclusion становятся многословны.

19. **Macro runtime: переход от интерпретации к bytecode VM.** Стартовая позиция (§4.6) — macro интерпретируется прямо в компиляторе над Adamas AST, ограниченным до pure-подмножества. Долгосрочно — компиляция в bytecode isolated VM (Zig-comptime-like). По каким метрикам решать переход: длительность macro-execution в типичных сборках (порог? 100ms на macro? 1s суммарно?), сложность/размер библиотечных macro-утилит (когда interpret-overhead становится существенным), реальные пользовательские жалобы. Возможно, никогда не понадобится — интерпретации хватит для research-прототипа.

20. **Формальный критерий `@fbip`-совместимости.** Что именно проверяет компилятор при `@fbip`? Стартово (§5.1): совпадение формы конструкторов исходной и результирующей структуры в pattern-match-ветвях + отсутствие структурно-возможных, но не применённых reuse-точек. Требуется публично документируемый набор правил, чтобы программист мог reason о том, пройдёт ли его функция проверку до написания. Особые случаи: mutually recursive types, GADTs, зависимо-типизированные конструкторы. Возможно, спецификация будет уточняться по мере обнаружения corner case'ов.

21. **LSP hints для FBIP-статуса.** Как именно IDE показывает FBIP-статус функции без `@fbip`? Inline hint над сигнатурой («reuse applies to unique inputs»)? Highlight в теле функции («this Node allocation is reused»)? Warning в problems panel для ветвей, где reuse не применяется? Требует прототипирования с реальным LSP.

22. **Явная закрытая row в сигнатуре функции.** Auto-lift row-переменных (§3.4, §4.2) делает все row в сигнатурах функций открытыми. Стартово это устраивает — реальных use case для «функция требует ровно этот набор эффектов/полей, ни больше» не выделено. Если такие случаи появятся, потребуется явный маркер закрытости — синтаксис вроде `{IO}!` или `strict {IO}`. Пока не вводим.

23. **Эргономика вложенных handler'ов при нескольких Except.** Обработка нескольких однотипных эффектов (`{Except IOError, Except ParseError, Except EvalError}`) требует либо цепочки вложенных `handle @T … with …` (многословно), либо цепочки `try` в prelude (тоже многословно из-за вложенных Result-типов). Замечено на capstone-сценарии (mini-interpreter) — не блокирует, но некомфортно. Варианты: (а) специальный синтаксис mult-handle типа `handle prog with @A ... | @B ... | @C ...`; (б) top-level `catch`-конструкция с несколькими ветками по типам; (в) стандартный prelude-комбинатор для composition Except-handler'ов. Не выбрано — решать после накопления реальных пользовательских паттернов. Уточнено: при row-как-мультимножестве (§4.1) такая сигнатура типизируется корректно, а проблема сводится к эргономике адресации — какой из одноимённых handler'ов имеется в виду. Общее решение — named instances в духе Koka (`named effect`), при котором handler порождает свежее имя; отвергнуто стартово, потому что помещает термы в метки row и тем вызывает проверку конвертируемости при унификации. Для мутабельности проблема снята иначе — параметризацией по идентичности региона (§3.6), а не по типу.

24. **Портируемость регионов между backend'ами.** `Arena` через malloc, через mmap, через специфический OS mechanism (например, jemalloc arenas) — разные trade-offs по производительности и портируемости. Стартово — один mainstream backend (malloc-based) для Arena, Pool, StackAlloc. Как параметризовать пользовательские стратегии для разных targets? Через target-conditional import? Через feature flags?

25. **Регионы и concurrency: детали cross-thread capability transfer.** Базовая политика (§3.6, §5.2): thread-local `Alloc r` не переносится через spawn, thread-safe `SharedAlloc r` переносится. Открыто: (а) как именно compiler маркирует эффекты как thread-portable — стартовая гипотеза «маркер `@thread-portable` на определении эффекта»; (б) правила migration local → shared, если программа сначала создаёт local регион, а потом решает шарить (запретить, или разрешить через явную операцию `promote`); (в) обратная миграция (shared → local для оптимизации после fork/join) — как выразить и есть ли смысл.

26. **Thread-safe allocator implementation strategies.** Конкретные механизмы для стандартных `SharedArena`/`SharedPool`: (а) `SharedArena` — atomic CAS на bump pointer'е (простое, но alloc contention) vs per-thread caches (сложнее, но масштабируется); (б) `SharedPool` — global lock-free freelist vs per-thread caches с fallback (в духе tcmalloc/jemalloc); (в) safe drop под конкурентным использованием — hazard pointers, epoch-based reclamation, или требование quiescence перед drop через withNursery join. Стартовый выбор — по мере реализации и benchmarks.

27. **User-defined AllocStrategy composability.** Пользователь пишет свою стратегию через module type `AllocStrategy`. Могут ли стратегии композироваться (например, Arena внутри Pool)? Правила статического расчёта размера региона? Interaction с debugging (profiling per-strategy). Аналогичный вопрос для `SharedAllocStrategy` — thread-safe composition сложнее.

28. **SIMD width mismatch policy.** `Vec 16 Float` на platform с 128-bit SIMD (SSE) требует loop unrolling в 4 native-операции; на AVX-512 — одна native-операция. Правила выбора: (а) compile-time error если mismatch (строго); (б) automatic unrolling с warning (прагматично); (в) target-specific attribute request от пользователя. Стартово (б), точные пороги — определять по бенчмаркам.

29. **SIMD target-specific optimization request syntax.** Как пользователь запрашивает specific target capabilities? `@simd(min_width=256)` на функции? Module-level pragma? Compile-time capability query внутри кода?

30. **FFI cross-boundary для полиморфных значений.** Как передать `List Int` в C-функцию? `Option Int`? Требует cross-boundary marshalling протокола или ограничения FFI на monomorphic simple типы. Стартовая гипотеза: FFI ограничена типами с известным C-layout (Int, Float, Ptr, resource-типы над Ptr, C-совместимые записи), полиморфные типы — только через explicit marshalling.

31. **FFI и эффектная система.** Может ли C-функция «делать» эффект? Например, callback из C, вызывающий Adamas-функцию с эффектом? Как это выразить в типе `extern` декларации? Стартовая позиция: `extern` функции считаются `{IO}` по умолчанию; для callback-паттернов — специальный extension, если понадобится.

32. **Верификация уровня 2: timing перехода к SMT.** §3.7 разделяет верификацию на уровень 1 (proof-terms native, стартово) и уровень 2 (SMT-backed refinements, долгосрочно). По каким метрикам решать переход? Кандидаты: (а) объём boilerplate arithmetic proofs в реальном user-коде становится существенным препятствием; (б) появляется external contributor с formal methods expertise, готовый нести SMT-integration работу; (в) пользовательский спрос — реальные жалобы, а не гипотетический комфорт. Стартовое решение: не переходить, пока не сработает (б) или сильный (а).

33. **Scope tactics library.** Для уровня 1 верификации (proof-terms) полезны utility-функции: `rewrite`, `induction`, `cong`, `symmetric`, `transitive`. Минимальный набор в prelude или полноценная tactic library в отдельном модуле? Полноценная — большая работа (Coq `Ltac` — годы разработки). Минимальный — 10-15 функций, покрывающих типичные patterns. Стартово — минимальный, расширять по мере накопления pain'а.

34. **Взаимодействие верификации с эффектами.** Как рассуждать о свойстве эффектной функции? Например, «функция, читающая файл, гарантированно возвращает non-empty result»? Варианты: (а) верифицировать через handler-based semantics (свойство сохраняется при any semantically-valid handler); (б) вводить отдельный logical framework для effectful reasoning (в духе separation logic для monadic code); (в) ограничить верификацию pure-функциями стартово, effectful — позже. Стартовая гипотеза (в) — для research-прототипа достаточно, effectful reasoning — advanced topic.

35. **Полный список restrictions для `@offload`-функций (§4.10).** Стартово: только pure или offload-совместимые эффекты, только Primitive типы + Vec + региональные Ref, без multi-shot, без Nursery. Что ещё? Restrictions на recursion depth (важно для GPU stack)? На indirect calls (проблема для GPU indirect branches)? На closure captures? Требует конкретной проработки при начале реализации GPU backend.

36. **Interaction offload-функций с эффектной системой.** Какие эффекты допустимы внутри `@offload gpu` функции? Явно нужны: `GPUMem g` (аллокация в GPU memory), `GPULocal` (per-thread state), возможно `GPUSync` (barriers, atomics). Что делать с обычным `IO` — запретить как unsafe? Разрешить через специальный «offload-IO» с ограничениями? Стартовая гипотеза: полный запрет обычных host-эффектов внутри offloaded кода, только GPU-specific эффекты.

37. **Heterogeneous computing coordination.** Одна программа с частью на CPU, частью на GPU: как выражается data transfer (host → device, device → host)? Автоматически по типу (`Ref g a` в CPU-контексте инициирует device→host copy)? Явно через `copyToDevice`/`copyFromHost`? Разграничение через эффекты (`{DeviceTransfer g}`)? Ожидается — комбинация: явные copy-точки, но с helper'ами в стандартной библиотеке.

38. ~~**Модель мутабельности.**~~ **Закрыт (см. §3.3, §3.6, §4.1).** Ось — не mutable/immutable, а aliased/unaliased. Неалиасованная мутация семантически невидима и эффекта не требует: `unique data` (статическая неалиасованность), FBIP §5.1 (обнаруженная в рантайме). Алиасованная наблюдаема и идёт через эффект `Alloc r` с параметризацией по идентичности региона. Сабтайпинга нет — переход через `freeze`. «Мутабельный» не совпадает с «кратности 1»: unique-тип влечёт кратность 1 у всех связываний, обратное неверно. Синхронизация через границу потока для unique-значений не требуется (уникальность исключает разделение, unique-типы вне RC-протокола); для регионов — см. вопрос 40. Граница с Perceus — там же, где §5.1 провёл её для линейных значений. Заимствования в языке нет и не планируется: разделяемое чтение закрывается `freeze`, скоупленная мутация — handler'ом региона, дизъюнктное разрезание — линейным `splitAt`; не закрывается только ссылка внутрь структуры (`&mut self.field`, итератор с мутируемыми элементами), для чего используется индексная адресация внутри региона.

39. **Полнота решения ограничений на уровнях.** Вывод уровней (§9 Фаза 1) решает паттерн `?m ~ l`, где `?m` не встречается в `l`, плюс снятие общих `suc` с обеих сторон — конструктор инъективен, поэтому `suc ?m ~ 3` однозначно даёт `?m ~ 2`. Не решается дырка под `max`: `max ?a u ~ v` не имеет единственного решения, а угадывать нельзя — неверная догадка принимает некорректную программу, тогда как отказ лишь отвергает корректную. Насколько часто такие ограничения возникают на реальном коде, станет видно на prelude: пока сигнатур, которые их порождают, попросту нет. Варианты, если помешает: откладывать нерешаемые ограничения до конца проверки определения (Agda), решать неравенства вместо равенств (Lean), либо требовать явной аннотации в этих позициях. Не путать с §10 вопросом 2 — тот был про *равенство* уровней и закрыт: нормальная форма полна. Здесь вопрос про *решение уравнений*, а это другая задача.

40. **Регионы и concurrency: мутабельные `Ref` в shared-регионах.** §3.6 гарантирует thread-safety **аллокатора** (`SharedAllocStrategy`), но не **ячейки**, а `SharedAlloc r` переносится через `spawn`. С добавлением `write` это открывает гонку данных: два воркера пишут в один `Ref`. Варианты: (а) `Ref` в shared-регионе read-only после инициализации; (б) мутация только через `Atomic`/`Mutex`-обёртку; (в) отдельный тип `SharedRef` со своим набором операций. Не блокирует Фазы 1–5 (однопоточный рантайм); блокирует Фазу 7. Смежно с вопросами 25 и 26.

41. **Полиморфизм по кратностям.** Для контейнеров задача снята дефолтом кратности полей (§4.1). Остаётся для функций, полиморфных по способу использования аргумента: `map`, применённый к линейной функции, требует либо дублирования сигнатур, либо квантификации по элементам полукольца. Понижено до долгосрочного. Отмечено, что цена ниже, чем у отвергнутых атрибутов уникальности: полукольцо {0, 1, ω} конечно, поэтому семантическое равенство выражений над кратностями разрешимо исчерпывающей подстановкой (3ⁿ), и канонические нормальные формы сохраняются — в отличие от уровней, где бесконечность домена и делала `imax` неразрешимым. Триггер к пересмотру: дублирование комбинаторов в prelude становится измеримой болью.

Требуется явное решение: убрать `imax` из §3.2 и из `Level` — или пересмотреть предикативность и ввести отдельный импредикативный сорт со всеми его ограничениями. (1) **Кратность суждения `σ ∈ {0, 1}`**, а не `{0, ω}`: правило переменной выдаёт использование `σ`, применение проверяет аргумент при `q · σ`. При `σ = 1` линейная переменная, использованная дважды, даёт `1 + 1 = ω` и отвергается; при `σ = 0` (весь фрагмент типов) всё схлопывается в ноль, и проверки кратностей выполняются тривиально — именно поэтому стёртая переменная свободно используется в типах и не может быть использована в рантайме. (2) **Кратность лямбды проверяется в `check` и игнорируется в `conv`.** Это не рассогласование: конвертируемость обязана её игнорировать ради транзитивности через η (запись от 2026-08-21), а `check` — единственное место, где аннотация на лямбде вообще что-то значит, иначе поле было бы декоративным. (3) **`Term::Let` получил кратность.** Без неё `let 1 h = openFile … in …` невыразим, а добавление поля задним числом — тот же дорогой ретрофит, из-за которого кратности сразу попали в `Pi`. (4) **`let` вводится как определение, а не как переменная**: в окружение кладётся значение, поэтому тип тела не может сослаться на связывание, которого снаружи уже нет. (5) **Ошибки ядра без спанов.** Вопрос был поднят ретроспективой warm-up'а. Решение: ядро отвечает «почему», элаборатор (Фаза 2) — «где», потому что он обходит поверхностный терм и в момент отказа держит его спан. Отвергнуто: спаны в узлах core (утяжеляют горячий путь `NbE` ради информации, которая уже есть у вызывающего). (6) **`Type 0` необитаем до появления индуктивных типов** — следствие предикативного правила `Pi`; зафиксировано в §9 и в тестах, чтобы не выглядело дефектом. Открытых вопросов не добавлено; вопрос про `imax` относится к §10 вопросу 2 и требует ответа до Фазы 2.

- **2026-08-22:** §3.2 / §10 — **`imax` убран, противоречие внутри §3.2 закрыто в пользу предикативности.** Было: раздел одновременно выбирал предикативную иерархию, посвящая отдельный абзац отказу от импредикативности, и перечислял `imax` среди операций над уровнями. Механизм, делающий это безопасным у Lean, — `Sort 0` как `Prop` с иррелевантностью доказательств и урезанной элиминацией — §3.2 явно отвергает («двухсортная система Coq … плохо сочетается с эффектами и линейностью»). Замена — universe polymorphism, уже выбранный §3.2 и запланированный §9 Фазой 1. Второй мотив для `Prop` — стирание доказательств — закрыт кратностью `0` в QTT (§3.3) и уже реализован. - **2026-08-23:** §9 (Фаза 1) / §3.2 — третий срез ядра: глобальный контекст и определения верхнего уровня (`adamas-core::sig`). До него ядро знало только замкнутые термы сами по себе; ни universe polymorphism, ни индуктивные типы без верхнего уровня не выражаются, а data-декларация — тоже определение, поэтому контекст нужен раньше них в любом случае. Решения. (1) **Universe polymorphism сначала явная.** Параметры уровня принадлежат определению, аргументы пишутся в месте использования (`Term::Const(name, levels)`). Тот же порядок, что с кратностями: §9 предостерегает от ретрофита *представления*, а вывод аргументов ложится сверху и представление не меняет. Проверяется выход параметра за объявленную арность — иначе определение молча зависело бы от переменной, которой у него нет. (2) **δ-редукция ленивая, с быстрым путём.** `eval` определения не разворачивает вовсе; конвертируемость сначала сравнивает как есть (совпали голова и аргументы уровня — достаточно сверить спайны, тело не нужно) и разворачивает только при неудаче. Обратный порядок — разворачивать при вычислении — даёт экспоненциальный рост на арифметике и раздувает нормальные формы и сообщения об ошибках телами всех определений. Важная тонкость: неудача быстрого пути **не** означает неравенство (`f a` и `f b` равны, если `f` игнорирует аргумент), поэтому откат к развороту обязателен, а не факультативен. (3) **Голова нейтрали стала двухвариантной** (`Head::Local | Head::Global`): постулат — определение без тела — застревает так же, как локальная переменная, и без этого его нечем представить. Аргументы уровня входят в голову, поэтому `Box{0}` и `Box{1}` — разные типы. (4) **Определения ацикличны по построению**: проверка идёт против сигнатуры без добавляемого имени. Это даёт завершаемость δ-разворота без отдельного счётчика. Ограничение снимается вместе с проверкой тотальности (§9, `@total`), когда появится рекурсия. (5) **Кратность у определения ограничена `{0, ω}`.** `1` означала бы «использовать не более одного раза на всю программу», а такого учёта нет и не планируется; линейное определение отвергается с явной ошибкой, а не принимается с бессмысленным значением. `0`-определение (доказательство, тип) в рантайм-позиции отвергается локально — вектор использований тут не при чём, глобалы в контексте места не занимают. (6) **`Ctx` получил ссылку на сигнатуру и время жизни.** Альтернатива с `Rc<Signature>` отвергнута: контекст пересоздаётся на каждом связывании, а сигнатура на время проверки одного терма неизменна, так что ссылка дешевле и честнее. - **2026-08-23:** §3.3 / §10 / §11 — **замыкания над линейными значениями: правило scope-bound**. Поднято на peer-review: спецификация не отвечала, какая кратность у замыкания, захватившего `1`-значение, что происходит при уничтожении невызванного замыкания и можно ли положить такое замыкание в структуру. При разборе вопрос сузился. QTT закрывает его сам почти везде: кратности живут на связывании, масштабирование учитывает захват автоматически, и вся аргументная позиция (`withFile`, `spawn`, любой колбэк) работает без единой дополнительной аннотации — «сколько раз применяется замыкание» уже записано в кратности параметра принимающей функции. Незакрытыми оказались ровно две позиции, у которых кратности нет: возврат из функции и поле конструктора. Принято: **замыкание над связыванием кратности `1` — scope-bound**; применяться и передаваться аргументом может, стоять в позиции возврата и в поле конструктора — нет; параметр кратности `1` функционального типа наследует ограничение внутри вызываемой функции; проверка локальна для тела функции. **Исключение — поле resource-типа**, что превращает запрет в принцип: захваченный ресурс покидает свой scope только внутри сущности с деструктором. `spawn`, кладущий тело в `Task` (resource по §5.2), проходит без специальных оговорок. **Следствие:** деструкторов у замыканий не заводим, и вопрос о невызванном замыкании снимается по построению — замыкание не переживает scope захваченного ресурса, ресурс закрывается собственным scope-exit на всех путях. Под запрет из реального кода попадают фабрики вида `mkLogger : (1 h : File) -> (String -> {IO} ())`; отвергаются заслуженно, поскольку в типе такой функции нет ответа, кто закроет файл. Отвергнута кратность на стрелке (`A ->{1} B`, Linear Haskell): работоспособна, покупает фабрики замыканий над ресурсами, но требует второй аннотации на стрелке, то есть расширения ядра — прямое нарушение инварианта §3.3 «resource реализуется как surface-фича поверх готового ядра без его модификации»; первое же кернел-расширение из этой области обесценило бы инвариант для всех последующих. Сами фабрики при этом не выглядят нужными: их каноническая форма — аргументная позиция либо явная resource-обёртка. В §11 добавлена ссылка на Osvald et al. 2016 (second-class values) как на формализацию правила. В §10 добавлен вопрос 38 (модель мутабельности) — он остаётся открытым, но частично предопределён этим решением. **Требует проверки по реализации:** утверждение о масштабировании контекста в аргументной позиции выведено из формулировки Аткея, а не из кода ядра; прогнать по правилу применения (`adamas-core`) перед тем, как считать §3.3 закрытым.

- **2026-08-23:** §4.1 — **группирующие инстансы**. Поднято как следствие пересмотра §4.3, где операции разводятся с законами (`Add`/`Mul`/`Neg`/`Div` без законов, `Ring`/`Field`/`Approximate` надстройками с законами) ради того, чтобы `Float` не объявлялся кольцом; правка §4.3 идёт отдельно. Разведение делает объявление числового типа делом четырёх-пяти классов вместо одного. При разборе исходная оценка «стена boilerplate» оказалась завышенной: повторяется только шапка `instance … T where`, порядка трёх лишних строк на тип при десятке числовых типов в экосистеме. Настоящая цена не в строках, а в том, что автор инстанса обязан знать, в каком классе живёт каждый метод — знание, которого `Num`-конгломерат не требовал; синтаксис группировки вида `instances T where …` экономил бы только шапки и этой цены не снимал бы. Принято: тело `instance C T where` принимает методы любого транзитивного суперкласса `C`; недостающие инстансы синтезируются в той же точке; конфликт с уже видимым инстансом суперкласса — ошибка, а не переопределение; синтезированные инстансы анонимны, именованные пишутся отдельно; коллизия имён методов из двух классов замыкания требует квалификации. Эргономика хаскелевского `Fractional` при сохранённой стратификации законов: `sumR : {Ring a} => …` по-прежнему отвергает `Float`. Существенно, что расщепление классов и группировка ортогональны — первое отвечает на вопрос, что значит ограничение, второе на вопрос, как записывается инстанс. **Контекст синтезированных инстансов наследуется целиком**, минимальный не выводится: следствие — `instance {Ring a} => Ring (Complex a)` не даёт `Add (Complex Float)`, и полиморфные инстансы с разными требованиями суперклассов расписываются вручную. Отвергнут вывод минимального контекста из тел методов: удобнее в коде с обёртками над числами, но контекст публичного инстанса перестаёт быть написанным в исходнике и меняется при правке тела метода — та же уступка, от которой §4.1 уже отказалась для эффектов на публичном API. Открытых вопросов не добавлено.

- **2026-08-23:** §4.3 / §4.4 — **операции разведены с законами**. Поднято на peer-review. Было: `(+) : {Ring a} => a -> a -> a`, то есть оператор привязан к классу, декларирующему ассоциативность и дистрибутивность, при том что `Float` этим законам не удовлетворяет. При разборе выяснилось, что причин две и они разного веса: NaN ломает `Eq`/`Ord` (тотальность сравнения, `x == x`), а ассоциативность ломает округление — `(a + b) + c ≠ a + (b + c)` на конечных числах без всяких особых значений, то есть никакое подмножество IEEE-носителя кольцом не станет. Стало: операторные классы `Add`, `Mul`, `Neg`, `Div` без законов; `Ring`/`Field` надстраиваются через `when` и добавляют нейтральные элементы вместе с законами; `Approximate` — параллельная надстройка для плавающей точки, законов не заявляющая. Оператор `+` работает на обоих, и ни в одном месте не написано, что сложение флоатов ассоциативно. Побочный выигрыш: `sumR : {Ring a} => …` теперь **не** типизируется на `Float`, то есть функция, корректность которой опирается на ассоциативность (параллельная редукция, переупорядочивание в оптимизаторе), сама себя защищает от плавающей точки; раньше она молча принимала `Float` и молча давала другой ответ при другом порядке свёртки. Сопутствующие решения. (1) **`Eq`/`Ord` у `Float` остаются, но по семантике IEEE-754 `totalOrder`** — побитовой: `nan == nan` истинно, `0.0 /= -0.0`; это законные инстансы, `Float` годится ключом `Map`. IEEE-сравнение переезжает в `ieeeEq`/`ieeeLt` внутри `Approximate`. Побочно `if x < threshold` перестаёт молча проваливаться на NaN. (2) **Второй примитивный float-тип не заводится**; `NonNaN Float` — библиотечный newtype в `Data.Float`, будущий refinement-тип уровня 2 (§3.7). Отвергнуто «Float с NaN и почти-Float без него» как два примитива: покупает законный `Ord`, который уже получен через `totalOrder`, не покупает законное кольцо, и стоит параллельного числового мира вопреки логике §2.3 про несовместимые String-типы. (3) **`Nat` не получает `Ring`** (нет `Neg`), **`Int` не получает `Div`** — целочисленное деление усекает и частично, уезжает в `Data.Int` как `divMod`/`quotRem` с `Option`. (4) **`Semigroup` намеренно не связан с `Add`**: первый заявляет ассоциативность, второй нет. Цена: новый числовой тип затрагивает четыре-пять классов вместо одного, что закрывается группирующими инстансами (§4.1, отдельная запись). Отвергнуто: оставить законы у `Ring` рекомендательными (прямое нарушение §2.1 «честный тип» — класс, чьи законы не выполняются, бесполезен для рассуждений и опасен для оптимизаций); отдельные операторы `+.`, `*.` в духе OCaml (налог на каждое выражение с плавающей точкой, платится в системном коде). §4.4 приведён в соответствие: комментарий у арифметических операторов и список классов prelude.

Стало: перед снятием `suc` уровни приводятся к нормальной форме — она канонична и полна после отказа от `imax`, поэтому `max (suc ?l) (suc ?l)` сводится к `suc ?l`. На действительно неоднозначные случаи это не влияет, что закреплено парным тестом: `max ?a ?b` по-прежнему не решается. (2) **Обобщение не было покрыто свойствами** — десять unit-тестов и ни одного property, при том что ключевой инвариант уже был сформулирован словами в комментарии к `generalization_preserves_checkability`: обобщённая форма обязана проходить проверку заново, и держится это только тестом, потому что в рабочем пути повторной проверки нет. Добавлены два property, оба проверены мутациями: обобщённая форма проверяется при любой форме типа, и параметры плотно занумерованы `0..arity`. Генератор порождает не произвольные термы (те почти никогда не типизируются), а вложенные `Pi` над универсумами, стоящими на дырках из общего набора, поэтому в выборку попадают и повторяющиеся дырки. (3) Типографика новых модулей доведена до ASCII. Открытых вопросов не добавлено.

- **2026-08-24:** §3.3 / §3.6 / §4.1 / §4.2 / §4.4 / §10 — **модель мутабельности закрыта**. Разбор §10 в.38 шёл в три захода, каждый следующий сдвигал предыдущий, поэтому фиксируется итог, а не траектория. (1) **Линейность ≠ уникальность.** Кратность `1` ограничивает потребление функцией, а не число ссылок на значение: ω-значение свободно затекает в `1`-параметр (ω·1 = ω). Поэтому подвопрос в.38 «совпадает ли мутабельный с кратностью 1» имеет ответ «нет», а механизм «мутабельность = линейность + FBIP» неверен. Введён `unique data` — surface-маркер на декларации, дающий связываниям кратность `1` автоматически; ω-связываний такого типа не существует, поэтому дыра закрыта отсутствием предмета, а не проверкой. Констрейнт `Shareable` не нужен: полиморфная инстанциация безвредна, ловится только попадание в ω-позицию. `resource T` ≡ `unique data T` + `drop` — факторизация, а не новый механизм. (2) **Рассмотрен и отвергнут кернел-вариант** (атрибуты уникальности Clean с coercion unique → shared): заводит первую решётку подтипов вопреки §3.4/§4.2 и лишает нормальную форму статуса полного инварианта — свойство, ради которого удалялся `imax` и на котором держится §7.3. Комбинация QTT + uniqueness + dependent types никем не реализована и могла бы быть исследовательским вкладом; цена признана перевешивающей. (3) **Правило «тип с unique-полем сам обязан быть unique» введено и тут же отменено** как лечение симптома. Настоящая причина утечки — дефолт кратности полей конструкторов, который был `ω` и фактически неверен: конструктор использует аргумент ровно однажды. **Дефолт изменён на `1`**; параметры функций остаются `ω`. Асимметрия обоснована: кратность описывает использование принимающей стороной, и для конструктора оно известно. Прецедент — Linear Haskell. Обычный код изменения не замечает; на unique-типах даёт правильное поведение вместо запрета и позволяет `withMut : (1 arr : Array a) -> … -> {e} (Array a, b)`. В prelude добавлен `Ur` для обратного случая. (4) **Row переопределён как scoped multiset.** Найдено на сигнатуре `foo : a -> b -> {Mut a, Mut b} …`: при row-как-множестве подстановка `a := b` схлопывает дубликат, и число handler'ов перестаёт соответствовать числу эффектов — то есть подстановка не сохраняет типизацию. Теория та же (Leijen 2005), взята была её упрощённая версия; Koka допускает дубликаты по той же причине. Побочно уточнено §4.2: базовая операция row — shadowing, surface-семантика update сохраняется через restriction перед extension. (5) **Алиасованная мутабельность — через регион, не через отдельный эффект.** Промежуточный вариант `effect Mut a` с параметризацией по типу элемента отвергнут: два объекта одного типа дают дубликат метки и `mask` на каждой операции. `Alloc r` расширен `read`/`write` — одна capability, потому что все три операции требуют живого региона, и параметризация по идентичности региона даёт один эффект при любом числе объектов. `withRegion` = `runST`, `Ref r` = `STRef s`. Проверено сценарием quicksort: перемежающиеся чтение и запись читаются как императивный код, токен не протаскивается, `Ref` — ω-значение. Заодно зафиксировано: индексация `Int` с bounds check (`Fin n` требует доказательств на каждом арифметическом шаге), системный код в регионах не `@total` и это законно по §4.7. (6) **Заимствования нет и не планируется.** Из четырёх классов употребления `&`/`&mut`: разделяемое чтение → `freeze`, скоупленная мутация → handler региона, дизъюнктное разрезание → линейный `splitAt` (честнее Rust, где `split_at_mut` содержит unsafe), ссылка внутрь структуры не выражается и заменяется индексной адресацией. §10: в.38 закрыт, в.23 уточнён (named instances рассмотрены и отвергнуты стартово — помещают термы в метки row), заведён в.40 (гонка через мутабельный `Ref` в shared-регионе; блокирует Фазу 7, не Фазы 1–5), заведён в.41 (полиморфизм по кратностям) сразу как долгосрочный, с заметкой, что полукольцо кратностей конечно и потому разрешимо перебором — цена ниже, чем у отвергнутых атрибутов. **Требует проверки по реализации:** (а) паттерн-матчинг скалирует кратность поля на кратность скрутинируемого (1·ω = ω, 1·1 = 1) — на этом стоит весь пункт 3; (б) `let 1 p = MkPair arr v` проверяет правую часть при кратности 1; (в) элаборатор не приписывает полям ω помимо дефолта деклараций. Пункт (а) — то же место ядра, что проверялось для правила применения 2026-08-22. **Не проверено сценарием:** массив unique-значений (`read` возвращает копию, значит элементы обязаны быть ω; move-out или swap-in-place — отдельный разбор).
