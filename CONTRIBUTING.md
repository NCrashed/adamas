# Contributing

## Среда

Канонический способ — Nix flake:

```sh
nix develop
```

Даёт тулчейн из `rust-toolchain.toml` плюс `cargo-insta` (snapshot-тесты) и
`cargo-mutants` (mutation testing критических путей).

`nix build` собирает оба бинаря в release и прогоняет тесты в изолированном
sandbox'е. **CI этот путь не проверяет** — там Nix не участвует вообще, — так
что прогонять его руками: перед публикацией и всякий раз, когда добавляется
крейт с системными зависимостями (там понадобятся `buildInputs`).

Без Nix достаточно rustup: он сам подтянет версию и компоненты из
`rust-toolchain.toml`. Версия тулчейна задаётся ровно в одном месте — этом
файле; и flake, и CI читают его.

MSRV (`workspace.package.rust-version`, дублируется в `clippy.toml`) — это
1.85, ровно столько же требуют `clap` и `proptest`. Поднимать его — осознанное
решение, а не побочный эффект `cargo update`: если обновление зависимости
тянет за собой MSRV, либо остаёмся на прежней версии зависимости, либо
поднимаем MSRV отдельным коммитом с записью в decision log. `Cargo.lock`
закоммичен, CI зовёт cargo с `--locked`, так что молча разъехаться не может.

## Проверки перед коммитом

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --all-targets
cargo test --workspace --doc
```

Ровно это гоняет CI (`.github/workflows/ci.yml`), плюс сборку на macOS aarch64
и проверку MSRV. Бенчмарки в CI только собираются и прогоняются один раз —
см. ниже.

## Структура репозитория

```
adamas-design.md              source of truth по дизайну
crates/adamas-core/           ядро: core language, elaborator, type checker
crates/adamas-cli/            драйвер `adamas`
crates/adamas-lsp/            LSP-сервер (заглушка до Фазы 3)
docs/reading-notes/           конспекты статей
docs/examples/                примеры кода на Adamas
tests/golden/                 языковые фикстуры, общие для нескольких крейтов
.github/workflows/            CI
```

Rust-интеграционные тесты живут в `crates/<crate>/tests/`, бенчмарки — в
`crates/<crate>/benches/`: cargo подхватывает эти директории только внутри
пакета, в корне virtual workspace они были бы мёртвым грузом. Корневой
`tests/golden/` — не Rust-код, а данные (см. `tests/golden/README.md`).

## Тесты

- Unit-тесты чистых функций — inline `#[cfg(test)] mod tests`.
- Интеграционные — `crates/<crate>/tests/`. Файл называется по фиче
  (`source_location.rs`, `cli_check.rs`) и собирает её сценарии; функции — без
  префикса `test_`, его роль уже играет атрибут. Каждый файл в `tests/` — это
  отдельный крейт со своей линковкой, поэтому файл на сценарий не заводим.
- Snapshot-тесты (`insta`) — для вывода type checker'а и элаборации.
  Обновление: `cargo insta review` (или `cargo insta test --accept`).
  Файлы `*.snap.new` не коммитятся.
- Property-based (`proptest`) — для core-алгоритмов: round-trip парсера,
  нормализация, разрешение позиций.

Для type-theory-heavy кода предпочитайте property- и snapshot-тесты bespoke
unit-тестам: последние легко начинают тестировать реализацию вместо
спецификации.

## Бенчмарки

```sh
cargo bench --workspace
```

CI проверяет только то, что бенчмарки собираются и проходят один прогон
(`cargo bench -- --test`). Измерений на раннере нет: разброс GitHub Actions на
микро-замерах перекрывает всё, что можно было бы поймать. Публикация истории
поднимается вместе с первым бенчмарком, который меряет компилятор, а не
fork/exec, — то есть с STLC-warm-up'ом (§9).

## Стиль кода

- `cargo fmt --check` и `cargo clippy -- -D warnings` обязаны проходить.
- Модули 200–500 строк; растёт — разбивай.
- `pub` только там, где нужно; остальное `pub(crate)` или приватное.
- Доменные ошибки внутри компилятора — `thiserror`-энумы, `anyhow` в CLI-слое.
  Диагностика для пользователя языка — отдельная инфраструктура со span'ами
  (§7.4), а не те же самые типы ошибок.
- Пользовательские ошибки не паникуют. `panic!` — только internal invariant.
  Это заэнфорсено `clippy::unwrap_used` / `expect_used` (в тестах разрешено).
- Прежде чем оптимизировать — профилируй. Type checker обязан быть быстрым с
  первой строки, но догадки о том, что именно тормозит, обычно неверны.

## Дизайн-документ

`adamas-design.md` — спецификация. Код, противоречащий ей, не принимается:
сначала обсуждение и правка документа, потом реализация.

Любое значимое дизайн-изменение сопровождается записью в decision log (§13):
дата `YYYY-MM-DD`, затронутые §разделы, что было / что стало / обоснование,
отвергнутые альтернативы с причинами.

Открытые вопросы собраны в §10 — перед решением спорного микровопроса
проверяйте, не зафиксирован ли он там.

## Коммиты и PR

Conventional commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
Первая строка — до 72 символов. В теле — что и почему, а не пересказ diff'а,
со ссылкой на разделы дизайна: `Implements §3.2 (predicative universes)`.

Описание PR — три части: **Что / Почему / Как проверить**. Плюс ссылки на
затронутые §разделы и список того, что осознанно оставлено на потом.

Крупные изменения декомпозируются: один коммит — одна логическая единица.
Реализация, форматирование и unrelated cleanup не смешиваются.
